Многопоточность (Concurrency)

Java Core Threads Async

Thread, Runnable, ExecutorService, synchronized, volatile, ReentrantLock, AtomicInteger, CompletableFuture. Deadlock, race condition — как избежать. Один из самых сложных топиков на собеседованиях.

📌 Краткий конспект
Главное правило
Многопоточность нужна для параллельных вычислений и неблокирующего I/O. Главные проблемы: race condition (гонка данных) и deadlock (взаимная блокировка). Современный подход: ExecutorService + CompletableFuture вместо ручного управления потоками.

🧵 Thread и Runnable

Поток (Thread) — наименьшая единица выполнения. В Java есть 3 способа создать поток:

СпособКакПлюсы / Минусы
Наследование Threadclass MyThread extends Thread❌ Нельзя наследовать другой класс
Реализация Runnableclass Task implements Runnable✅ Можно передавать в ExecutorService

⚠️ thread.start() vs thread.run()
start() — создаёт новый поток и выполняет в нём run(). run() напрямую — выполняет в текущем потоке, никакой многопоточности! Это классическая ошибка новичков.

⚡ ExecutorService — пул потоков

Никогда не создавай потоки вручную в продакшене. ExecutorService управляет пулом потоков — переиспользует их, ограничивает количество, обрабатывает очередь задач.

Фабричный методТип пулаКогда

newCachedThreadPool()Растёт по необходимостиМного коротких задач
newSingleThreadExecutor()1 поток, очередь задачПоследовательное выполнение
newScheduledThreadPool(n)Планировщик, с задержкойПериодические задачи

💡 Virtual Threads (Java 21)
Виртуальные потоки — лёгкие потоки управляемые JVM, не OS. Можно создать миллионы без проблем с памятью. Идеальны для I/O-задач (HTTP, БД). Революция для Java Backend.
🚫 Не используй Executors.newCachedThreadPool() в продакшене
При резком росте нагрузки создаст тысячи потоков → OutOfMemoryError. Используй ThreadPoolExecutor с явными границами или готовые решения типа Spring's TaskExecutor.
🔐 synchronized и volatile
synchronized
  • Взаимное исключение (mutex)
  • Только один поток в блоке одновременно
  • Гарантирует видимость + атомарность
  • Может быть на методе или блоке
  • Монитор — любой Object
  • Блокирует поток при ожидании (BLOCKED)
volatile
  • Только гарантия видимости
  • Все потоки видят актуальное значение
  • НЕ гарантирует атомарность (i++ не атомарен!)
  • Только для одной переменной
  • Нет блокировки — быстрее synchronized
  • Применение: флаги остановки, singleton
⚠️ volatile НЕ заменяет synchronized
volatile int counter; counter++; — НЕ атомарная операция! counter++ — это три шага: read → increment → write. Между ними другой поток может вмешаться. Используй AtomicInteger или synchronized.

💡 ReentrantLock vs synchronized
ReentrantLock — всегда используй в блоке try { lock.lock(); ... } finally { lock.unlock(); }. Если забыть unlock() — deadlock навсегда. synchronized разблокируется автоматически — безопаснее.
⚛️ Atomic классы

Пакет java.util.concurrent.atomic — потокобезопасные операции без synchronized, используют аппаратные CAS-инструкции (Compare-And-Swap).

💡 CAS (Compare-And-Swap)
Атомарная CPU-инструкция: «если текущее значение == ожидаемое, то заменить на новое». Нет блокировок → нет deadlock → очень быстро. AtomicInteger.compareAndSet(expected, newValue).

💥 Deadlock, Race Condition, Livelock
🔴 Deadlock — взаимная блокировка ▼

Ситуация: Поток A держит блокировку 1 и ждёт блокировку 2. Поток B держит блокировку 2 и ждёт блокировку 1. Оба ждут вечно.

Условия (все 4 должны быть): взаимное исключение, удержание и ожидание, отсутствие вытеснения, циклическое ожидание.

Решения: всегда захватывать блокировки в одном порядке, использовать tryLock(timeout), избегать вложенных блокировок, использовать высокоуровневые примитивы.

🟡 Race Condition — гонка данных ▼

Ситуация: Два потока читают и изменяют одну переменную без синхронизации. Результат зависит от порядка выполнения — непредсказуем.

Пример: counter++ из двух потоков одновременно. Ожидаем 2, но можем получить 1 — оба прочитали 0, оба записали 1.

Решения: synchronized, AtomicInteger, volatile (только для видимости), неизменяемые объекты.

🟠 Livelock и Starvation ▼

Livelock: Потоки активны, но не делают полезной работы — постоянно реагируют друг на друга. Как два человека в коридоре, которые уступают дорогу одновременно.

Starvation (голодание): Поток никогда не получает ресурс, потому что другие потоки с более высоким приоритетом всё время его забирают.

Решения: fair locks (new ReentrantLock(true)), равные приоритеты, случайные задержки.

💻 Примеры кода
1. Thread, Runnable, Callable — три способа создания
Java
// ── Способ 1: наследование Thread (устаревший, избегай)
class MyThread extends Thread {
    @Override
    public void run() {                         // тело потока — что выполняется
        System.out.println("Thread: " + getName()); // getName() — имя потока
    }
}
MyThread t = new MyThread();
t.setName("Worker-1");                          // имя видно в профайлере
t.start();                                       // ВАЖНО: start(), не run()!

// ── Способ 2: Runnable (рекомендуется)
Runnable task = () -> {                            // лямбда = реализация Runnable
    System.out.println("Runnable в потоке: "
        + Thread.currentThread().getName());      // имя текущего потока
};
new Thread(task).start();                        // оборачиваем в Thread

// ── Способ 3: Callable — возвращает результат
Callable<Integer> callable = () -> {              // Callable возвращает T
    Thread.sleep(100);                            // имитируем работу
    return 42;                                    // возвращаем результат
};

ExecutorService executor = Executors.newSingleThreadExecutor();
Future<Integer> future = executor.submit(callable); // запускаем, получаем Future

try {
    Integer result = future.get();               // БЛОКИРУЕТ поток до готовности
    System.out.println("Результат: " + result);  // 42
} catch (InterruptedException | ExecutionException e) {
    Thread.currentThread().interrupt();           // восстанавливаем флаг прерывания
} finally {
    executor.shutdown();                          // ВСЕГДА завершай ExecutorService
}
2. ExecutorService — пул потоков правильно
Java
// ── Создание пула с правильными параметрами
int cores = Runtime.getRuntime().availableProcessors(); // число CPU ядер

// CPU-задачи: cores потоков (нет смысла больше ядер)
ExecutorService cpuPool = Executors.newFixedThreadPool(cores);

// I/O-задачи: больше потоков (ждут сеть/диск)
ExecutorService ioPool = Executors.newFixedThreadPool(cores * 4);

// ── Отправка задач
Future<String> f1 = cpuPool.submit(() -> computeHeavy()); // Callable
cpuPool.execute(() -> logSomething());                    // Runnable (без результата)

// ── invokeAll — запустить все и дождаться
List<Callable<String>> tasks = List.of(
    () -> fetchUser(1L),        // задача 1
    () -> fetchUser(2L),        // задача 2
    () -> fetchUser(3L)         // задача 3
);
List<Future<String>> results = ioPool.invokeAll(tasks);   // ждём все
for (Future<String> res : results) {
    System.out.println(res.get());  // получаем каждый результат
}

// ── Правильное завершение пула
cpuPool.shutdown();                              // прекратить принимать задачи
if (!cpuPool.awaitTermination(60, TimeUnit.SECONDS)) { // ждём завершения 60 сек
    cpuPool.shutdownNow();                        // принудительно если не успел
}

// ── ScheduledExecutorService — периодические задачи
ScheduledExecutorService scheduler =
    Executors.newScheduledThreadPool(1);

scheduler.scheduleAtFixedRate(             // выполнять каждые N секунд
    () -> System.out.println("Tick"),       // задача
    0,                                       // начальная задержка
    5,                                       // период
    TimeUnit.SECONDS                         // единица времени
);
3. synchronized и volatile — примеры правильного использования
Java
// ── Synchronized метод — блокировка на this
public class Counter {
    private int count = 0;                    // обычное поле — небезопасно

    public synchronized void increment() {   // synchronized = блокировка на this
        count++;                               // теперь атомарно: read+inc+write
    }

    public synchronized int getCount() {     // тоже synchronized для видимости
        return count;
    }
}

// ── Synchronized блок — более гранулярный контроль
public class BankAccount {
    private final Object lock = new Object(); // отдельный объект-монитор
    private double balance;

    public void transfer(BankAccount to, double amount) {
        synchronized (lock) {                 // только этот блок — критическая секция
            if (balance >= amount) {
                balance -= amount;             // списываем
                to.balance += amount;          // зачисляем
            }
        }                                     // блокировка снимается автоматически
    }
}

// ── volatile — только видимость, не атомарность
public class Worker implements Runnable {
    private volatile boolean running = true; // volatile: все потоки видят изменение

    public void stop() {
        running = false;                      // главный поток меняет флаг
    }

    @Override
    public void run() {
        while (running) {                     // рабочий поток видит изменение
            doWork();                          // без volatile мог бы loop вечно
        }
        System.out.println("Остановлен");
    }
}

// ── Double-checked locking Singleton (volatile обязателен!)
public class Singleton {
    private static volatile Singleton instance; // volatile — запрет переупорядочивания

    public static Singleton getInstance() {
        if (instance == null) {              // первая проверка — без блокировки
            synchronized (Singleton.class) { // блокировка только при первом создании
                if (instance == null) {      // вторая проверка — уже под блокировкой
                    instance = new Singleton(); // создаём единственный экземпляр
                }
            }
        }
        return instance;
    }
}
4. AtomicInteger и ReentrantLock
Java
import java.util.concurrent.atomic.*;
import java.util.concurrent.locks.*;

// ── AtomicInteger — счётчик без synchronized
AtomicInteger counter = new AtomicInteger(0);  // начальное значение 0

counter.incrementAndGet();     // ++counter атомарно, возвращает новое значение
counter.getAndIncrement();     // counter++ атомарно, возвращает старое значение
counter.addAndGet(5);          // прибавить 5, вернуть новое
counter.get();                  // просто прочитать

// CAS — compare and set (используется внутри всех Atomic)
boolean updated = counter.compareAndSet(10, 20); // если значение == 10, поставить 20
// true если обновилось, false если кто-то уже изменил значение

// ── ReentrantLock — гибкая блокировка
ReentrantLock lock = new ReentrantLock();       // несправедливый по умолчанию
// new ReentrantLock(true) — справедливый: FIFO порядок потоков

lock.lock();                                    // захватить блокировку (ждать если занята)
try {
    criticalSection();                           // защищённый код
} finally {
    lock.unlock();                               // ВСЕГДА в finally — иначе deadlock!
}

// tryLock — не блокируем поток, пробуем захватить
if (lock.tryLock(500, TimeUnit.MILLISECONDS)) { // пробуем 500мс
    try {
        doWork();
    } finally {
        lock.unlock();
    }
} else {
    System.out.println("Не удалось захватить блокировку"); // не ждём
}

// ── ReadWriteLock — оптимизация для чтения
ReadWriteLock rwLock = new ReentrantReadWriteLock();
Lock readLock  = rwLock.readLock();   // много потоков могут читать одновременно
Lock writeLock = rwLock.writeLock(); // только один поток пишет, остальные ждут

public String read() {
    readLock.lock();                  // несколько потоков читают параллельно
    try { return data; }
    finally { readLock.unlock(); }
}

public void write(String val) {
    writeLock.lock();                 // эксклюзивный доступ при записи
    try { data = val; }
    finally { writeLock.unlock(); }
}
5. CompletableFuture — асинхронные цепочки
Java
import java.util.concurrent.*;

// ── Простая асинхронная задача
CompletableFuture<String> future =
    CompletableFuture.supplyAsync(() -> {      // запускает в ForkJoinPool
        Thread.sleep(200);                      // имитируем I/O
        return fetchUserFromDB(1L);           // результат
    });

// ── Цепочка преобразований
CompletableFuture<String> result = future
    .thenApply(String::toUpperCase)          // преобразуем (синхронно в том же потоке)
    .thenApply(s -> "Пользователь: " + s)     // ещё преобразование
    .exceptionally(ex -> "Ошибка: " + ex.getMessage()); // обработка ошибки

System.out.println(result.join());           // join() блокирует и возвращает результат

// ── Комбинирование двух задач
CompletableFuture<User>    userFuture    = CompletableFuture.supplyAsync(() -> getUser(1L));
CompletableFuture<Profile> profileFuture = CompletableFuture.supplyAsync(() -> getProfile(1L));

CompletableFuture<String> combined =
    userFuture.thenCombine(profileFuture,     // ждём обоих, затем комбинируем
        (user, profile) -> user.getName() + " — " + profile.getBio());

// ── Запустить несколько параллельно, дождаться всех
List<CompletableFuture<String>> futures = List.of(
    CompletableFuture.supplyAsync(() -> callServiceA()), // параллельно
    CompletableFuture.supplyAsync(() -> callServiceB()), // параллельно
    CompletableFuture.supplyAsync(() -> callServiceC())  // параллельно
);

CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
    .join();                                   // ждём ВСЕ задачи

List<String> results = futures.stream()
    .map(CompletableFuture::join)             // собираем результаты
    .collect(Collectors.toList());

// ── Свой пул потоков (рекомендуется для I/O)
ExecutorService myPool = Executors.newFixedThreadPool(10);
CompletableFuture.supplyAsync(() -> heavyIO(), myPool)  // не ForkJoinPool!
    .thenAcceptAsync(res -> process(res), myPool);        // продолжить в том же пуле
6. CountDownLatch и Semaphore
Java
// ── CountDownLatch: ждём пока N потоков завершат работу
int workerCount = 3;
CountDownLatch latch = new CountDownLatch(workerCount); // счётчик = 3

for (int i = 0; i < workerCount; i++) {
    int id = i;
    new Thread(() -> {
        try {
            doWork(id);                      // выполняем работу
        } finally {
            latch.countDown();               // декрементируем счётчик (3→2→1→0)
        }
    }).start();
}

latch.await();                             // главный поток ждёт пока счётчик = 0
System.out.println("Все потоки завершили работу");

// ── Semaphore: ограничиваем число одновременных потоков
Semaphore semaphore = new Semaphore(3);    // максимум 3 потока одновременно

void accessResource() throws InterruptedException {
    semaphore.acquire();                     // захватить разрешение (ждать если нет)
    try {
        useResource();                       // максимум 3 потока здесь одновременно
    } finally {
        semaphore.release();                 // ВСЕГДА освобождать в finally
    }
}
❓ Вопросы для собеседования
В чём разница между synchronized и volatile?
What is the difference between synchronized and volatile?
Hard▼
✅ Ответ
synchronized гарантирует атомарность + видимость: только один поток выполняет блок, другие ждут. volatile гарантирует только видимость: все потоки видят актуальное значение переменной, но операции не атомарны. i++ с volatile — не потокобезопасно, нужен AtomicInteger или synchronized.
🔥 Сильный ответ
«Под капотом volatile запрещает CPU и JIT переупорядочивать инструкции (memory barrier) и гарантирует чтение из main memory, а не из CPU кэша. synchronized же использует монитор объекта и создаёт happens-before отношение между потоками.»
Что такое deadlock и как его избежать?
What is a deadlock and how do you prevent it?
Hard▼
✅ Ответ
Deadlock — два потока ждут ресурсы друг друга и никогда не продолжат. Профилактика: 1) всегда захватывать блокировки в одном порядке, 2) использовать tryLock(timeout) вместо lock(), 3) избегать вложенных synchronized блоков, 4) использовать высокоуровневые примитивы (ConcurrentHashMap вместо synchronized Map).
⚠️ Ошибка кандидата
«Просто не использовать synchronized» — неверно. Надо уметь применять синхронизацию правильно, а не избегать её.
Чем CompletableFuture лучше Future?
What advantages does CompletableFuture have over Future?
Medium▼
✅ Ответ
Future.get() всегда блокирует поток. Нельзя комбинировать несколько задач, нет обработки ошибок, нельзя задать колбек. CompletableFuture: цепочки через thenApply/thenCompose, комбинирование через allOf/anyOf/thenCombine, обработка ошибок через exceptionally, можно завершить вручную через complete().

What is a race condition? Give an example and solution.
Medium▼
✅ Ответ
Race condition — результат зависит от порядка выполнения потоков. Пример: два потока делают balance -= amount. Оба читают 1000, оба вычитают 100, оба записывают 900 — потеряли одно списание. Решения: synchronized, AtomicInteger, неизменяемые объекты, ограничение мутации одним потоком.
Когда использовать ReentrantLock вместо synchronized?
When would you use ReentrantLock instead of synchronized?
Medium▼
✅ Ответ
ReentrantLock выбирают когда нужно: 1) tryLock(timeout) — не блокировать бесконечно, 2) прерываемое ожидание (lockInterruptibly()), 3) справедливый порядок FIFO (new ReentrantLock(true)), 4) несколько условных переменных (newCondition()). Для простых случаев — synchronized проще и читаемее.
Что такое happens-before в Java Memory Model?
What is happens-before in the Java Memory Model?
Hard▼
✅ Ответ
Happens-before — гарантия: если действие A happens-before B, то B видит все изменения A. Основные правила: запись в volatile HB чтению той же переменной; unlock монитора HB его следующему lock; Thread.start() HB первому действию потока; Thread.join() HB возврату join(). JMM позволяет CPU и JIT переупорядочивать инструкции — happens-before запрещает опасные переупорядочивания.
💡 Совет
Этот вопрос задают Senior-позициям. Достаточно сказать: «HB — гарантия видимости изменений между потоками. volatile и synchronized создают HB отношения.»
