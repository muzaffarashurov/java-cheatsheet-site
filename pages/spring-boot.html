🔄 IoC и Dependency Injection

IoC (Inversion of Control) — инверсия управления. Вместо того чтобы ты создавал объекты (new Service()), это делает контейнер Spring. Ты только описываешь зависимости — Spring сам их собирает.

DI (Dependency Injection) — один из способов реализации IoC. Зависимости «вливаются» в объект снаружи — через конструктор, setter или поле.

3 способа инжекции зависимостей
СпособПримерРекомендация
Конструктор ✅ public Service(Repo repo) { this.repo = repo; } ✅ Рекомендован: immutable, легко тестировать
Setter @Autowired void setRepo(Repo r) { repo = r; } ⚠️ Только для опциональных зависимостей
Поле ❌ @Autowired private Repo repo; ❌ Избегай: нельзя тестировать без Spring, скрывает зависимости
✅ Почему конструктор — лучший способ DI
1. Зависимости явные и обязательные — нельзя создать объект без них.
2. Поля можно сделать final — объект immutable.
3. Легко тестировать — просто передай мок в конструктор без Spring.
4. С Lombok @RequiredArgsConstructor — никакого бойлерплейта.

⚠️ Проблема: prototype бин в singleton
Если singleton бин зависит от prototype бина — prototype создаётся один раз при инициализации singleton и больше не обновляется. Решение: ApplicationContext.getBean(), @Lookup, или ObjectProvider<T>.

⚙️ Auto-Configuration

Spring Boot анализирует classpath и автоматически настраивает приложение. Добавил spring-boot-starter-data-jpa → Spring сам настроит DataSource, EntityManagerFactory, TransactionManager.

Как работает Auto-Configuration изнутри ▼

1. @SpringBootApplication включает @EnableAutoConfiguration.

2. Spring Boot читает файл META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (до Boot 2.7: spring.factories).

3. Для каждого Auto-Configuration класса проверяются условия: @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty.

4. Если условия выполнены — бины регистрируются. Твои собственные бины имеют приоритет (перекрывают auto-configured).

💡 Отладка
Запусти с --debug или добавь logging.level.org.springframework.boot.autoconfigure=DEBUG — увидишь какие auto-configurations сработали и почему.

🏭 ApplicationContext

ApplicationContext — главный IoC-контейнер Spring. Управляет жизненным циклом бинов, разрешает зависимости, публикует события, загружает конфигурацию.

Метод контекстаОписание
getBean(Class<T>)Получить бин по типу (кидает если нет или несколько)
getBean(String name)Получить бин по имени
getBeanNamesForType(Class<T>)Все имена бинов заданного типа
containsBean(String name)Существует ли бин с таким именем
publishEvent(event)Опубликовать событие
getEnvironment()Доступ к properties и profiles
⚠️ Не злоупотребляй getBean()
Прямое обращение к ApplicationContext — это Service Locator антипаттерн. Используй только в крайних случаях (например, prototype бины в singleton). В обычном коде — всегда DI через конструктор.
События Spring (Event System)

Spring реализует паттерн Observer через события. Можно публиковать и слушать как встроенные события (ContextRefreshedEvent, ApplicationReadyEvent), так и свои.

🔐 Безопасность Actuator в продакшене
По умолчанию открыт только /health. В продакшене: закрой /actuator/** за Spring Security или вынеси на отдельный порт (management.server.port=8081). Никогда не открывай /env и /beans публично — там секреты!

✅ Best Practices и типичные ошибки
✅ Best Practices
  • DI только через конструктор (+ Lombok @RequiredArgsConstructor)
  • Зависимости через интерфейсы, а не конкретные классы
  • Один @SpringBootApplication в корневом пакете
  • @ConfigurationProperties вместо множества @Value
  • Никогда не хранить секреты в application.yml — ENV переменные
  • Закрывать Actuator endpoints в продакшене
  • Использовать профили для разных окружений
  • Логировать через @Slf4j (Lombok), не System.out.println
🚫 Частые ошибки
  • Field injection (@Autowired на поле) — скрывает зависимости
  • Circular dependency — A зависит от B, B от A
  • Stateful singleton бины — потокобезопасность нарушена
  • Слишком много бинов с @Primary — неочевидное поведение
  • Не закрывать ExecutorService и ресурсы в @PreDestroy
  • Тяжёлая логика в @PostConstruct — замедляет старт
  • Хранить секреты в application.yml в репозитории

1. @SpringBootApplication и точка входа

@SpringBootApplication   // = @Configuration + @EnableAutoConfiguration + @ComponentScan
public class MyApplication {

    }
}

// ── Настройка SpringApplication программно
@SpringBootApplication
public class MyApplication {

    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(MyApplication.class);
        app.setAdditionalProfiles("dev");              // активировать профиль
        app.setBannerMode(Banner.Mode.OFF);             // убрать баннер Spring
        app.run(args);
    }

// ── CommandLineRunner — выполнить код после старта
@Component
public class DataInitializer implements CommandLineRunner {

    private final UserRepository userRepository;  // инжектируем через конструктор

    public DataInitializer(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Override
    public void run(String... args) {              // вызывается после старта
        if (userRepository.count() == 0) {          // только если БД пуста
            userRepository.save(new User("admin", "admin@example.com"));
        }
    }
}
2. @Configuration и @Bean — регистрация бинов вручную
Java
@Configuration                                    // класс конфигурации Spring
public class AppConfig {

    // ── @Bean — регистрируем бин вручную (для сторонних классов)
    @Bean
    public ObjectMapper objectMapper() {           // имя бина = имя метода
        ObjectMapper mapper = new ObjectMapper();
        mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);
        mapper.registerModule(new JavaTimeModule());  // поддержка LocalDate и др.
        return mapper;                               // Spring управляет этим объектом
    }

    // ── @Bean с зависимостью — Spring автоматически передаёт параметр
    @Bean
    public RestTemplate restTemplate(ObjectMapper objectMapper) { // DI через параметр
        return new RestTemplateBuilder()
            .messageConverters(new MappingJackson2HttpMessageConverter(objectMapper))
            .build();
    }

    // ── @Bean с профилем — создаётся только для prod
    @Bean
    @Profile("prod")                               // только в prod окружении
    public DataSource productionDataSource() {
        return DataSourceBuilder.create()
            .url("jdbc:postgresql://prod-server:5432/mydb")
            .build();
    }

    // ── @Bean с условием — создаётся только если property задан
    @Bean
    @ConditionalOnProperty(name = "feature.cache.enabled", havingValue = "true")
    public CacheManager cacheManager() {           // включён только если feature.cache.enabled=true
        return new ConcurrentMapCacheManager("users", "products");
    }
}
3. @ConfigurationProperties — type-safe конфигурация
Java
// ── application.yml
// app:
//   name: My App
//   version: 1.0.0
//   jwt:
//     secret: mySecretKey
//     expiration: 86400
//   mail:
//     host: smtp.gmail.com
//     port: 587

@ConfigurationProperties(prefix = "app")  // читаем всё что начинается с "app."
@Component                                  // или @EnableConfigurationProperties в конфиге
public class AppProperties {

    private String name;                    // → app.name
    private String version;                 // → app.version
    private Jwt jwt = new Jwt();            // → app.jwt.*
    private Mail mail = new Mail();          // → app.mail.*

    // геттеры и сеттеры обязательны для @ConfigurationProperties
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    // ... остальные геттеры/сеттеры

    public static class Jwt {
        private String secret;                // → app.jwt.secret
        private long expiration;              // → app.jwt.expiration (в секундах)
        // геттеры/сеттеры...
    }

    public static class Mail {
        private String host;                  // → app.mail.host
        private int port;                     // → app.mail.port
        // геттеры/сеттеры...
    }
}

// ── Использование в сервисе
@Service
public class JwtService {

    private final AppProperties appProperties;   // инжектируем весь конфиг

    public JwtService(AppProperties appProperties) {
        this.appProperties = appProperties;
    }

    public String getSecret() {
        return appProperties.getJwt().getSecret(); // type-safe доступ к настройкам
    }
}
4. Scope, @Primary, @Qualifier
Java
// ── @Primary — реализация по умолчанию
@Service
@Primary                                          // используется когда не указан @Qualifier
public class EmailNotificationService implements NotificationService { ... }

@Service
public class SmsNotificationService implements NotificationService { ... }

// ── @Qualifier — явный выбор реализации
@Service
public class OrderService {
    private final NotificationService notificationService;

    public OrderService(
        @Qualifier("smsNotificationService") // имя бина = имя класса с маленькой буквы
        NotificationService notificationService) {
        this.notificationService = notificationService;
    }
}

// ── @Scope prototype — новый объект каждый раз
@Component
@Scope("prototype")                              // каждый getBean() = новый объект
public class ReportGenerator {
    private List<String> lines = new ArrayList<>(); // состояние свежее каждый раз
    public void addLine(String line) { lines.add(line); }
}

// ── Правильное использование prototype в singleton
@Service
public class ReportService {
    private final ObjectProvider<ReportGenerator> generatorProvider; // lazy

    public ReportService(ObjectProvider<ReportGenerator> generatorProvider) {
        this.generatorProvider = generatorProvider;
    }

    public void generateReport() {
        ReportGenerator gen = generatorProvider.getObject(); // новый экземпляр!
        gen.addLine("Отчёт сгенерирован");
    }
}

// ── @PostConstruct и @PreDestroy
@Service
public class CacheService {
    private Map<String, Object> cache;

    @PostConstruct                                  // после DI, перед первым использованием
    public void init() {
        cache = new ConcurrentHashMap<>();          // инициализация кэша
        warmUpCache();                              // прогрев — загружаем часто нужные данные
    }

    @PreDestroy                                     // перед уничтожением бина
    public void cleanup() {
        cache.clear();                              // очищаем ресурсы
        System.out.println("Кэш очищен при остановке");
    }
}
5. Spring Events — публикация и обработка событий
Java
// ── Своё событие
public class UserRegisteredEvent extends ApplicationEvent {  // наследуем
    private final String email;                                  // данные события

    public UserRegisteredEvent(Object source, String email) {
        super(source);                                           // источник события
        this.email = email;
    }

    public String getEmail() { return email; }
}

// ── Публикация события
@Service
public class UserService {
    private final ApplicationEventPublisher eventPublisher; // Spring инжектирует
    private final UserRepository userRepository;

    public UserService(ApplicationEventPublisher pub, UserRepository repo) {
        this.eventPublisher = pub;
        this.userRepository = repo;
    }

    public User register(String email) {
        User user = userRepository.save(new User(email));           // сохраняем
        eventPublisher.publishEvent(new UserRegisteredEvent(this, email)); // публикуем
        return user;
    }
}

// ── Слушатель события (отдельный бин)
@Component
public class WelcomeEmailListener {

    @EventListener                                  // слушаем событие
    public void onUserRegistered(UserRegisteredEvent event) {
        // вызывается автоматически при публикации UserRegisteredEvent
        sendWelcomeEmail(event.getEmail());         // отправляем приветственное письмо
    }

    @EventListener
    @Async                                          // выполнить асинхронно (не блокировать)
    public void onUserRegisteredAsync(UserRegisteredEvent event) {
        sendAnalyticsData(event.getEmail());         // аналитика асинхронно
    }
}

// ── Слушать ApplicationReadyEvent — приложение полностью запущено
@Component
public class StartupListener {

    @EventListener(ApplicationReadyEvent.class)   // после полного старта
    public void onApplicationReady() {
        System.out.println("🚀 Приложение готово!");
    }
}
❓ Вопросы для собеседования
Что такое IoC и DI? В чём разница?
What is IoC and DI? What is the difference?
Easy▼
✅ Ответ
IoC — принцип: контроль над созданием объектов передаётся от программиста к фреймворку. Вместо new Service() — контейнер сам создаёт и управляет объектами.
DI — конкретная реализация IoC: зависимости «вливаются» в объект через конструктор, setter или поле. DI — один из способов IoC, самый популярный.
🔥 Сильный ответ
«IoC — широкий принцип (управление передано контейнеру), DI — его реализация через передачу зависимостей. Я предпочитаю DI через конструктор: зависимости явные, поля можно сделать final, легко тестировать без Spring — просто передаю мок в конструктор.»
Что делает @SpringBootApplication?
What does @SpringBootApplication do?
Easy▼
✅ Ответ
Это мета-аннотация, объединяющая три:
@Configuration — класс является источником бин-определений.
@EnableAutoConfiguration — включает авто-конфигурацию по classpath.
@ComponentScan — сканирует пакет (и подпакеты) в поиске компонентов.
Что такое Auto-Configuration? Как работает?
What is Spring Boot Auto-Configuration and how does it work?
Medium▼
✅ Ответ
Spring Boot анализирует classpath и автоматически создаёт нужные бины. Механизм: читает список Auto-Configuration классов из META-INF/spring.factories (или imports файла). Каждый класс проверяет условия через @ConditionalOnClass, @ConditionalOnMissingBean и др. Если условия выполнены — бины регистрируются. Твои бины всегда имеют приоритет.
💡 Пример
Добавил spring-boot-starter-data-jpa → на classpath появился Hibernate → HibernateJpaAutoConfiguration видит это и создаёт EntityManagerFactory, TransactionManager и DataSource автоматически.
В чём разница между @Component, @Service, @Repository?
What is the difference between @Component, @Service, and @Repository?
Easy▼
✅ Ответ
Все три — специализации @Component и регистрируют бин в контейнере. Разница — семантическая и одна техническая: @Repository дополнительно активирует перевод исключений БД в Spring DataAccessException. @Service — чистая семантика (бизнес-слой). Используй по назначению — это улучшает читаемость и позволяет AOP таргетировать по слоям.
Какие Scope есть у бинов? Что такое singleton scope?
What are bean scopes in Spring? Explain singleton scope.
Medium▼
✅ Ответ
Основные: singleton (один на контейнер, по умолчанию), prototype (новый при каждом запросе), request, session, application (для Web). Singleton — самый частый: один экземпляр на весь контейнер, создаётся при старте. Важно: singleton-бины должны быть stateless — иначе потокобезопасность нарушена.
⚠️ Ошибка кандидата
Путают Spring singleton и паттерн Singleton. Spring singleton — один бин на контейнер. Паттерн Singleton — один объект на JVM. Это разные вещи! В тестах может быть несколько контейнеров.
Как Spring решает конфликт при нескольких реализациях одного интерфейса?
How does Spring resolve ambiguity when multiple beans implement the same interface?
Medium▼
✅ Ответ
Spring кидает NoUniqueBeanDefinitionException если не может выбрать. Решения: 1) @Primary — пометить основную реализацию, 2) @Qualifier("beanName") — явно указать какую инжектировать, 3) инжектировать List<Interface> — получишь все реализации, 4) Map<String, Interface> — имя бина → реализация.
Что такое circular dependency и как решить?
What is circular dependency in Spring and how to fix it?
Hard▼
✅ Ответ
Circular dependency: A зависит от B, B зависит от A. При конструкторной инжекции — Spring кидает BeanCurrentlyInCreationException. Решения: 1) рефакторинг архитектуры — вынести общую логику в третий класс C, 2) @Lazy на одной из зависимостей — создаётся прокси, 3) setter injection для одной из зависимостей. Лучшее решение — исправить архитектуру: circular dependency часто признак неправильного разделения обязанностей.
