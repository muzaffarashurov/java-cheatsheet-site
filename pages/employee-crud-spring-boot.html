📦 Шаг 1: Зависимости (pom.xml)

Maven управляет сборкой и зависимостями. spring-boot-starter-parent задаёт версии и настройки по умолчанию.

pom.xml 
<?xml version="1.0" encoding="UTF-8"?>
<!-- pom.xml — "сердце" Maven-проекта. Управляет сборкой, зависимостями, плагинами -->
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">

    <!-- Наследуемся от spring-boot-starter-parent: версии, плагины, настройки по умолчанию -->
    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.2.5</version>
    </parent>

    <!-- Координаты проекта: уникальный идентификатор в репозитории -->
    <groupId>com.example</groupId>
    <artifactId>employee-crud</artifactId>
    <version>0.0.1-SNAPSHOT</version>
    <name>Employee CRUD</name>
    <description>Учебное Spring Boot приложение — CRUD операции с сотрудниками</description>

    <!-- Свойства: версия Java, кодировка и т.д. -->
    <properties>
        <java.version>17</java.version>
    </properties>

    <!-- ЗАВИСИМОСТИ: библиотеки, которые Maven скачает автоматически -->
    <dependencies>

        <!-- spring-boot-starter-web: Tomcat + Spring MVC + Jackson (JSON) -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>

        <!-- spring-boot-starter-data-jpa: Hibernate + Spring Data JPA (автогенерация SQL!) -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-data-jpa</artifactId>
        </dependency>

        <!-- spring-boot-starter-validation: @NotBlank, @Email, @Min, @Max -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-validation</artifactId>
        </dependency>

        <!-- H2 Database: in-memory БД для разработки/тестов (данные пропадают при перезапуске) -->
        <dependency>
            <groupId>com.h2database</groupId>
            <artifactId>h2</artifactId>
            <scope>runtime</scope>
        </dependency>

        <!-- Lombok: @Data, @Builder, @NoArgsConstructor — убирает шаблонный код -->
        <dependency>
            <groupId>org.projectlombok</groupId>
            <artifactId>lombok</artifactId>
            <optional>true</optional>
        </dependency>

        <!-- spring-boot-starter-test: JUnit 5, Mockito, AssertJ — для тестов -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>

    </dependencies>

    <!-- СБОРКА: плагины для Maven -->
    <build>
        <plugins>
            <!-- spring-boot-maven-plugin: запуск, упаковка в fat JAR -->

                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
                <configuration>
                    <excludes>
                        <exclude>
                            <groupId>org.projectlombok</groupId>

⚙️ Шаг 2б: Конфигурация (application.properties)

💡 YAML vs Properties
application.yml — читаемый, с вложенностью (отступы).
application.properties — плоский формат, ключ=значение. Оба работают одинаково!
🟢 H2 (In-Memory) — для разработки

spring.datasource.driver-class-name=org.h2.Driver
spring.datasource.username=sa
spring.datasource.password=

# --- JPA/Hibernate ---
spring.jpa.hibernate.ddl-auto=update
spring.jpa.defer-datasource-initialization=true
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

# --- H2 Console (веб-интерфейс) ---
spring.h2.console.enabled=true

⚠️ Профили (Profiles) — лучший способ
Вместо того чтобы менять файл вручную, используй Spring Profiles:

application.yml — общие настройки (порт, логирование)
application-dev.yml — H2 для разработки
application-prod.yml — PostgreSQL для продакшена

Запуск с профилем: mvn spring-boot:run -Dspring.profiles.active=prod

🚀 Шаг 3: Точка входа

@SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan. Автоматически настраивает контекст и запускает встроенный Tomcat.

EmployeeCrudApplication.java
/*
 * EmployeeCrudApplication.java — ТОЧКА ВХОДА в приложение
 * @SpringBootApplication — комбинация трёх аннотаций:
 *   @Configuration — этот класс содержит настройки Spring
 *   @EnableAutoConfiguration — Spring настраивает компоненты автоматически
 *   @ComponentScan — сканирует пакет и находит @Controller, @Service, @Repository
 */
package com.example.employeecrud;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class EmployeeCrudApplication {
    
    /*
     * main() — стандартная точка входа Java.
     * SpringApplication.run() делает ВСЮ магию:
     *   1. Создаёт Spring-контекст (контейнер для всех объектов)
     *   2. Сканирует и создаёт все бины (управляемые объекты)
     *   3. Запускает встроенный веб-сервер Tomcat
     *   4. Приложение готово принимать HTTP-запросы!
     */
    public static void main(String[] args) {
        SpringApplication.run(EmployeeCrudApplication.class, args);
    }
}

🗃️ Шаг 4: Модель / Entity

🔑 JPA Callbacks
@PrePersist и @PreUpdate автоматически проставляют даты создания/обновления перед вставкой или изменением в БД.
Employee.java
/*
 * Employee.java — МОДЕЛЬ (Entity) — представление сотрудника в БД
 * Entity — Java-класс, который представляет таблицу в базе данных.
 * Каждый экземпляр = одна строка в таблице "employees".
 */
package com.example.employeecrud.model;

import jakarta.persistence.*;
import jakarta.validation.constraints.*;
import lombok.*;
import java.time.LocalDateTime;

/*
 * === АННОТАЦИИ LOMBOK (генерация кода при компиляции) ===
 * @Data — генерирует getters, setters, toString(), equals(), hashCode()
 * @Builder — паттерн Builder для удобного создания объектов
 * @NoArgsConstructor — пустой конструктор (нужен для JPA/Hibernate)
 * @AllArgsConstructor — конструктор со всеми полями (нужен для @Builder)
 */
@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor

/*
 * === АННОТАЦИИ JPA (связь с базой данных) ===
 * @Entity — говорит JPA: "Этот класс — таблица в базе данных!"
 * @Table(name = "employees") — имя таблицы в БД (явно указываем)
 */
@Entity
@Table(name = "employees")
public class Employee {
    
    /*
     * @Id — это поле является ПЕРВИЧНЫМ КЛЮЧОМ (уникальный идентификатор).
     * @GeneratedValue — база данных САМА генерирует id (1, 2, 3, ...).
     * Strategy.IDENTITY — БД увеличивает счётчик (PostgreSQL, MySQL).
     */
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    /*
     * @Column — настройки столбца в таблице:
     *   name — имя столбца (snake_case в БД vs camelCase в Java)
     *   nullable — может ли быть NULL?
     *   length — максимальная длина строки
     *
     * @NotBlank/@Size — ВАЛИДАЦИЯ: поле не может быть пустым, длина 2-50
     */
    @Column(name = "first_name", nullable = false, length = 50)
    @NotBlank(message = "Имя не может быть пустым")
    @Size(min = 2, max = 50, message = "Имя должно быть от 2 до 50 символов")
    private String firstName;

    @Column(name = "last_name", nullable = false, length = 50)
    @NotBlank(message = "Фамилия не может быть пустой")
    @Size(min = 2, max = 50, message = "Фамилия должна быть от 2 до 50 символов")
    private String lastName;

    /*
     * @Email — ВАЛИДАЦИЯ: проверяет корректность email.
     * unique = true — в таблице не может быть двух одинаковых email.
     */
    @Column(name = "email", nullable = false, unique = true, length = 100)
    @NotBlank(message = "Email не может быть пустым")
    @Email(message = "Некорректный формат email")
    private String email;

    @Column(name = "department", length = 100)
    private String department;

    /*
     * @Min/@Max — ВАЛИДАЦИЯ для чисел:
     *   зарплата не может быть отрицательной и не может превышать 10 млн
     */
    @Column(name = "salary")
    @Min(value = 0, message = "Зарплата не может быть отрицательной")
    @Max(value = 10_000_000, message = "Зарплата не может превышать 10 000 000")
    private Double salary;

    /*
     * LocalDateTime — дата и время (Java 8+).
     * @Column(updatable = false) — дата создания НЕ меняется после создания.
     *
     * @PrePersist — вызывается ПЕРЕД INSERT (вставкой в БД)
     * @PreUpdate — вызывается ПЕРЕД UPDATE (обновлением в БД)
     * Это как "триггеры" — автоматические действия перед операцией.
     */
    @Column(name = "created_at", updatable = false)
    private LocalDateTime createdAt;

    @Column(name = "updated_at")
    private LocalDateTime updatedAt;

    @PrePersist
    protected void onCreate() {
        this.createdAt = LocalDateTime.now();
        this.updatedAt = LocalDateTime.now();
    }

    @PreUpdate
    protected void onUpdate() {
        this.updatedAt = LocalDateTime.now();
    }
}

🔄 Шаг 5: DTO и Response

Никогда не отдавайте Entity напрямую клиенту! DTO контролирует входящие данные, Response — исходящие. Это защищает от перезаписи служебных полей и позволяет добавить вычисляемые поля (например, fullName).

EmployeeDTO.java
/*
 * EmployeeDTO.java — Data Transfer Object (Объект Передачи Данных)
 * DTO — это "фильтр" между клиентом и базой данных.
 * Клиент отправляет только нужные поля (имя, фамилия, email...).
 * Здесь НЕТ поля id, createdAt, updatedAt — их устанавливает сервер/БД.
 */
package com.example.employeecrud.dto;

import jakarta.validation.constraints.*;
import lombok.*;

@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class EmployeeDTO {
    
    /*
     * Валидация происходит ДО преобразования в Entity.
     * Это называется "валидация на входе" — ловим ошибки как можно раньше.
     */
    @NotBlank(message = "Имя не может быть пустым")
    @Size(min = 2, max = 50, message = "Имя должно быть от 2 до 50 символов")
    private String firstName;

    @NotBlank(message = "Фамилия не может быть пустой")
    @Size(min = 2, max = 50, message = "Фамилия должна быть от 2 до 50 символов")
    private String lastName;

    @NotBlank(message = "Email не может быть пустым")
    @Email(message = "Некорректный формат email")
    private String email;

    private String department;

    @Min(value = 0, message = "Зарплата не может быть отрицательной")
    @Max(value = 10_000_000, message = "Зарплата не может превышать 10 000 000")
    private Double salary;
}
EmployeeResponse.java
/*
 * EmployeeResponse.java — ОТВЕТ КЛИЕНТУ (Response DTO)
 * Это объект, который клиент получает в JSON-ответе.
 * Отличия от EmployeeDTO:
 *   - Включает id, createdAt, updatedAt (генерируются сервером)
 *   - Может содержать вычисляемые поля (например, fullName)
 * Принцип: DTO = "что клиент ОТПРАВЛЯЕТ", Response = "что мы ОТПРАВЛЯЕМ клиенту"
 */
package com.example.employeecrud.dto;

import lombok.*;
import java.time.LocalDateTime;

@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class EmployeeResponse {
    
    private Long id;
    private String firstName;
    private String lastName;

    /*
     * fullName — вычисляемое поле (не хранится в БД!).
     * Удобно для клиента — не нужно склеивать имя и фамилию.
     * Мы НЕ используем @Builder для этого поля — оно вычисляется через getter.
     */
    public String getFullName() {
        return firstName + " " + lastName;
    }

    private String email;
    private String department;
    private Double salary;

    /*
     * Даты создания и обновления.
     * Клиент видит, когда запись была создана и когда изменялась.
     * Формат в JSON: "2024-01-15T10:30:00"
     */
    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;
}

📊 Шаг 6: Репозиторий

JpaRepository автоматически генерирует SQL по имени метода. Это называется Query Derivation.

EmployeeRepository.java
/*
 * EmployeeRepository.java — РЕПОЗИТОРИЙ (слой доступа к данным)
 * Репозиторий — "посредник" между Java-кодом и базой данных.
 * Spring Data JPA ГЕНЕРИРУЕТ SQL автоматически — не нужно писать запросы вручную!
 *
 * JpaRepository<Employee, Long> — два параметра:
 *   Employee — с какой сущностью работаем
 *   Long     — тип первичного ключа (id)
 *
 * Что мы получаем БЕСПЛАТНО от JpaRepository:
 *   save()      → INSERT/UPDATE
 *   findById()  → SELECT WHERE id = ?
 *   findAll()   → SELECT * FROM employees
 *   delete()    → DELETE
 */
package com.example.employeecrud.repository;

import com.example.employeecrud.model.Employee;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.stereotype.Repository;
import java.util.List;
import java.util.Optional;

/*
 * @Repository — говорит Spring: "Это компонент для работы с данными!"
 * Spring автоматически создаст реализацию этого интерфейса.
 * Технически для JpaRepository @Repository не обязателен,
 * но мы пишем его явно для наглядности.
 */
@Repository
public interface EmployeeRepository extends JpaRepository<Employee, Long> {
    
    /*
     * =====================================================
     *  КАСТОМНЫЕ МЕТОДЫ — "Query Methods" (методы-запросы)
     * =====================================================
     *
     * Spring Data JPA умеет ГЕНЕРИРОВАТЬ SQL из ИМЕНИ метода!
     * Это называется "Query Derivation" (вывод запроса).
     *
     * Правила именования:
     *   findBy{Поле}           → WHERE поле = ?
     *   findBy{Поле}Containing → WHERE поле LIKE '%?%'
     *   existsBy{Поле}         → SELECT EXISTS(WHERE поле = ?)
     */

    /*
     * findByEmail("ivan@mail.ru")
     * → SELECT * FROM employees WHERE email = 'ivan@mail.ru'
     *
     * Optional<Employee> — контейнер, который может содержать
     * Employee или быть пустым. Это лучше, чем возвращать null!
     */
    Optional<Employee> findByEmail(String email);

    /*
     * findByDepartment("IT")
     * → SELECT * FROM employees WHERE department = 'IT'
     *
     * Возвращает список, потому что в одном отделе
     * может быть много сотрудников.
     */
    List<Employee> findByDepartment(String department);

    /*
     * findByFirstNameContainingIgnoreCase("ива")
     * → SELECT * FROM employees WHERE LOWER(first_name) LIKE LOWER('%ива%')
     *
     * Containing — поиск подстроки (LIKE '%...%')
     * IgnoreCase — без учёта регистра (Иван = иван = ИВАН)
     */
    List<Employee> findByFirstNameContainingIgnoreCase(String firstName);

    /*
     * existsByEmail("ivan@mail.ru")
     * → SELECT EXISTS(SELECT 1 FROM employees WHERE email = 'ivan@mail.ru')
     *
     * Возвращает true/false — есть ли сотрудник с таким email?
     * Используем для проверки уникальности перед созданием.
     */
    boolean existsByEmail(String email);
}

🔗 Шаг 7: Маппер

⚠️ Зачем отдельный Mapper?
Разделяет ответственность (SRP). При изменении полей правим только маппер, а не весь сервис. Легко тестируется отдельно.
EmployeeMapper.java
/*
 * EmployeeMapper.java — МАППЕР (преобразователь объектов)
 * Маппер конвертирует объекты одного типа в другой:
 *   EmployeeDTO  ←→  Employee (Entity)
 *
 * Зачем отдельный класс?
 * ✅ ВСЯ логика преобразования в ОДНОМ месте
 * ✅ Добавил поле? Поменял только маппер!
 * ✅ Легко тестировать отдельно
 * ✅ Принцип SRP (каждый класс делает одно дело)
 */
package com.example.employeecrud.mapper;

import com.example.employeecrud.dto.EmployeeDTO;
import com.example.employeecrud.dto.EmployeeResponse;
import com.example.employeecrud.model.Employee;
import org.springframework.stereotype.Component;
import java.util.List;
import java.util.stream.Collectors;

/*
 * @Component — говорит Spring: "Создай экземпляр этого класса и управляй им!"
 * После этого маппер можно "внедрять" через конструктор в любой другой класс.
 */
@Component
public class EmployeeMapper {
    
    // ==================== DTO → Entity ====================

    /*
     * toEntity() — преобразует DTO (данные от клиента) в Entity (для БД).
     *
     * Что ВКЛЮЧАЕМ: firstName, lastName, email, department, salary
     * Что НЕ ВКЛЮЧАЕМ:
     *   - id → генерируется базой данных автоматически
     *   - createdAt/updatedAt → устанавливаются через @PrePersist/@PreUpdate
     *
     * Используем Builder (от Lombok) — читаемый способ создания объекта.
     */
    public Employee toEntity(EmployeeDTO dto) {
        if (dto == null) {
            return null;  // Защита от NullPointerException
        }
        return Employee.builder()
                .firstName(dto.getFirstName())
                .lastName(dto.getLastName())
                .email(dto.getEmail())
                .department(dto.getDepartment())
                .salary(dto.getSalary())
                .build();
    }

    // ==================== Entity → DTO ====================

    /*
     * toDTO() — преобразует Entity (из БД) обратно в DTO.
     * Может использоваться для экспорта данных, передачи между микросервисами.
     */
    public EmployeeDTO toDTO(Employee entity) {
        if (entity == null) {
            return null;
        }
        return EmployeeDTO.builder()
                .firstName(entity.getFirstName())
                .lastName(entity.getLastName())
                .email(entity.getEmail())
                .department(entity.getDepartment())
                .salary(entity.getSalary())
                .build();
    }

    // ==================== Entity → Response ====================

    /*
     * toResponse() — преобразует Entity в EmployeeResponse.
     *
     * EmployeeResponse — это то, что КЛИЕНТ получает в ответ.
     * Он содержит id и даты, но НЕ содержит чувствительные данные.
     *
     * Разница DTO vs Response:
     *   DTO      — ВХОДЯЩИЕ данные (от клиента → серверу)
     *   Response — ИСХОДЯЩИЕ данные (от сервера → клиенту)
     */
    public EmployeeResponse toResponse(Employee entity) {
        if (entity == null) {
            return null;
        }
        return EmployeeResponse.builder()
                .id(entity.getId())
                .firstName(entity.getFirstName())
                .lastName(entity.getLastName())
                .email(entity.getEmail())
                .department(entity.getDepartment())
                .salary(entity.getSalary())
                .createdAt(entity.getCreatedAt())
                .updatedAt(entity.getUpdatedAt())
                .build();
    }

    // ==================== Списки (List) ====================

    /*
     * toResponseList() — преобразует СПИСОК Entity в список Response.
     *
     * Используем Stream API (Java 8+):
     *   .stream() — создаём поток из списка
     *   .map(this::toResponse) — применяем toResponse() к КАЖДОМУ элементу
     *   .collect(...) — собираем результат обратно в список
     *
     * this::toResponse — "ссылка на метод" (method reference).
     * Эквивалентно: .map(employee -> toResponse(employee)), но короче.
     */
    public List<EmployeeResponse> toResponseList(List<Employee> entities) {
        if (entities == null) {
            return List.of();  // Возвращаем пустой список, а не null!
        }
        return entities.stream()
                .map(this::toResponse)
                .collect(Collectors.toList());
    }

    // ==================== Обновление Entity из DTO ====================

    /*
     * updateEntityFromDTO() — обновляет СУЩЕСТВУЮЩИЙ Entity данными из DTO.
     *
     * Зачем отдельный метод? При UPDATE мы НЕ создаём новый объект!
     * Мы обновляем поля СУЩЕСТВУЮЩЕГО объекта, чтобы сохранить:
     *   - id (не менять!)
     *   - createdAt (не менять!)
     *   - updatedAt (обновится через @PreUpdate автоматически)
     *
     * Это важное отличие от toEntity():
     *   toEntity() — создаёт НОВЫЙ объект (для CREATE)
     *   updateEntityFromDTO() — модифицирует СУЩЕСТВУЮЩИЙ (для UPDATE)
     */
    public void updateEntityFromDTO(Employee entity, EmployeeDTO dto) {
        if (entity == null || dto == null) {
            return;
        }
        entity.setFirstName(dto.getFirstName());
        entity.setLastName(dto.getLastName());
        entity.setEmail(dto.getEmail());
        entity.setDepartment(dto.getDepartment());
        entity.setSalary(dto.getSalary());
    }
}

⚙️ Шаг 8: Сервисный слой

Содержит всю бизнес-логику. Использует @Transactional для атомарности операций. Внедряет Repository и Mapper через конструктор.

EmployeeService.java
/*
 * EmployeeService.java — СЕРВИСНЫЙ СЛОЙ (бизнес-логика)
 *
 * Архитектура Spring-приложения — три слоя:
 *   1. CONTROLLER — принимает HTTP, отдаёт ответы (НЕ содержит бизнес-логику!)
 *   2. SERVICE ← МЫ ЗДЕСЬ — вся бизнес-логика, валидация, правила
 *   3. REPOSITORY — работа с БД, CRUD операции
 *
 * Зачем разделять на слои?
 * ✅ Каждый слой имеет ОДНУ ответственность (SRP)
 * ✅ Можно менять БД без изменения контроллера
 * ✅ Легче тестировать — каждый слой тестируется отдельно
 */
package com.example.employeecrud.service;

import com.example.employeecrud.dto.EmployeeDTO;
import com.example.employeecrud.dto.EmployeeResponse;
import com.example.employeecrud.exception.ResourceNotFoundException;
import com.example.employeecrud.mapper.EmployeeMapper;
import com.example.employeecrud.model.Employee;
import com.example.employeecrud.repository.EmployeeRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.util.List;

/*
 * @Service — говорит Spring: "Это бизнес-компонент! Создай его экземпляр."
 * Spring создаст ОДИН экземпляр (Singleton) на всё приложение.
 *
 * @RequiredArgsConstructor (Lombok) — генерирует конструктор для ВСЕХ final-полей.
 * Это лучший способ внедрения зависимостей (Dependency Injection)!
 *
 * Dependency Injection (DI) — ключевой принцип Spring:
 * Вместо new EmployeeRepository(), мы ОБЪЯВЛЯЕМ зависимости,
 * а Spring сам "внедряет" (передаёт) нужные объекты.
 */
@Service
@RequiredArgsConstructor
public class EmployeeService {
    
    /*
     * final — поле нельзя переназначить после инициализации.
     * Это ГАРАНТИРУЕТ, что зависимости всегда будут установлены.
     */
    private final EmployeeRepository employeeRepository;
    
    /*
     * EmployeeMapper — наш маппер для преобразования объектов.
     * Вынесен в отдельный @Component, внедряется через DI.
     * Преимущества: каждый класс делает ОДНО дело (SRP),
     * маппер можно переиспользовать и тестировать отдельно.
     */
    private final EmployeeMapper employeeMapper;

    // ==================== CREATE (Создание) ====================

    /*
     * Создание нового сотрудника.
     *
     * @Transactional — ОЧЕНЬ ВАЖНАЯ аннотация!
     * Оборачивает метод в транзакцию базы данных.
     * Транзакция — это "всё или ничего":
     *   - Если всё ОК → данные сохраняются (COMMIT)
     *   - Если ошибка → все изменения откатываются (ROLLBACK)
     *
     * Возвращаем EmployeeResponse вместо Employee (Entity).
     * Это правильный подход: клиент НИКОГДА не видит Entity напрямую!
     *
     * Поток данных:
     *   EmployeeDTO (вход) → Employee (БД) → EmployeeResponse (выход)
     */
    @Transactional
    public EmployeeResponse createEmployee(EmployeeDTO dto) {
        // Проверяем: нет ли уже сотрудника с таким email?
        if (employeeRepository.existsByEmail(dto.getEmail())) {
            throw new IllegalArgumentException(
                "Сотрудник с email " + dto.getEmail() + " уже существует!"
            );
        }
        // Шаг 1: DTO → Entity (через маппер)
        Employee employee = employeeMapper.toEntity(dto);
        // Шаг 2: Сохраняем в БД (получаем Entity с заполненным id)
        Employee saved = employeeRepository.save(employee);
        // Шаг 3: Entity → Response (через маппер)
        return employeeMapper.toResponse(saved);
    }

    // ==================== READ (Чтение) ====================

    /*
     * Получить ВСЕХ сотрудников.
     *
     * @Transactional(readOnly = true) — оптимизация:
     *   Говорим Hibernate: "Мы только читаем, не изменяем".
     *   Hibernate отключает "dirty checking" (отслеживание изменений),
     *   что ускоряет работу.
     *
     * Используем employeeMapper.toResponseList() — преобразуем
     * ВЕСЬ список Entity в список Response за один вызов.
     */
    @Transactional(readOnly = true)
    public List<EmployeeResponse> getAllEmployees() {
        List<Employee> employees = employeeRepository.findAll();
        return employeeMapper.toResponseList(employees);
    }

    /*
     * Получить сотрудника по ID.
     *
     * findById() возвращает Optional<Employee>.
     * .orElseThrow() — если сотрудник не найден, бросаем исключение.
     *
     * Лямбда () -> new ResourceNotFoundException(...)
     * — создаёт исключение ТОЛЬКО если сотрудник не найден.
     * Если найден — исключение не создаётся (экономия ресурсов).
     */
    @Transactional(readOnly = true)
    public EmployeeResponse getEmployeeById(Long id) {
        Employee employee = findEmployeeOrThrow(id);
        return employeeMapper.toResponse(employee);
    }

    /*
     * Поиск сотрудников по отделу.
     */
    @Transactional(readOnly = true)
    public List<EmployeeResponse> getEmployeesByDepartment(String department) {
        List<Employee> employees = employeeRepository.findByDepartment(department);
        return employeeMapper.toResponseList(employees);
    }

    /*
     * Поиск сотрудников по имени (частичное совпадение).
     */
    @Transactional(readOnly = true)
    public List<EmployeeResponse> searchByName(String name) {
        List<Employee> employees = employeeRepository
                .findByFirstNameContainingIgnoreCase(name);
        return employeeMapper.toResponseList(employees);
    }

    // ==================== UPDATE (Обновление) ====================

    /*
     * Обновление данных сотрудника.
     *
     * Используем employeeMapper.updateEntityFromDTO() — маппер
     * обновляет СУЩЕСТВУЮЩИЙ объект, а не создаёт новый.
     * Это сохраняет id, createdAt и другие поля Entity.
     */
    @Transactional
    public EmployeeResponse updateEmployee(Long id, EmployeeDTO dto) {
        // Шаг 1: Ищем сотрудника (бросит 404, если не найден)
        Employee existing = findEmployeeOrThrow(id);
        
        // Шаг 2: Проверяем email (если изменился)
        if (!existing.getEmail().equals(dto.getEmail())
                && employeeRepository.existsByEmail(dto.getEmail())) {
            throw new IllegalArgumentException(
                "Email " + dto.getEmail() + " уже используется другим сотрудником!"
            );
        }
        
        // Шаг 3: Обновляем поля через маппер
        // Маппер обновляет СУЩЕСТВУЮЩИЙ объект, не создавая новый!
        employeeMapper.updateEntityFromDTO(existing, dto);
        
        // Шаг 4: Сохраняем (UPDATE, потому что id уже существует)
        // @PreUpdate в Employee автоматически обновит updatedAt
        Employee updated = employeeRepository.save(existing);
        
        // Шаг 5: Entity → Response
        return employeeMapper.toResponse(updated);
    }

    // ==================== DELETE (Удаление) ====================

    /*
     * Удаление сотрудника по ID.
     *
     * Сначала проверяем, существует ли сотрудник.
     * Если нет — бросаем 404, а не молча игнорируем.
     * Это важно: клиент должен знать, если он пытается
     * удалить несуществующую запись.
     */
    @Transactional
    public void deleteEmployee(Long id) {
        Employee employee = findEmployeeOrThrow(id);
        employeeRepository.delete(employee);
    }

    // ==================== ВСПОМОГАТЕЛЬНЫЕ МЕТОДЫ ====================

    /*
     * findEmployeeOrThrow() — находит сотрудника или бросает 404.
     *
     * Вынесен в отдельный метод, потому что используется в:
     *   - getEmployeeById()
     *   - updateEmployee()
     *   - deleteEmployee()
     *
     * Принцип DRY — не повторяй одну и ту же логику!
     *
     * Этот метод возвращает ENTITY (не Response), потому что
     * он используется внутри сервиса для работы с данными.
     * Преобразование в Response происходит уже в публичных методах.
     */
    private Employee findEmployeeOrThrow(Long id) {
        return employeeRepository.findById(id)
                .orElseThrow(() -> new ResourceNotFoundException(
                    "Сотрудник с id " + id + " не найден"
                ));
    }
}

🌐 Шаг 9: REST Контроллер

Принимает HTTP-запросы, вызывает сервис, возвращает ResponseEntity с правильными статус-кодами. @Valid включает валидацию входящих DTO.

EmployeeController.java
/*
 * EmployeeController.java — REST КОНТРОЛЛЕР (обработка HTTP-запросов)
 *
 * Контроллер — это "дверь" в приложение. Он:
 *   1. Принимает HTTP-запросы от клиента (браузер, Postman, фронтенд)
 *   2. Вызывает сервис для выполнения бизнес-логики
 *   3. Возвращает HTTP-ответ (JSON)
 *
 * REST API — архитектурный стиль для веб-сервисов:
 *   POST   /api/employees       → Создать сотрудника
 *   GET    /api/employees       → Получить всех сотрудников
 *   GET    /api/employees/5     → Получить сотрудника с id=5
 *   PUT    /api/employees/5     → Обновить сотрудника с id=5
 *   DELETE /api/employees/5     → Удалить сотрудника с id=5
 *
 * ВАЖНО: Контроллер возвращает EmployeeResponse вместо Employee!
 * Клиент НИКОГДА не видит Entity (Employee) напрямую.
 */
package com.example.employeecrud.controller;

import com.example.employeecrud.dto.EmployeeDTO;
import com.example.employeecrud.dto.EmployeeResponse;
import com.example.employeecrud.service.EmployeeService;
import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import java.util.List;

/*
 * @RestController — комбинация:
 *   @Controller — это контроллер Spring MVC
 *   @ResponseBody — все методы возвращают JSON (а не HTML-страницу)
 *
 * @RequestMapping("/api/employees") — базовый URL для всех методов.
 * Все URL в этом контроллере начинаются с "/api/employees".
 * Полный URL: http://localhost:8080/api/employees
 */
@RestController
@RequestMapping("/api/employees")

/*
 * @RequiredArgsConstructor — Lombok генерирует конструктор:
 *   public EmployeeController(EmployeeService employeeService) {
 *     this.employeeService = employeeService;
 *   }
 * Spring автоматически "внедрит" (inject) EmployeeService.
 */
@RequiredArgsConstructor
public class EmployeeController {
    
    private final EmployeeService employeeService;

    // ==================== POST — СОЗДАНИЕ ====================

    /*
     * POST /api/employees
     *
     * Создание нового сотрудника.
     *
     * @PostMapping — обрабатывает HTTP POST запросы.
     *
     * @Valid — ВКЛЮЧАЕТ валидацию!
     *   Без @Valid аннотации @NotBlank, @Email и т.д. в DTO
     *   будут просто ИГНОРИРОВАТЬСЯ. Это частая ошибка новичков!
     *
     * @RequestBody — говорит Spring:
     *   "Возьми тело HTTP-запроса (JSON) и преобразуй в объект EmployeeDTO"
     *
     *   JSON запроса:
     *   { "firstName": "Иван", "lastName": "Петров", "email": "ivan@mail.ru", ... }
     *                    ↓ Jackson автоматически
     *   EmployeeDTO(firstName="Иван", lastName="Петров", ...)
     *
     * ResponseEntity<EmployeeResponse> — полный HTTP-ответ:
     *   - Тело: EmployeeResponse (JSON) — данные с id и датами
     *   - Статус: 201 Created (ресурс успешно создан)
     */
    @PostMapping
    public ResponseEntity<EmployeeResponse> createEmployee(
            @Valid @RequestBody EmployeeDTO employeeDTO) {
        
        EmployeeResponse created = employeeService.createEmployee(employeeDTO);
        return new ResponseEntity<>(created, HttpStatus.CREATED); // 201
    }

    // ==================== GET — ЧТЕНИЕ ====================

    /*
     * GET /api/employees
     *
     * Получить список ВСЕХ сотрудников.
     * Возвращает List<EmployeeResponse> — каждый элемент содержит
     * id, fullName, даты и все остальные поля.
     *
     * HttpStatus.OK = 200 — стандартный успешный ответ.
     */
    @GetMapping
    public ResponseEntity<List<EmployeeResponse>> getAllEmployees() {
        List<EmployeeResponse> employees = employeeService.getAllEmployees();
        return new ResponseEntity<>(employees, HttpStatus.OK); // 200
    }

    /*
     * GET /api/employees/5
     *
     * Получить ОДНОГО сотрудника по его ID.
     *
     * @GetMapping("/{id}") — {id} это "переменная пути" (path variable).
     *   URL /api/employees/5  → id = 5
     *   URL /api/employees/42 → id = 42
     *
     * @PathVariable — извлекает значение из URL.
     *   Spring автоматически конвертирует строку "5" в Long 5.
     *
     * Если сотрудник не найден, сервис бросит ResourceNotFoundException,
     * которую перехватит GlobalExceptionHandler и вернёт 404.
     */
    @GetMapping("/{id}")
    public ResponseEntity<EmployeeResponse> getEmployeeById(@PathVariable Long id) {
        EmployeeResponse employee = employeeService.getEmployeeById(id);
        return new ResponseEntity<>(employee, HttpStatus.OK);
    }

    /*
     * GET /api/employees/department/IT
     *
     * Поиск сотрудников по отделу.
     * Пример: GET /api/employees/department/HR → Все сотрудники из отдела HR
     */
    @GetMapping("/department/{department}")
    public ResponseEntity<List<EmployeeResponse>> getByDepartment(
            @PathVariable String department) {
        
        List<EmployeeResponse> employees = employeeService
                .getEmployeesByDepartment(department);
        return new ResponseEntity<>(employees, HttpStatus.OK);
    }

    /*
     * GET /api/employees/search?name=иван
     *
     * Поиск сотрудников по имени.
     *
     * @RequestParam — извлекает ПАРАМЕТР ЗАПРОСА из URL.
     *   URL: /api/employees/search?name=иван → name = "иван"
     *
     * Разница @PathVariable vs @RequestParam:
     *   @PathVariable — часть URL:     /employees/5       (id = 5)
     *   @RequestParam — после знака ?: /search?name=иван  (name = "иван")
     *
     * Когда что использовать:
     *   @PathVariable — для идентификации ресурса (id, slug)
     *   @RequestParam — для фильтрации, поиска, пагинации
     */
    @GetMapping("/search")
    public ResponseEntity<List<EmployeeResponse>> searchByName(
            @RequestParam String name) {
        
        List<EmployeeResponse> employees = employeeService.searchByName(name);
        return new ResponseEntity<>(employees, HttpStatus.OK);
    }

    // ==================== PUT — ОБНОВЛЕНИЕ ====================

    /*
     * PUT /api/employees/5
     *
     * Обновить данные сотрудника.
     *
     * @PutMapping("/{id}") — обрабатывает HTTP PUT запросы.
     *
     * PUT vs PATCH:
     *   PUT   — полная замена (нужно отправить ВСЕ поля)
     *   PATCH — частичное обновление (только изменённые поля)
     *   Мы используем PUT для простоты.
     */
    @PutMapping("/{id}")
    public ResponseEntity<EmployeeResponse> updateEmployee(
            @PathVariable Long id,
            @Valid @RequestBody EmployeeDTO employeeDTO) {
        
        EmployeeResponse updated = employeeService.updateEmployee(id, employeeDTO);
        return new ResponseEntity<>(updated, HttpStatus.OK);
    }

    // ==================== DELETE — УДАЛЕНИЕ ====================

    /*
     * DELETE /api/employees/5
     *
     * Удалить сотрудника.
     *
     * @DeleteMapping("/{id}") — обрабатывает HTTP DELETE запросы.
     *
     * HttpStatus.NO_CONTENT (204) — "Успешно, но нечего возвращать".
     *   Это правильный статус для DELETE — ресурс удалён,
     *   возвращать его данные нет смысла.
     *
     * Void — метод ничего не возвращает в теле ответа.
     */
    @DeleteMapping("/{id}")
    public ResponseEntity<Void> deleteEmployee(@PathVariable Long id) {
        employeeService.deleteEmployee(id);
        return new ResponseEntity<>(HttpStatus.NO_CONTENT); // 204
    }
}

🚨 Шаг 10: Глобальная обработка ошибок

@RestControllerAdvice перехватывает исключения из всех контроллеров и возвращает унифицированный JSON-ответ.

ResourceNotFoundException.java
/*
 * ResourceNotFoundException.java — КАСТОМНОЕ ИСКЛЮЧЕНИЕ
 *
 * Зачем создавать своё исключение?
 * Когда клиент запрашивает сотрудника с id=999, а его нет в базе,
 * мы должны вернуть понятную ошибку: "Сотрудник с id 999 не найден"
 * и HTTP-статус 404 (Not Found).
 *
 * Стандартные исключения Java (NullPointerException и т.д.)
 * не подходят — они возвращают статус 500 (Internal Server Error),
 * что вводит клиента в заблуждение.
 *
 * @ResponseStatus(HttpStatus.NOT_FOUND) — когда это исключение
 * выбрасывается, Spring автоматически вернёт HTTP 404.
 *
 * Иерархия наследования:
 *   Throwable → Exception → RuntimeException → ResourceNotFoundException
 *
 * Почему RuntimeException, а не Exception?
 *   RuntimeException — "непроверяемое" исключение (unchecked)
 *   Не требует try-catch или throws в сигнатуре метода
 *   Код чище и проще
 *   Spring лучше работает с RuntimeException
 */
package com.example.employeecrud.exception;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.ResponseStatus;

@ResponseStatus(value = HttpStatus.NOT_FOUND)
public class ResourceNotFoundException extends RuntimeException {
    
    /*
     * Конструктор принимает сообщение об ошибке.
     * super(message) — передаём сообщение родительскому классу.
     *
     * Пример использования:
     *   throw new ResourceNotFoundException("Сотрудник с id 5 не найден");
     *
     * Клиент получит:
     *   HTTP 404
     *   { "message": "Сотрудник с id 5 не найден" }
     */
    public ResourceNotFoundException(String message) {
        super(message);
    }
}
GlobalExceptionHandler.java
/*
 * GlobalExceptionHandler.java — ГЛОБАЛЬНЫЙ ОБРАБОТЧИК ОШИБОК
 *
 * Представь: в разных контроллерах могут возникать одинаковые ошибки.
 * Вместо того чтобы обрабатывать их в каждом контроллере отдельно,
 * мы создаём ОДИН централизованный обработчик.
 *
 * @RestControllerAdvice — комбинация:
 *   @ControllerAdvice — "советчик" для всех контроллеров
 *   @ResponseBody     — ответ автоматически в JSON
 *
 * Аналогия: это как "служба безопасности" в здании —
 * перехватывает все инциденты из всех кабинетов.
 */
package com.example.employeecrud.exception;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.*;
import java.time.LocalDateTime;
import java.util.HashMap;
import java.util.Map;

@RestControllerAdvice
public class GlobalExceptionHandler {
    
    /*
     * Обработчик для ResourceNotFoundException (сотрудник не найден).
     *
     * @ExceptionHandler — говорит Spring:
     *    "Когда где-либо возникает ResourceNotFoundException,
     *    вызови ЭТОТ метод для обработки!"
     *
     * ResponseEntity<?> — полный HTTP-ответ:
     *   - Тело (body) — JSON с деталями ошибки
     *   - Статус — HTTP 404 (NOT_FOUND)
     *   - Заголовки (headers) — опционально
     *
     * Пример ответа клиенту:
     * {
     *    "timestamp": "2024-01-15T10:30:00",
     *    "status": 404,
     *    "error": "Not Found",
     *    "message": "Сотрудник с id 5 не найден"
     * }
     */
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<Map<String, Object>> handleResourceNotFound(
            ResourceNotFoundException ex) {
        
        Map<String, Object> body = new HashMap<>();
        body.put("timestamp", LocalDateTime.now().toString());
        body.put("status", HttpStatus.NOT_FOUND.value());       // 404
        body.put("error", "Not Found");
        body.put("message", ex.getMessage());
        
        return new ResponseEntity<>(body, HttpStatus.NOT_FOUND);
    }

    /*
     * Обработчик ошибок ВАЛИДАЦИИ.
     *
     * Когда клиент отправляет невалидные данные (пустое имя, кривой email),
     * Spring выбрасывает MethodArgumentNotValidException.
     *
     * Мы перехватываем его и возвращаем ПОНЯТНЫЙ список ошибок:
     *
     * Пример: клиент отправил { "firstName": "", "email": "не-email" }
     *
     * Ответ (HTTP 400 — Bad Request):
     * {
     *    "timestamp": "2024-01-15T10:30:00",
     *    "status": 400,
     *    "error": "Validation Failed",
     *    "errors": {
     *      "firstName": "Имя не может быть пустым",
     *      "email": "Некорректный формат email"
     *    }
     * }
     */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Map<String, Object>> handleValidationErrors(
            MethodArgumentNotValidException ex) {
        
        /*
         * Собираем ВСЕ ошибки валидации в удобный формат.
         * getBindingResult().getAllErrors() — список всех ошибок.
         * Каждая FieldError содержит:
         *   getField()          — имя поля ("firstName", "email")
         *   getDefaultMessage() — сообщение ("Имя не может быть пустым")
         */
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getAllErrors().forEach(error -> {
            String fieldName = ((FieldError) error).getField();
            String errorMessage = error.getDefaultMessage();
            errors.put(fieldName, errorMessage);
        });
        
        Map<String, Object> body = new HashMap<>();
        body.put("timestamp", LocalDateTime.now().toString());
        body.put("status", HttpStatus.BAD_REQUEST.value());      // 400
        body.put("error", "Validation Failed");
        body.put("errors", errors);
        
        return new ResponseEntity<>(body, HttpStatus.BAD_REQUEST);
    }

    /*
     * "Ловушка" для ВСЕХ остальных непредвиденных ошибок.
     *
     * Если произойдёт что-то неожиданное (например, база данных упала),
     * клиент получит аккуратное сообщение, а не stack trace.
     *
     * ВАЖНО: в продакшене НИКОГДА не отдавайте ex.getMessage() клиенту!
     * Это может раскрыть внутреннюю архитектуру (пути файлов, SQL и т.д.).
     * В реальном проекте логируйте ошибку и возвращайте общее сообщение.
     */
    @ExceptionHandler(Exception.class)
    public ResponseEntity<Map<String, Object>> handleGeneralException(
            Exception ex) {
        
        Map<String, Object> body = new HashMap<>();
        body.put("timestamp", LocalDateTime.now().toString());
        body.put("status", HttpStatus.INTERNAL_SERVER_ERROR.value()); // 500
        body.put("error", "Internal Server Error");
        body.put("message", "Произошла внутренняя ошибка сервера");
        
        return new ResponseEntity<>(body, HttpStatus.INTERNAL_SERVER_ERROR);
    }
}

✅ Best & ⚠️ Anti Practices

✅ Best Practices
  • Разделяй DTO (вход) и Response (выход)
  • Используй @Transactional(readOnly = true) для SELECT
  • Внедряй зависимости через конструктор (@RequiredArgsConstructor)
  • Выноси маппинг в отдельный @Component
  • Проверяй уникальность до сохранения
  • Используй Optional.orElseThrow() вместо null
  • Покрывай сервис и маппер юнит-тестами с Mockito
⚠️ Antipatterns
  • ❌ Возвращать Entity напрямую в контроллере
  • ❌ Писать SQL в контроллере или сервисе
  • ❌ Использовать new Service() вместо DI
  • ❌ Игнорировать @Valid на входящих DTO
  • ❌ Ловить Exception в каждом методе (используй @RestControllerAdvice)
  • ❌ Хардкодить сообщения об ошибках в контроллере
  • ❌ Загружать data.sql без defer-datasource-initialization

❓ Вопросы для собеседования

Зачем разделять Entity, DTO и Response?
Why separate Entity, DTO, and Response?
Easy ▼
✅ Ответ
Entity привязан к БД и может содержать служебные поля, пароли или внутренние ID. Отдавать его клиенту опасно (overposting/underposting). DTO контролирует вход (валидация, нужные поля). Response контролирует выход (скрытие данных, добавление вычисляемых полей вроде fullName).
Чем @RestController отличается от @Controller?
Difference between @RestController and @Controller?
Easy ▼
✅ Ответ
@RestController = @Controller + @ResponseBody. Он автоматически сериализует возвращаемые объекты в JSON (через Jackson). Обычный @Controller ожидает возвращение имени View (HTML-страницы) и использует ModelAndView или Thymeleaf.
Как работает @Transactional? Зачем readOnly?
How does @Transactional work? Why readOnly?
Medium ▼
✅ Ответ
Аннотация оборачивает метод в транзакцию БД. При успехе — COMMIT, при исключении — ROLLBACK. readOnly = true оптимизирует чтение: Hibernate отключает dirty checking (отслеживание изменений сущностей), что снижает потребление памяти и ускоряет выполнение SELECT-запросов.
Что делает defer-datasource-initialization: true?
What does defer-datasource-initialization do?
Medium ▼
✅ Ответ
По умолчанию Spring Boot выполняет data.sql до инициализации Hibernate. Если таблицы ещё не созданы, приложение упадет с ошибкой. Эта настройка откладывает выполнение SQL-скриптов после создания схемы Hibernate, что критично для ddl-auto: update или create.
Зачем мокают Repository в тестах Service?
Why mock Repository in Service tests?
Hard ▼
✅ Ответ
Чтобы тестировать только бизнес-логику сервиса, изолированно от БД. Mockito позволяет вернуть предсказуемые данные (when().thenReturn()) и проверить вызовы (verify()). Это ускоряет тесты в 100x раз (миллисекунды вместо секунд) и делает их детерминированными.
