⚖️ @NotNull vs @NotEmpty vs @NotBlank
⚠️ Самый частый вопрос на собеседовании
Это различие спрашивают почти всегда. Запомни таблицу выше и примеры ниже.
Java — демонстрация разницы
// ── @NotNull — только проверяет что не null
@NotNull
String field;

// field = null       → ОШИБКА валидации ❌
// field = ""         → ОК ✅ (пустая строка не null)
// field = "   "      → ОК ✅ (строка из пробелов не null)
// field = "Иван"     → ОК ✅

// ── @NotEmpty — не null И не пустая коллекция/строка
@NotEmpty
String field;

// field = null       → ОШИБКА валидации ❌
// field = ""         → ОШИБКА валидации ❌ (пустая строка)
// field = "   "      → ОК ✅ (пробелы считаются непустой строкой!)
// field = "Иван"     → ОК ✅

@NotEmpty
List<String> items;
// items = null           → ОШИБКА ❌
// items = []             → ОШИБКА ❌ (пустой список)
// items = ["a"]          → ОК ✅

// ── @NotBlank — не null, не пустая, не только пробелы (только для String!)
@NotBlank
String field;

// field = null       → ОШИБКА валидации ❌
// field = ""         → ОШИБКА валидации ❌
// field = "   "      → ОШИБКА валидации ❌ (только пробелы!)
// field = " Иван "   → ОК ✅ (есть непробельный символ)
// field = "Иван"     → ОК ✅

// ── Практический вывод:
// Для строк используй @NotBlank — самая строгая проверка
// Для коллекций используй @NotEmpty
// @NotNull только когда null недопустим, но "" и "  " разрешены
🆚 @Valid vs @Validated
Критерий@Valid (javax/jakarta)@Validated (Spring)
ИсточникJakarta ValidationSpring Framework
Поддержка групп❌ Нет✅ Да — @Validated(CreateGroup.class)
На @RequestBody✅ Работает✅ Работает
На @RequestParam / @PathVariable❌ Не работает✅ Работает (на классе)
Каскадная валидация✅ @Valid на вложенных объектах✅ Через @Valid внутри
Исключение при ошибкеMethodArgumentNotValidExceptionConstraintViolationException
💡 Когда что использовать
@Valid — для валидации @RequestBody в контроллере. Стандарт Jakarta.
@Validated — когда нужны группы валидации ИЛИ валидация параметров метода (@RequestParam, @PathVariable). Ставится на класс контроллера/сервиса.
🔍 BindingResult

BindingResult — объект который содержит результат валидации. Если добавить его как параметр сразу после валидируемого объекта, Spring не будет кидать исключение при ошибках — вместо этого заполнит BindingResult, и ты сам решаешь что делать.

⚠️ Важно: порядок параметров
BindingResult должен идти сразу после объекта с @Valid. Иначе Spring кинет исключение до того как ты получишь BindingResult.
Без BindingResult
  • Spring автоматически кидает MethodArgumentNotValidException
  • GlobalExceptionHandler перехватывает
  • Более чистый код контроллера
  • ✅ Рекомендован для REST API
С BindingResult
  • Исключение не кидается
  • Сам проверяешь result.hasErrors()
  • Гибкость — можно добавить свою логику
  • ⚠️ Нужно не забывать проверять ошибки
🔧 Кастомный валидатор

Когда стандартных аннотаций недостаточно — создаём свою. Нужно: 1) аннотация с @Constraint, 2) класс реализующий ConstraintValidator<A, T>.

ШагЧто создатьОписание
1Аннотация с @Constraint(validatedBy = ...)Объявляем новую аннотацию
2Класс с implements ConstraintValidator<Ann, Type>Логика проверки в методе isValid()
3Применяем аннотацию к полю/классуКак обычная аннотация
👥 Группы валидации

Разные правила для разных операций. Например: при создании пользователя пароль обязателен, при обновлении — нет.

СценарийГруппаПоля
POST /users (создание)OnCreatename, email, password — все обязательны
PUT /users/{id} (обновление)OnUpdatename, email — обязательны; password — нет
💻 Примеры кода
1. DTO с полным набором аннотаций
Java
import jakarta.validation.constraints.*;

public record CreateUserRequest(

    @NotBlank(message = "Имя не может быть пустым")   // не null, не "", не "  "
    @Size(min = 2, max = 50,
          message = "Имя должно быть от 2 до 50 символов")
    String name,

    @NotBlank(message = "Email обязателен")
    @Email(message = "Введите корректный email")        // user@example.com
    String email,

    @NotBlank(message = "Пароль обязателен")
    @Size(min = 8, max = 100,
          message = "Пароль должен быть от 8 до 100 символов")
    String password,

    @NotNull(message = "Возраст обязателен")            // null недопустим
    @Min(value = 18, message = "Минимальный возраст 18 лет")
    @Max(value = 120, message = "Максимальный возраст 120 лет")
    Integer age,

    @Pattern(                                             // регулярное выражение
        regexp = "^\\+?[0-9]{10,15}$",
        message = "Неверный формат телефона")
    String phone,                                        // опционально (null допустим)

    @NotNull(message = "Дата рождения обязательна")
    @Past(message = "Дата рождения должна быть в прошлом") // строго в прошлом
    LocalDate birthDate,

    @Future(message = "Дата доставки должна быть в будущем")
    LocalDate deliveryDate,                              // опционально

    @NotEmpty(message = "Укажите хотя бы одну роль")     // не null и не пустой список
    List<String> roles,

    @NotNull
    @Positive(message = "Цена должна быть положительной")  // строго > 0
    BigDecimal price,

    @PositiveOrZero(message = "Количество не может быть отрицательным") // >= 0
    int quantity,

    @AssertTrue(message = "Необходимо принять условия использования")
    boolean termsAccepted                                // должно быть true
) {}
2. @Valid в контроллере и @Validated для параметров
Java
// ── @Valid для @RequestBody
@RestController
@RequestMapping("/api/v1/users")
public class UserController {

    @PostMapping
    public ResponseEntity<UserResponse> create(
            @RequestBody @Valid CreateUserRequest request) { // @Valid запускает валидацию
        // если валидация провалилась — Spring кидает MethodArgumentNotValidException
        // GlobalExceptionHandler перехватит и вернёт 400 с описанием ошибок
        return ResponseEntity.status(201).body(userService.create(request));
    }
}

// ── @Validated на классе — для валидации @PathVariable и @RequestParam
@RestController
@RequestMapping("/api/v1/products")
@Validated                                            // ОБЯЗАТЕЛЬНО на классе для параметров
public class ProductController {

    // GET /api/v1/products/0 → ConstraintViolationException → 400
    @GetMapping("/{id}")
    public ResponseEntity<ProductResponse> getById(
            @PathVariable
            @Positive(message = "ID должен быть положительным") // валидация PathVariable
            Long id) {
        return ResponseEntity.ok(productService.findById(id));
    }

    // GET /api/v1/products?size=-1 → ConstraintViolationException → 400
    @GetMapping
    public ResponseEntity<List<ProductResponse>> getAll(
            @RequestParam(defaultValue = "0")
            @Min(value = 0, message = "Страница >= 0")          // валидация RequestParam
            int page,

            @RequestParam(defaultValue = "10")
            @Min(1) @Max(100)                                  // размер страницы 1-100
            int size) {
        return ResponseEntity.ok(productService.findAll(page, size));
    }
}
3. BindingResult — ручная обработка ошибок
Java
@PostMapping("/register")
public ResponseEntity<?> register(
        @RequestBody @Valid RegisterRequest request,
        BindingResult bindingResult) {    // СРАЗУ после @Valid объекта — порядок важен!

    // ── Если есть ошибки — обрабатываем сами (не кидается исключение)
    if (bindingResult.hasErrors()) {
        // Собираем все ошибки в Map
        Map<String, String> errors = bindingResult
            .getFieldErrors()                              // ошибки конкретных полей
            .stream()
            .collect(Collectors.toMap(
                FieldError::getField,                       // "email", "password"
                fe -> Objects.requireNonNullElse(
                    fe.getDefaultMessage(), "Ошибка"),      // сообщение аннотации
                (a, b) -> a                                    // при дубле ключа берём первый
            ));
        return ResponseEntity.badRequest().body(errors); // 400 с картой ошибок
    }

    // ── Можно проверить только конкретное поле
    if (bindingResult.hasFieldErrors("email")) {
        String emailError = bindingResult
            .getFieldError("email")
            .getDefaultMessage();
        return ResponseEntity.badRequest().body(emailError);
    }

    // ── Добавить ошибку вручную (cross-field validation)
    if (!request.password().equals(request.confirmPassword())) {
        bindingResult.rejectValue(
            "confirmPassword",                            // поле
            "password.mismatch",                          // код ошибки
            "Пароли не совпадают");                        // сообщение
        return ResponseEntity.badRequest()
            .body(Map.of("confirmPassword", "Пароли не совпадают"));
    }

    return ResponseEntity.ok(authService.register(request));
}
4. Кастомный валидатор — @UniqueEmail
Java
// ── Шаг 1: создаём аннотацию
@Documented                                        // включить в Javadoc
@Constraint(validatedBy = UniqueEmailValidator.class) // класс с логикой
@Target({ ElementType.FIELD, ElementType.PARAMETER })
@Retention(RetentionPolicy.RUNTIME)
public @interface UniqueEmail {
    String message() default "Email уже используется"; // дефолтное сообщение
    Class<?>[] groups() default {};                   // для групп валидации
    Class<? extends Payload>[] payload() default {};  // метаданные (обязательное поле)
}

// ── Шаг 2: реализуем логику
@Component                                         // Spring бин — можно инжектировать
public class UniqueEmailValidator
        implements ConstraintValidator<UniqueEmail, String> { // <Аннотация, ТипПоля>

    private final UserRepository userRepository;   // инжектируем репозиторий

    public UniqueEmailValidator(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Override
    public void initialize(UniqueEmail constraintAnnotation) {
        // вызывается при создании — можно считать параметры аннотации
    }

    @Override
    public boolean isValid(String email, ConstraintValidatorContext context) {
        if (email == null) return true;              // null проверяет @NotNull отдельно
        return !userRepository.existsByEmail(email); // false → ошибка валидации
    }
}

// ── Шаг 3: используем в DTO
public record RegisterRequest(
    @NotBlank
    @Email
    @UniqueEmail                                    // наша кастомная аннотация!
    String email,

    @NotBlank
    @Size(min = 8)
    String password
) {}
5. Кастомный валидатор на уровне класса — проверка паролей
Java
// ── Аннотация на уровне класса (cross-field validation)
@Documented
@Constraint(validatedBy = PasswordMatchValidator.class)
@Target(ElementType.TYPE)                          // TYPE — на весь класс/record
@Retention(RetentionPolicy.RUNTIME)
public @interface PasswordMatch {
    String message() default "Пароли не совпадают";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
    String field()        default "password";       // имя поля пароля
    String matchField()  default "confirmPassword"; // имя поля подтверждения
}

// ── Реализатор
public class PasswordMatchValidator
        implements ConstraintValidator<PasswordMatch, Object> { // Object = весь класс

    private String field;
    private String matchField;

    @Override
    public void initialize(PasswordMatch ann) {
        this.field      = ann.field();               // читаем параметры аннотации
        this.matchField = ann.matchField();
    }

    @Override
    public boolean isValid(Object value, ConstraintValidatorContext ctx) {
        try {
            // Читаем поля через рефлексию
            String pwd  = (String) value.getClass().getMethod(field).invoke(value);
            String conf = (String) value.getClass().getMethod(matchField).invoke(value);
            boolean match = Objects.equals(pwd, conf); // сравниваем пароли
            if (!match) {
                // Ошибка привязывается к конкретному полю
                ctx.disableDefaultConstraintViolation();
                ctx.buildConstraintViolationWithTemplate(ctx.getDefaultConstraintMessageTemplate())
                   .addPropertyNode(matchField)     // на поле confirmPassword
                   .addConstraintViolation();
            }
            return match;
        } catch (Exception e) {
            return false;
        }
    }
}

// ── Использование на DTO
@PasswordMatch                                     // на классе — проверяет два поля
public record ChangePasswordRequest(
    @NotBlank String password,
    @NotBlank String confirmPassword
) {}
6. Группы валидации
Java
// ── Шаг 1: интерфейсы-маркеры для групп
public interface OnCreate {}   // группа для создания
public interface OnUpdate {}   // группа для обновления

// ── Шаг 2: DTO с группами
public class UserRequest {

    @NotBlank(groups = { OnCreate.class, OnUpdate.class }) // обязателен в обоих случаях
    private String name;

    @NotBlank(groups = { OnCreate.class, OnUpdate.class })
    @Email(groups = { OnCreate.class, OnUpdate.class })
    private String email;

    @NotBlank(groups = OnCreate.class)              // обязателен ТОЛЬКО при создании
    @Size(min = 8, groups = OnCreate.class)
    private String password;                        // при обновлении — опционально
    // геттеры/сеттеры...
}

// ── Шаг 3: @Validated с группой в контроллере
@RestController
@RequestMapping("/api/v1/users")
public class UserController {

    @PostMapping
    public ResponseEntity<UserResponse> create(
            @RequestBody
            @Validated(OnCreate.class)               // только аннотации группы OnCreate
            UserRequest request) {                   // password обязателен
        return ResponseEntity.status(201).body(userService.create(request));
    }

    @PutMapping("/{id}")
    public ResponseEntity<UserResponse> update(
            @PathVariable Long id,
            @RequestBody
            @Validated(OnUpdate.class)               // только аннотации группы OnUpdate
            UserRequest request) {                   // password НЕ обязателен
        return ResponseEntity.ok(userService.update(id, request));
    }
}
❓ Вопросы для собеседования
В чём разница между @NotNull, @NotEmpty и @NotBlank?
What is the difference between @NotNull, @NotEmpty, and @NotBlank?
Medium▼
✅ Ответ
@NotNull — только проверяет что значение не null. Пустая строка "" и " " — пройдут.
@NotEmpty — не null и не пустой. Работает для String, Collection, Map, Array. Строка из пробелов " " пройдёт!
@NotBlank — только для String. Не null, не "", не только пробелы. Самая строгая — используй по умолчанию для строковых полей.
В чём разница между @Valid и @Validated?
What is the difference between @Valid and @Validated?
Medium▼
✅ Ответ
@Valid — из Jakarta Validation. Используется для валидации @RequestBody. Не поддерживает группы. Кидает MethodArgumentNotValidException.
@Validated — из Spring. Поддерживает группы (@Validated(OnCreate.class)). Для валидации @PathVariable и @RequestParam — ставится на весь класс контроллера. Кидает ConstraintViolationException.
Как создать кастомный валидатор?
How do you create a custom validator in Spring?
Hard▼
✅ Ответ
1. Создать аннотацию с @Constraint(validatedBy = MyValidator.class) и обязательными полями message(), groups(), payload().
2. Создать класс реализующий ConstraintValidator<MyAnnotation, FieldType> с методом isValid(value, context).
3. Пометить класс @Component если нужен DI (например, обращение к БД).
4. Применить аннотацию к полю или классу DTO.
Что такое BindingResult и зачем он нужен?
What is BindingResult and when would you use it?
Medium▼
✅ Ответ
BindingResult — объект содержащий результаты валидации. Если добавить его параметром сразу после @Valid объекта, Spring не кидает исключение при ошибках. Вместо этого заполняет BindingResult. Используется когда нужна особая логика при ошибках: дополнительные проверки, частичное сохранение, специальный ответ. В большинстве REST API лучше использовать GlobalExceptionHandler — он чище.
Как работают группы валидации?
How do validation groups work in Spring?
Hard▼
✅ Ответ
Группы позволяют применять разные правила валидации для разных операций. Создаются как интерфейсы-маркеры (interface OnCreate {}). На аннотациях указывается группа: @NotBlank(groups = OnCreate.class). В контроллере используется @Validated(OnCreate.class) вместо @Valid — Spring применит только правила указанной группы. Пример: пароль обязателен при создании, но не при обновлении профиля.
