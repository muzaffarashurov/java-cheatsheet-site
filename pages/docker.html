📦 Образы и контейнеры

Docker образ состоит из слоёв (layers). Каждая инструкция в Dockerfile создаёт новый слой. Слои кэшируются — если слой не изменился, Docker использует кэш. Это ускоряет пересборку.

Структура слоёв образа
  ┌─────────────────────────────┐
  │   Writable Container Layer  │  ← контейнер пишет сюда (временно)
  ├─────────────────────────────┤
  │   COPY app.jar /app.jar     │  ← слой 4 (наш jar)
  ├─────────────────────────────┤
  │   RUN apt-get install ...   │  ← слой 3
  ├─────────────────────────────┤
  │   ENV JAVA_OPTS=""          │  ← слой 2
  ├─────────────────────────────┤
  │   FROM eclipse-temurin:21   │  ← слой 1 (базовый образ)
  └─────────────────────────────┘
  Слои кэшируются! Изменение jar пересобирает только слой 4.
💡 Жизненный цикл контейнера
created → running → paused → stopped → removed
docker run = pull + create + start

⚠️ CMD vs ENTRYPOINT
CMD — команда по умолчанию, легко переопределяется при docker run image другая_команда.
ENTRYPOINT — основной исполняемый файл, аргументы из CMD добавляются к нему.
Лучше использовать оба: ENTRYPOINT ["java"] + CMD ["-jar", "app.jar"]

🏗 Multi-stage Build

Multi-stage build позволяет использовать несколько FROM в одном Dockerfile. Финальный образ копирует только нужные артефакты из промежуточных стадий — получается маленький продакшен образ без инструментов сборки.

✅ Результат
Образ со стадией сборки Maven: ~500 МБ. Финальный образ только с JRE + jar: ~150 МБ. Меньше размер → быстрее деплой → меньше attack surface.
🌱 Spring Boot + Docker

Spring Boot создаёт fat JAR со всеми зависимостями. При правильной слоёвке Dockerfile зависимости кэшируются отдельно от кода приложения — пересборка намного быстрее.

💡 Layered JAR (Spring Boot 2.3+)
Spring Boot поддерживает слоёные JAR-ы: spring-boot-maven-plugin раскладывает зависимости, ресурсы и код по отдельным слоям Docker. Зависимости меняются редко — их слой кэшируется. Код меняется часто — только он пересобирается.
✅ Best Practices
✅ Правильно
  • Multi-stage build — маленький финальный образ
  • Использовать JRE а не JDK в продакшене
  • Запускать не под root: USER appuser
  • Конкретные теги: :21-jre, не :latest
  • Копировать зависимости отдельно от кода (кэш)
  • HEALTHCHECK для мониторинга
  • Секреты через ENV переменные, не в Dockerfile
  • .dockerignore — исключить target/, .git/, *.md
🚫 Ошибки
  • Хранить секреты (пароли) в Dockerfile
  • Использовать :latest тег в продакшене
  • Запускать контейнер под root
  • Копировать всё подряд (COPY . .) — включая target/
  • Слишком много слоёв RUN (лучше объединять через &&)
  • Не чистить кэш пакетного менеджера (apt-get clean)
  • Не использовать .dockerignore
💻 Примеры кода
1. Простой Dockerfile для Spring Boot
Dockerfile
# ── Базовый образ: только JRE (не JDK!) — меньше размер
FROM eclipse-temurin:21-jre-alpine             # alpine = минимальный Linux (~5MB)

# ── Метаданные образа
LABEL maintainer="team@company.com"
LABEL version="1.0.0"
LABEL description="My Spring Boot Application"

# ── Рабочая директория внутри контейнера
WORKDIR /app                                  # все следующие команды выполняются здесь

# ── Создаём непривилегированного пользователя (безопасность)
RUN addgroup -S appgroup && adduser -S appuser -G appgroup # alpine синтаксис

# ── Копируем JAR (отдельным слоем для кэширования)
COPY target/*.jar app.jar                    # из target/ берём jar файл

# ── Меняем владельца файлов
RUN chown -R appuser:appgroup /app

# ── Переключаемся на непривилегированного пользователя
USER appuser                                  # не запускаем под root!

# ── Документируем порт (информационно, не открывает реально)
EXPOSE 8080

# ── Health check через Actuator
HEALTHCHECK --interval=30s --timeout=10s --retries=3 \
    CMD wget -q --spider http://localhost:8080/actuator/health || exit 1

# ── Переменные окружения по умолчанию
ENV JAVA_OPTS=""                             # можно переопределить при запуске
ENV SPRING_PROFILES_ACTIVE="prod"

# ── Точка входа + параметры JVM
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar /app/app.jar"]
2. Multi-stage Dockerfile (Maven + Spring Boot)
Dockerfile
# ════════════════════════════════
   СТАДИЯ 1: Сборка (Build Stage)
   ════════════════════════════════
FROM eclipse-temurin:21-jdk-alpine AS builder  # AS builder — имя стадии

WORKDIR /build

# ── Сначала копируем только pom.xml — слой кэшируется
COPY pom.xml .
COPY .mvn/ .mvn/                              # Maven wrapper если есть
COPY mvnw .

# ── Скачиваем зависимости (кэшируется пока pom.xml не изменился)
RUN ./mvnw dependency:go-offline -q          # -q = тихий режим

# ── Теперь копируем исходный код
COPY src/ src/

# ── Собираем проект (пропускаем тесты для скорости)
RUN ./mvnw package -DskipTests -q            # создаёт target/*.jar

# ── Разбиваем JAR на слои (Spring Boot Layered JAR)
RUN java -Djarmode=layertools -jar target/*.jar extract # создаёт: dependencies/, snapshot-dependencies/, spring-boot-loader/, application/

# ════════════════════════════════
   СТАДИЯ 2: Продакшен образ
   ════════════════════════════════
FROM eclipse-temurin:21-jre-alpine           # только JRE — намного меньше

WORKDIR /app

# ── Безопасность: непривилегированный пользователь
RUN addgroup -S spring && adduser -S spring -G spring

# ── Копируем слои из стадии builder (порядок важен для кэша!)
COPY --from=builder --chown=spring:spring /build/dependencies/          ./  # редко меняются
COPY --from=builder --chown=spring:spring /build/snapshot-dependencies/ ./  # snapshot зависимости
COPY --from=builder --chown=spring:spring /build/spring-boot-loader/    ./  # Spring загрузчик
COPY --from=builder --chown=spring:spring /build/application/           ./  # наш код — часто меняется

USER spring                                  # запускаем не под root

EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
    CMD wget -qO- http://localhost:8080/actuator/health | grep -q UP || exit 1

# ── Запускаем через Spring Boot LayeredJar загрузчик
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

4. Основные команды для работы с Spring Boot контейнером
Bash
# ── Сборка образа
docker build -t myapp:1.0 .                  # собрать с тегом
docker build -t myapp:latest --no-cache .     # без кэша (чистая сборка)
docker build -f Dockerfile.prod -t myapp .    # указать файл Dockerfile

# ── Запуск Spring Boot контейнера
docker run -d \                               # -d = detached (фоновый режим)
  --name myapp \                              # имя контейнера
  -p 8080:8080 \                              # хост_порт:контейнер_порт
  -e SPRING_PROFILES_ACTIVE=prod \           # ENV переменная
  -e DATABASE_URL=jdbc:postgresql://db:5432/mydb \
  -e DATABASE_PASSWORD=secret \
  --memory=512m \                             # ограничение памяти
  --cpus=1.0 \                               # ограничение CPU
  --restart unless-stopped \                  # перезапускать автоматически
  --network mynetwork \                       # подключить к сети
  myapp:1.0

# ── Логи
docker logs myapp                             # все логи
docker logs -f myapp                          # следить в реальном времени (follow)
docker logs --tail 100 myapp                  # последние 100 строк
docker logs --since 10m myapp                 # за последние 10 минут

# ── Отладка внутри контейнера
docker exec -it myapp sh                      # войти в shell (alpine = sh, не bash)
docker exec -it myapp bash                    # bash (если установлен)
docker exec myapp ps aux                      # запущенные процессы
docker exec myapp cat /etc/os-release         # версия OS в контейнере

# ── Сеть
docker network create mynetwork              # создать bridge сеть
docker network ls                            # список сетей
docker network connect mynetwork myapp       # подключить контейнер к сети
docker network inspect mynetwork             # детали сети

# ── Очистка (осторожно!)
docker system prune                          # удалить остановленные контейнеры, неиспользуемые образы
docker system prune -a --volumes             # + volumes (ОСТОРОЖНО: удалит данные!)
docker image prune -a                        # удалить все неиспользуемые образы

# ── Ресурсы
docker stats                                 # CPU, память всех контейнеров
docker stats myapp                           # только myapp
docker top myapp                             # процессы в контейнере
5. JVM настройки для Docker
Dockerfile + Bash
# ── С Java 11+ JVM автоматически определяет лимиты контейнера
# Раньше нужно было: -XX:+UseContainerSupport (теперь включено по умолчанию)

# ── Рекомендуемые JVM флаги для Docker
ENV JAVA_OPTS="\
  -XX:MaxRAMPercentage=75.0 \
  -XX:InitialRAMPercentage=50.0 \
  -XX:+UseG1GC \
  -XX:+ExitOnOutOfMemoryError \
  -Djava.security.egd=file:/dev/./urandom \
  -Dspring.backgroundpreinitializer.ignore=true"

# Объяснение флагов:
# MaxRAMPercentage=75 — JVM использует 75% от лимита контейнера для heap
# InitialRAMPercentage=50 — начальный heap 50% от лимита
# UseG1GC — G1 сборщик мусора (хорош для heap > 4GB)
# ExitOnOutOfMemoryError — завершить при OOM (Docker перезапустит)
# urandom — ускоряет генерацию случайных чисел (важно для SSL)

# ── Запуск с лимитами памяти
docker run -d \
  --memory=1g \                              # контейнер получит 1GB RAM
  -e JAVA_OPTS="-XX:MaxRAMPercentage=75.0 -XX:+UseG1GC" \
  myapp:1.0
# JVM получит 768MB heap (75% от 1GB)

# ── Проверка heap внутри контейнера
docker exec myapp java -XshowSettings:vm -version # показать настройки JVM
❓ Вопросы для собеседования
В чём разница между Docker образом и контейнером?
What is the difference between a Docker image and a container?
Easy▼
✅ Ответ
Image — неизменяемый (read-only) шаблон файловой системы, состоящий из слоёв. Как класс в Java. Container — запущенный экземпляр образа с дополнительным записываемым слоем. Как объект класса. Один образ → много контейнеров. Когда контейнер останавливается — его записываемый слой теряется (если нет Volume).
Что такое multi-stage build и зачем он нужен?
What is a multi-stage Docker build and why is it used?
Medium▼
✅ Ответ
Multi-stage build использует несколько FROM инструкций. Первая стадия (builder) — с JDK и Maven собирает jar. Финальная стадия — только JRE, копирует jar из builder через COPY --from=builder. Результат: маленький продакшен образ (~150МБ) вместо образа с полным JDK и Maven (~500МБ). Меньше размер → быстрее деплой, меньше уязвимостей.
Почему нельзя запускать контейнер под root?
Why shouldn't you run a container as root?
Medium▼
✅ Ответ
Если злоумышленник получит доступ к контейнеру запущенному под root, и у него есть уязвимость escape (выход из контейнера) — он получит root права на хостовой машине. Используй USER appuser в Dockerfile. Непривилегированный пользователь не может читать/писать системные файлы хоста.
Как работает кэширование слоёв Docker и как его использовать?
How does Docker layer caching work and how to leverage it?
Hard▼
✅ Ответ
Каждая инструкция Dockerfile создаёт слой. Docker кэширует слои — если инструкция и её входные файлы не изменились, берётся кэш. Изменение слоя инвалидирует все последующие слои. Оптимизация: сначала копировать то что меняется редко (pom.xml → скачать зависимости), потом то что меняется часто (src/). Так при изменении кода зависимости не перекачиваются.
Чем COPY отличается от ADD в Dockerfile?
What is the difference between COPY and ADD in Dockerfile?
Easy▼
✅ Ответ
COPY — просто копирует файлы с хоста в образ. ADD умеет больше: скачать файл по URL, автоматически распаковать tar архив. Рекомендуется использовать COPY — поведение предсказуемо. ADD только когда нужна его дополнительная функциональность (распаковка tar). Скачивать файлы через ADD не рекомендуется — лучше RUN wget чтобы в одном слое скачать и очистить.
