📌 Краткий конспект
Порядок выполнения SQL запроса
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT/OFFSET

⚠️ NULL — ловушка для новичков
NULL = NULL → UNKNOWN (не true!). Для сравнения с NULL всегда используй IS NULL или IS NOT NULL. NULL != NULL тоже не работает! Функции: COALESCE(val, default), NULLIF(a, b).

💡 LEFT JOIN + WHERE IS NULL — антиджоин
LEFT JOIN b ON a.id = b.a_id WHERE b.id IS NULL — найти строки в A, у которых нет соответствия в B. Например: пользователи без заказов.

💡 WHERE vs HAVING
WHERE фильтрует строки до группировки — нельзя использовать агрегатные функции.
HAVING фильтрует группы после GROUP BY — можно использовать COUNT, SUM и т.д.

🪟 Window Functions (Оконные функции)

Оконные функции вычисляют значение для каждой строки на основе «окна» связанных строк. В отличие от GROUP BY — не схлопывают строки в группу.

📑 Индексы

Индекс — вспомогательная структура данных (обычно B-Tree), ускоряющая поиск. Ускоряет SELECT, замедляет INSERT/UPDATE/DELETE.

Тип индексаСтруктураКогда
B-Tree (default)Сбалансированное дерево=, <, >, BETWEEN, ORDER BY
HashХэш-таблицаТолько = (очень быстро)
GINИнвертированный индексМассивы, JSONB, полнотекстовый поиск
GiSTДерево поискаГеоданные, диапазоны
PartialИндекс по условиюWHERE deleted_at IS NULL
CompositeПо нескольким столбцамЗапросы по нескольким полям
CoveringВключает все нужные столбцыIndex-only scan без чтения таблицы
✅ Создавай индекс на
  • Поля в WHERE, JOIN ON, ORDER BY
  • Foreign keys
  • Поля с высокой кардинальностью (email, uuid)
  • Поля частых поисковых запросов
  • Composite: порядок важен — самое селективное первым
🚫 Не создавай индекс на
  • Маленькие таблицы (seq scan быстрее)
  • Поля с низкой кардинальностью (boolean, статус 3 значения)
  • Таблицы с частыми INSERT/UPDATE/DELETE
  • Поля редко используемые в WHERE/JOIN
⚠️ Когда индекс НЕ используется
Функция на столбце: WHERE UPPER(name) = 'IVAN' → индекс не используется.
Начало LIKE с %: WHERE name LIKE '%ван' → полный скан.
Неявное приведение типов: WHERE id = '123' (id — integer) → может не использовать.
Маленький результат относительно таблицы — планировщик может выбрать seq scan.

Аномалии изоляции — что это такое ▼

Dirty Read — читаем данные незакоммиченной транзакции. Та транзакция откатится — мы работали с фантомными данными.

Non-repeatable Read — в рамках одной транзакции дважды читаем одну строку и получаем разные значения (другая транзакция изменила и закоммитила между чтениями).

Phantom Read — повторный SELECT с условием возвращает разные строки (другая транзакция вставила/удалила строки между чтениями).

📐 Нормализация БД
Нормальная формаТребованиеЧто устраняет
1NFАтомарные значения, нет повторяющихся группМассивы в ячейках, дублирующиеся колонки
2NF1NF + нет частичных зависимостей от составного PKЗависимость от части ключа
3NF2NF + нет транзитивных зависимостейA→B→C (B не ключ, но определяет C)
BCNFСтроже 3NF — каждая нетривиальная зависимость от суперключаАномалии при нескольких кандидат-ключах
✅ Нормализация
  • Нет дублирования данных
  • Аномалии вставки/обновления/удаления устранены
  • Экономия места
  • Целостность данных
  • Подходит для OLTP (транзакционные системы)
📊 Денормализация
  • Дублирование для ускорения чтения
  • Меньше JOIN-ов в запросах
  • Быстрее для аналитики
  • Подходит для OLAP (аналитические системы)
  • Применяется осознанно, не по незнанию
💻 Примеры SQL запросов
1. SELECT с фильтрацией, сортировкой, пагинацией
SQL
-- ── Базовый SELECT
SELECT
    u.id,                                        -- id пользователя
    u.name,                                      -- имя
    u.email,                                     -- email
    COALESCE(u.phone, 'не указан') AS phone,   -- NULL → 'не указан'
    UPPER(u.name) AS name_upper,               -- функция на поле
    DATE_PART('year', u.created_at) AS year    -- год регистрации
FROM users u                                     -- алиас u для таблицы
WHERE
    u.active = true                              -- только активные
    AND u.age BETWEEN 18 AND 65                 -- возраст 18-65
    AND u.role IN ('USER', 'MODERATOR')         -- роль из списка
    AND u.email ILIKE '%@gmail%'               -- gmail без учёта регистра
    AND u.deleted_at IS NULL                    -- не удалённые (soft delete)
ORDER BY
    u.created_at DESC,                          -- сначала новые
    u.name ASC                                  -- при равной дате — по имени
LIMIT 20                                        -- страница = 20 записей
OFFSET 40;                                       -- пропустить первые 40 (страница 3)

-- ── DISTINCT — уникальные значения
SELECT DISTINCT department                       -- только уникальные отделы
FROM employees
ORDER BY department;

-- ── CASE WHEN — условное выражение (как if-else)
SELECT
    name,
    salary,
    CASE
        WHEN salary < 50000  THEN 'Junior'      -- если зарплата < 50k
        WHEN salary < 100000 THEN 'Middle'
        WHEN salary < 200000 THEN 'Senior'
        ELSE 'Lead'                               -- иначе
    END AS grade                                 -- псевдоним столбца
FROM employees;
2. JOIN — все типы
SQL
-- ── INNER JOIN: только пользователи у которых ЕСТЬ заказы
SELECT
    u.name,
    o.id       AS order_id,
    o.total    AS order_total
FROM users u
INNER JOIN orders o ON u.id = o.user_id        -- связь по внешнему ключу
WHERE o.status = 'COMPLETED';

-- ── LEFT JOIN: ВСЕ пользователи, даже без заказов
SELECT
    u.name,
    COUNT(o.id) AS orders_count,               -- 0 если заказов нет
    COALESCE(SUM(o.total), 0) AS total_spent   -- NULL → 0
FROM users u
LEFT JOIN orders o ON u.id = o.user_id         -- у пользователей без заказов o.* = NULL
GROUP BY u.id, u.name;

-- ── Найти пользователей БЕЗ заказов (антиджоин)
SELECT u.name
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.id IS NULL;                            -- нет совпадения в правой таблице

-- ── SELF JOIN: сотрудник и его менеджер (в одной таблице)
SELECT
    e.name  AS employee,                        -- сотрудник
    m.name  AS manager                          -- его менеджер
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;   -- тот же employees, алиас m

-- ── JOIN трёх таблиц
SELECT
    u.name,
    o.id       AS order_id,
    p.name     AS product,
    oi.quantity
FROM users u
JOIN orders o      ON u.id = o.user_id          -- пользователь → заказы
JOIN order_items oi ON o.id = oi.order_id       -- заказы → позиции заказа
JOIN products p    ON oi.product_id = p.id;    -- позиции → товары
3. GROUP BY, HAVING и агрегации
SQL
-- ── Продажи по отделам: только отделы с суммой > 100k
SELECT
    department,
    COUNT(*)            AS employee_count,       -- количество сотрудников
    AVG(salary)         AS avg_salary,           -- средняя зарплата
    MAX(salary)         AS max_salary,           -- максимальная зарплата
    SUM(salary)         AS total_payroll         -- общий фонд зарплат
FROM employees
WHERE active = true                              -- WHERE фильтрует ДО группировки
GROUP BY department                              -- группируем по отделу
HAVING SUM(salary) > 100000                    -- HAVING фильтрует ПОСЛЕ группировки
ORDER BY total_payroll DESC;

-- ── Топ-5 клиентов по сумме заказов
SELECT
    u.name,
    COUNT(o.id)   AS orders_count,
    SUM(o.total)  AS total_spent
FROM users u
JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name                           -- по id и name (name функционально зависит от id)
ORDER BY total_spent DESC
LIMIT 5;

-- ── COUNT DISTINCT: уникальные покупатели в каждом городе
SELECT
    city,
    COUNT(DISTINCT user_id) AS unique_buyers    -- только уникальные пользователи
FROM orders o
JOIN users u ON o.user_id = u.id
GROUP BY city;
4. CTE и подзапросы
SQL
-- ── CTE (WITH) — именованный подзапрос для читаемости
WITH
-- Шаг 1: считаем сумму по каждому пользователю
user_totals AS (
    SELECT
        user_id,
        SUM(total) AS total_spent,
        COUNT(*)   AS orders_count
    FROM orders
    WHERE status = 'COMPLETED'
    GROUP BY user_id
),
-- Шаг 2: присваиваем категорию
user_segments AS (
    SELECT
        ut.*,
        CASE
            WHEN total_spent > 100000 THEN 'VIP'
            WHEN total_spent > 10000  THEN 'Regular'
            ELSE 'New'
        END AS segment
    FROM user_totals ut
)
-- Финальный запрос — используем оба CTE
SELECT
    u.name,
    u.email,
    us.total_spent,
    us.orders_count,
    us.segment
FROM user_segments us
JOIN users u ON us.user_id = u.id
ORDER BY us.total_spent DESC;

-- ── Рекурсивный CTE: обход дерева категорий
WITH RECURSIVE category_tree AS (
    -- Базовый случай: корневые категории
    SELECT id, name, parent_id, 0 AS level, name AS path
    FROM categories
    WHERE parent_id IS NULL

    UNION ALL

    -- Рекурсивный случай: дочерние категории
    SELECT
        c.id, c.name, c.parent_id,
        ct.level + 1,                           -- увеличиваем уровень
        ct.path || ' > ' || c.name              -- строим путь
    FROM categories c
    JOIN category_tree ct ON c.parent_id = ct.id -- связь с родителем
)
SELECT level, path
FROM category_tree
ORDER BY path;
5. Window Functions — оконные функции
SQL
-- ── ROW_NUMBER: нумерация в каждом отделе
SELECT
    name,
    department,
    salary,
    ROW_NUMBER() OVER (
        PARTITION BY department  -- отдельное окно для каждого отдела
        ORDER BY salary DESC    -- нумеруем от самого высокого
    ) AS rank_in_dept
FROM employees;

-- ── Топ-1 сотрудник по зарплате в каждом отделе
SELECT * FROM (
    SELECT
        name, department, salary,
        ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
    FROM employees
) ranked
WHERE rn = 1;                                   -- берём только первую строку каждого отдела

-- ── LAG: сравниваем продажи с предыдущим месяцем
SELECT
    month,
    revenue,
    LAG(revenue, 1) OVER (ORDER BY month) AS prev_revenue, -- предыдущий месяц
    revenue - LAG(revenue, 1) OVER (ORDER BY month) AS diff,  -- разница
    ROUND(
        (revenue - LAG(revenue,1) OVER (ORDER BY month))
        / LAG(revenue,1) OVER (ORDER BY month) * 100, 2
    ) AS growth_pct                              -- рост в процентах
FROM monthly_revenue;

-- ── SUM OVER: накопительная сумма (running total)
SELECT
    sale_date,
    amount,
    SUM(amount) OVER (ORDER BY sale_date) AS running_total  -- нарастающий итог
FROM sales;

-- ── RANK vs DENSE_RANK vs ROW_NUMBER
SELECT
    name, score,
    ROW_NUMBER()  OVER (ORDER BY score DESC) AS row_num,   -- 1,2,3,4,5
    RANK()        OVER (ORDER BY score DESC) AS rank,      -- 1,1,3,4,5 (пропуск!)
    DENSE_RANK()  OVER (ORDER BY score DESC) AS drank      -- 1,1,2,3,4 (без пропуска)
FROM scores;
6. DDL — создание таблиц и индексов
SQL
-- ── Создание таблицы с ограничениями
CREATE TABLE users (
    id          BIGSERIAL PRIMARY KEY,           -- автоинкремент PK
    email       VARCHAR(255) NOT NULL UNIQUE,   -- уникальный email
    name        VARCHAR(100) NOT NULL,
    age         INTEGER CHECK (age >= 0 AND age <= 150), -- диапазон
    role        VARCHAR(20) NOT NULL DEFAULT 'USER',
    active      BOOLEAN NOT NULL DEFAULT true,
    created_at  TIMESTAMP NOT NULL DEFAULT NOW(), -- текущее время по умолчанию
    deleted_at  TIMESTAMP                          -- NULL = не удалён (soft delete)
);

-- ── Внешний ключ
CREATE TABLE orders (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT NOT NULL
                    REFERENCES users(id)         -- FK на users
                    ON DELETE CASCADE,           -- удалить заказы при удалении юзера
    total       DECIMAL(12, 2) NOT NULL,         -- 10 цифр до запятой, 2 после
    status      VARCHAR(20) NOT NULL,
    created_at  TIMESTAMP NOT NULL DEFAULT NOW()
);

-- ── Создание индексов
CREATE INDEX idx_users_email
    ON users(email);                             -- простой индекс на email

CREATE INDEX idx_orders_user_status
    ON orders(user_id, status);                  -- составной индекс

CREATE INDEX idx_users_active
    ON users(id)
    WHERE deleted_at IS NULL;                  -- частичный индекс только для активных

❓ Вопросы для собеседования
В чём разница между WHERE и HAVING?
What is the difference between WHERE and HAVING?
Easy▼
✅ Ответ
WHERE фильтрует строки до группировки — нельзя использовать агрегатные функции (COUNT, SUM). HAVING фильтрует группы после GROUP BY — можно использовать агрегатные функции. Если нет GROUP BY — HAVING применяется ко всей таблице как одной группе.
🔥 Пример
WHERE salary > 50000 — фильтруем сотрудников до группировки. HAVING AVG(salary) > 80000 — оставляем только отделы со средней зарплатой > 80k.
Что такое ACID? Расскажи каждое свойство.
What is ACID? Explain each property.
Medium▼
✅ Ответ
A — Atomicity: транзакция — атомарная единица, либо все операции выполнены, либо ни одна.
C — Consistency: транзакция переводит БД из одного корректного состояния в другое, не нарушая ограничения.
I — Isolation: параллельные транзакции не видят незакоммиченных изменений друг друга.
D — Durability: после COMMIT данные сохранены даже при сбое системы.
🔥 Пример
«Перевод денег: списание и зачисление — одна транзакция. Atomicity: нельзя списать без зачисления. Consistency: баланс не может стать отрицательным. Isolation: другой пользователь не видит промежуточного состояния. Durability: после подтверждения данные сохранены.»
Что такое индекс и когда его создавать?
What is a database index and when should you create one?
Medium▼
✅ Ответ
Индекс — вспомогательная структура (обычно B-Tree), ускоряющая поиск. Ускоряет SELECT с WHERE/JOIN/ORDER BY, но замедляет INSERT/UPDATE/DELETE (нужно обновить индекс). Создавать на: поля в WHERE и JOIN ON, Foreign Keys, поля с высокой кардинальностью, часто используемые в запросах. НЕ создавать на: маленькие таблицы, поля с малой кардинальностью (bool, enum из 2-3 значений).
Чем отличается INNER JOIN от LEFT JOIN?
What is the difference between INNER JOIN and LEFT JOIN?
Easy▼
✅ Ответ
INNER JOIN — возвращает только строки, у которых есть совпадение в обеих таблицах. LEFT JOIN — возвращает все строки из левой таблицы, для несовпадающих строк правой таблицы вставляет NULL. Пример: LEFT JOIN нужен когда хочешь показать всех пользователей, включая тех у кого нет заказов.
Что такое Window Functions и чем они отличаются от GROUP BY?
What are Window Functions and how do they differ from GROUP BY?
Hard▼
✅ Ответ
GROUP BY сжимает строки в группы — теряем доступ к отдельным строкам. Window Functions вычисляют значение для каждой строки на основе «окна» связанных строк — строки не схлопываются. Например: ROW_NUMBER() нумерует строки в каждой группе, SUM() OVER() считает накопительную сумму, LAG() даёт значение предыдущей строки.
🔥 Пример использования
«Топ-1 сотрудник по зарплате в каждом отделе: GROUP BY не даст строки сотрудников, даст только агрегаты. ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) = 1 — идеальное решение.»
Какие уровни изоляции транзакций существуют?
What are the transaction isolation levels?
Hard▼
✅ Ответ
READ UNCOMMITTED — видим незакоммиченные данные (dirty read). Почти не используется.
READ COMMITTED — видим только закоммиченные данные. Default в PostgreSQL. Non-repeatable read возможен.
REPEATABLE READ — одни и те же строки дают одинаковый результат в рамках транзакции. Phantom read возможен.
SERIALIZABLE — полная изоляция, транзакции выполняются как последовательные. Самый медленный.
