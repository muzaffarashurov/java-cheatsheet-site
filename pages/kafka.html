📌 Краткий конспект
Что такое Kafka
Apache Kafka — распределённая платформа потоковой передачи событий (event streaming). Используется для: асинхронного взаимодействия микросервисов, обработки потоков данных в реальном времени, надёжной передачи событий с гарантией доставки.

🧩 Ключевые концепции
Схема Kafka
  Producer                    Kafka Broker                  Consumer Group A
  ┌──────────┐                ┌──────────────────┐            ┌──────────────┐
  │ Service A│──publish──────▶│  Topic: orders   │──consume──▶│ Consumer 1   │ → Partition 0
  │          │                │  Partition 0 ●●● │            │ Consumer 2   │ → Partition 1
  └──────────┘                │  Partition 1 ●●● │            │ Consumer 3   │ → Partition 2
                              │  Partition 2 ●●● │            └──────────────┘
  Producer                    │                  │
  ┌──────────┐                │  Replication     │            Consumer Group B
  │ Service B│──publish──────▶│  Factor: 3       │──consume──▶┌──────────────┐
  └──────────┘                └──────────────────┘            │ Consumer 1   │ → все партиции
                                                              └──────────────┘

  Каждая Consumer Group читает топик независимо!
  В группе: 1 партиция = 1 consumer (параллельность = число партиций)
💡 Гарантии доставки
At most once — сообщение доставляется 0 или 1 раз (возможна потеря).
At least once — минимум 1 раз (возможны дубли). ✅ Default в большинстве систем.
Exactly once — ровно 1 раз. Требует idempotent producer + transactional consumer. Сложнее и медленнее.

💡 Выбор партиции по ключу
Если у сообщения есть ключ — Kafka гарантирует что все сообщения с одним ключом попадут в одну партицию → порядок сохранён. Без ключа — round-robin по партициям.
📥 Consumer и Consumer Group

Consumers объединяются в Consumer Group. Каждая партиция обрабатывается ровно одним consumer в группе. Число consumer в группе > числа партиций — лишние простаивают.

ПараметрОписаниеЗначение

auto.offset.resetОткуда начать если нет offsetearliest или latest
enable.auto.commitАвто-коммит offsetfalse для надёжности
max.poll.recordsМаксимум записей за один poll500 (default)
session.timeout.msТаймаут сессии consumer45000ms
heartbeat.interval.msИнтервал heartbeat3000ms
⚠️ Rebalancing — частая проблема
Rebalance происходит когда consumer присоединяется или уходит из группы. Во время rebalance обработка приостанавливается. Признак: длинные паузы в обработке. Решение: увеличить session.timeout.ms, использовать Static Group Membership.
📊 Partitions и Offset
Партиции
  • Единица параллельности в Kafka
  • Внутри партиции порядок гарантирован
  • Между партициями порядок НЕ гарантирован
  • Число партиций = максимум consumer в группе
  • Нельзя уменьшить после создания
  • Рекомендация: 3-12 партиций для начала
Offset
  • Монотонно возрастающий номер сообщения
  • Хранится в специальном топике __consumer_offsets
  • Commit offset = сообщение обработано
  • auto.commit — риск потери или дублей
  • Ручной commit после обработки = надёжность
  • Можно перемотать (reset) на любой offset

⚙️ Конфигурация application.yml
YAML
spring:
  kafka:
    bootstrap-servers: localhost:9092       # адрес брокера

    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
      acks: all                              # ждать подтверждения от всех реплик
      retries: 3                            # число повторов
      properties:
        enable.idempotence: true           # идемпотентная отправка
        compression.type: snappy            # сжатие
        linger.ms: 5                        # батчинг 5ms

    consumer:
      group-id: my-service-group           # ID группы потребителей
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.JsonDeserializer
      auto-offset-reset: earliest          # начать с начала если нет offset
      enable-auto-commit: false           # ручной commit для надёжности
      properties:
        spring.json.trusted.packages: "com.example.dto"  # доверенные пакеты для десериализации
        max.poll.records: 100              # батч обработка

    listener:
      ack-mode: MANUAL_IMMEDIATE           # подтверждать вручную
      concurrency: 3                       # 3 потока = 3 партиции параллельно
      missing-topics-fatal: false          # не падать если топик не найден
✅ Best Practices
✅ Правильно
  • Использовать ключ сообщения для гарантии порядка
  • enable.auto.commit=false + ручной commit
  • Идемпотентная обработка сообщений (at-least-once)
  • Dead Letter Topic для необработанных сообщений
  • Retry с exponential backoff (@RetryableTopic)
  • Мониторинг consumer lag
  • Версионирование схем (Avro + Schema Registry)
  • Отдельные топики для разных типов событий
🚫 Ошибки
  • Не обрабатывать исключения в listener (сообщение теряется)
  • Слишком большие сообщения (>1MB) — лучше хранить данные отдельно
  • Использовать Kafka как БД (не для этого)
  • Один consumer на все партиции в группе
  • Не настраивать DLT — потеря проблемных сообщений
  • Игнорировать consumer lag — признак проблем
💻 Примеры кода
1. KafkaTemplate — отправка сообщений
Java
// ── DTO события
public record OrderCreatedEvent(
    String     orderId,
    Long       userId,
    BigDecimal amount,
    Instant    createdAt
) {}

// ── Producer сервис
@Service
@RequiredArgsConstructor
@Slf4j
public class OrderEventProducer {

    private final KafkaTemplate<String, OrderCreatedEvent> kafkaTemplate;

    private static final String TOPIC = "orders.created";

    // ── Простая отправка
    public void sendOrderCreated(OrderCreatedEvent event) {
        kafkaTemplate.send(TOPIC, event.orderId(), event) // topic, key, value
            .whenComplete((result, ex) -> {              // async callback
                if (ex != null) {
                    log.error("Ошибка отправки события orderId={}: {}",
                        event.orderId(), ex.getMessage());
                } else {
                    log.info("Событие отправлено: topic={}, partition={}, offset={}",
                        result.getRecordMetadata().topic(),
                        result.getRecordMetadata().partition(),
                        result.getRecordMetadata().offset());
                }
            });
    }

    // ── Отправка с явными метаданными
    public void sendToPartition(OrderCreatedEvent event, int partition) {
        ProducerRecord<String, OrderCreatedEvent> record =
            new ProducerRecord<>(
                TOPIC,                                // топик
                partition,                            // конкретная партиция
                event.orderId(),                   // ключ
                event                                 // значение
            );
        record.headers().add("source", "order-service".getBytes()); // заголовки
        kafkaTemplate.send(record);
    }

    // ── Синхронная отправка (блокирует поток — используй редко)
    public void sendSync(OrderCreatedEvent event) throws Exception {
        kafkaTemplate.send(TOPIC, event.orderId(), event)
            .get(5, TimeUnit.SECONDS);              // ждём подтверждения 5 секунд
    }
}
2. @KafkaListener — приём сообщений
Java
@Service
@RequiredArgsConstructor
@Slf4j
public class OrderEventConsumer {

    private final OrderService orderService;

    // ── Простой listener
    @KafkaListener(
        topics = "orders.created",              // топик или массив топиков
        groupId = "order-processor-group"       // группа потребителей
    )
    public void handleOrderCreated(OrderCreatedEvent event) { // автодесериализация
        log.info("Получено событие: orderId={}", event.orderId());
        orderService.processOrder(event);
    }

    // ── Listener с метаданными сообщения
    @KafkaListener(topics = "orders.created", groupId = "order-processor-group")
    public void handleWithMetadata(
            ConsumerRecord<String, OrderCreatedEvent> record,  // полное сообщение
            @Header(KafkaHeaders.RECEIVED_PARTITION) int partition,  // партиция
            @Header(KafkaHeaders.OFFSET) long offset) {         // offset
        log.info("topic={}, partition={}, offset={}, key={}",
            record.topic(), partition, offset, record.key());
        orderService.processOrder(record.value());
    }

    // ── Listener с ручным commit offset
    @KafkaListener(topics = "orders.created", groupId = "order-processor-group")
    public void handleWithManualCommit(
            ConsumerRecord<String, OrderCreatedEvent> record,
            Acknowledgment ack) {                 // для ручного ack
        try {
            orderService.processOrder(record.value());
            ack.acknowledge();                     // подтверждаем ПОСЛЕ успешной обработки
        } catch (Exception e) {
            log.error("Ошибка обработки: {}", e.getMessage());
            // НЕ подтверждаем — сообщение будет обработано повторно
        }
    }

    // ── Batch listener — обработка пачки сообщений
    @KafkaListener(
        topics = "orders.created",
        groupId = "order-batch-group",
        containerFactory = "batchKafkaListenerContainerFactory"  // отдельная фабрика
    )
    public void handleBatch(List<ConsumerRecord<String, OrderCreatedEvent>> records) {
        log.info("Получена пачка: {} сообщений", records.size());
        List<OrderCreatedEvent> events = records.stream()
            .map(ConsumerRecord::value)
            .toList();
        orderService.processBatch(events);        // batch insert в БД
    }

    // ── Несколько топиков
    @KafkaListener(topics = {"orders.created", "orders.updated"},
                   groupId = "audit-group")
    public void handleAudit(ConsumerRecord<String, ?> record) {
        log.info("Аудит: topic={}, key={}", record.topic(), record.key());
    }
}
3. @RetryableTopic и Dead Letter Topic
Java
@Service
@Slf4j
public class ResilientOrderConsumer {

    // ── @RetryableTopic — автоматические retry с backoff
    @RetryableTopic(
        attempts = "4",                            // 1 оригинал + 3 retry
        backoff = @Backoff(delay = 1000, multiplier = 2, maxDelay = 10000),
        // retry через 1s, 2s, 4s (exponential backoff)
        dltTopicSuffix = "-dlt",                  // суффикс DLT топика
        include = { OrderProcessingException.class } // только для этих исключений
    )
    @KafkaListener(topics = "orders.created", groupId = "order-resilient-group")
    public void handleOrder(OrderCreatedEvent event) {
        // Spring автоматически создаст топики:
        // orders.created-retry-0 (задержка 1s)
        // orders.created-retry-1 (задержка 2s)
        // orders.created-retry-2 (задержка 4s)
        // orders.created-dlt (Dead Letter Topic)
        orderService.processOrder(event);
    }

    // ── Обработчик Dead Letter Topic
    @DltHandler
    public void handleDlt(
            OrderCreatedEvent event,
            @Header(KafkaHeaders.RECEIVED_TOPIC) String topic,
            @Header(KafkaHeaders.EXCEPTION_MESSAGE) String error) {
        // Сообщение не обработалось после всех retry
        log.error("DLT: topic={}, orderId={}, error={}",
            topic, event.orderId(), error);
        // Сохраняем в БД для ручной обработки / алерт команде
        deadLetterService.save(event, topic, error);
    }
}
4. Конфигурация Kafka в Java
Java
@Configuration
@EnableKafka                                       // включаем Kafka
public class KafkaConfig {

    // ── Фабрика для batch listener
    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, ?>
            batchKafkaListenerContainerFactory(
            ConsumerFactory<String, ?> consumerFactory) {

        ConcurrentKafkaListenerContainerFactory<String, ?> factory =
            new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(consumerFactory);
        factory.setBatchListener(true);                // включить batch режим
        factory.getContainerProperties()
            .setAckMode(ContainerProperties.AckMode.MANUAL_IMMEDIATE);
        return factory;
    }

    // ── Создание топика программно
    @Bean
    public NewTopic ordersTopic() {
        return TopicBuilder.name("orders.created")  // имя топика
            .partitions(6)                          // 6 партиций
            .replicas(3)                             // фактор репликации
            .config(TopicConfig.RETENTION_MS_CONFIG,
                String.valueOf(7 * 24 * 60 * 60 * 1000L)) // хранить 7 дней
            .config(TopicConfig.COMPRESSION_TYPE_CONFIG, "snappy")
            .build();
    }

    @Bean
    public NewTopic ordersDltTopic() {
        return TopicBuilder.name("orders.created-dlt") // DLT топик
            .partitions(1)
            .replicas(3)
            .build();
    }
}
❓ Вопросы для собеседования
Что такое Consumer Group и зачем он нужен?
What is a Consumer Group in Kafka and why is it used?
Medium▼
✅ Ответ
Consumer Group — группа consumers, работающих совместно для обработки топика. Kafka распределяет партиции между consumers в группе: каждая партиция → ровно одному consumer. Это даёт горизонтальное масштабирование — добавил consumer, увеличил параллельность. Разные сервисы имеют разные группы и читают топик независимо (например, order-service и notification-service читают один топик).
Чем Kafka отличается от RabbitMQ?
What is the difference between Kafka and RabbitMQ?
Hard▼
✅ Ответ
Kafka: лог-ориентированный, сообщения хранятся до истечения retention (дни/недели), consumer сам контролирует offset, масштабируется до миллионов сообщений в секунду, подходит для event streaming и replay.
RabbitMQ: очередь — сообщение удаляется после доставки, broker контролирует доставку, routing через exchanges, проще для task queues, request-reply паттернов.
Что такое offset и зачем делать ручной commit?
What is an offset in Kafka and why use manual commit?
Medium▼
✅ Ответ
Offset — порядковый номер сообщения в партиции. Consumer сохраняет (коммитит) offset чтобы при перезапуске продолжить с того места. Авто-коммит коммитит offset через интервал времени — если приложение упало после коммита но до обработки — сообщение потеряно. Ручной commit (после успешной обработки) гарантирует at-least-once: сообщение обработается минимум раз.
Что такое Dead Letter Topic и зачем он нужен?
What is a Dead Letter Topic in Kafka?
Medium▼
✅ Ответ
Dead Letter Topic (DLT) — специальный топик куда попадают сообщения которые не удалось обработать после всех retry. Предотвращает бесконечный цикл повторов и блокировку очереди. Из DLT команда может вручную проверить и переотправить сообщения или разобраться с причиной ошибки. Spring Kafka автоматически создаёт DLT при использовании @RetryableTopic.
Как гарантировать порядок сообщений в Kafka?
How do you guarantee message ordering in Kafka?
Hard▼
✅ Ответ
Порядок гарантирован только внутри одной партиции. Чтобы сообщения одного объекта (например, одного заказа) шли по порядку — используй ключ сообщения (orderId). Kafka направит все сообщения с одним ключом в одну партицию. В группе одна партиция обрабатывается одним consumer → порядок сохранён. Нельзя гарантировать порядок между разными ключами в разных партициях.
