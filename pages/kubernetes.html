📌 Краткий конспект
Что такое Kubernetes
Kubernetes — система оркестрации контейнеров. Автоматически управляет: развёртыванием, масштабированием, самовосстановлением, балансировкой нагрузки. Запускает Docker контейнеры на кластере серверов (nodes).

🧩 Архитектура Kubernetes
Схема кластера
  ── CONTROL PLANE (Master) ──────────────────────────────────
  │  API Server    — центральная точка управления (kubectl → API)
  │  etcd          — хранилище состояния кластера
  │  Scheduler     — назначает Pod'ы на Node'ы
  │  Controller Manager — следит за желаемым состоянием

  ── WORKER NODES ────────────────────────────────────────────
  │
  ├── Node 1
  │   ├── kubelet      — агент на ноде, запускает Pod'ы
  │   ├── kube-proxy   — сетевые правила (iptables)
  │   └── Pods:
  │       ├── [app-pod-1]   { container: myapp:1.0 }
  │       └── [app-pod-2]   { container: myapp:1.0 }
  │
  └── Node 2
      └── Pods:
          └── [app-pod-3]   { container: myapp:1.0 }

  ── ОБЪЕКТЫ ──────────────────────────────────────────────────
  Deployment → ReplicaSet → Pod × 3
  Service → Pod × 3  (load balancing)
  Ingress → Service  (HTTP routing)
📦 Ключевые объекты
Pod — минимальная единица развёртывания ▼

Pod содержит один или несколько контейнеров, разделяющих сеть и хранилище. Pods — эфемерны: при перезапуске IP меняется. Не создавай Pod напрямую — используй Deployment.

Жизненный цикл Pod: Pending → Running → Succeeded/Failed/Unknown

Deployment — управление репликами и обновлениями ▼

Deployment описывает желаемое состояние: сколько реплик, какой образ, стратегия обновления. K8s автоматически поддерживает это состояние.

Стратегии обновления:
RollingUpdate (default) — постепенная замена Pod'ов, нет downtime.
Recreate — убить все, запустить новые. Есть downtime.

Service — стабильный сетевой адрес ▼

ConfigMap и Secret — конфигурация ▼

ConfigMap — несекретная конфигурация. Монтируется как файл или ENV переменные. Изменение без перезапуска Pod'а (если через volume).

Secret — секретные данные в base64. Типы: Opaque (произвольные), TLS, Docker registry. В продакшене используй HashiCorp Vault или AWS Secrets Manager — встроенный Secret хранится в etcd и не достаточно защищён.

HPA — Horizontal Pod Autoscaler ▼

HPA автоматически масштабирует число Pod'ов на основе метрик: CPU, memory, кастомных метрик. Требует Metrics Server в кластере.

При высокой нагрузке (CPU > 70%) → добавляет Pod'ы. При низкой → удаляет. Минимум/максимум реплик — настраивается.

📄 YAML манифесты
1. Deployment для Spring Boot приложения
YAML — deployment.yml
apiVersion: apps/v1                            # версия API
kind: Deployment                                # тип объекта
metadata:
  name: myapp                                   # имя Deployment'а
  namespace: production                         # namespace
  labels:
    app: myapp
    version: "1.0"
spec:
  replicas: 3                                   # 3 Pod'а
  selector:
    matchLabels:
      app: myapp                                # Pod'ы с label app=myapp
  strategy:
    type: RollingUpdate                         # обновлять постепенно
    rollingUpdate:
      maxSurge: 1                              # максимум +1 Pod при обновлении
      maxUnavailable: 0                        # ни один Pod не должен быть недоступен
  template:                                     # шаблон Pod'а
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: myapp
          image: myregistry/myapp:1.0          # образ приложения
          imagePullPolicy: Always               # всегда тянуть образ
          ports:
            - containerPort: 8080             # порт приложения

          # ── Переменные окружения из ConfigMap и Secret
          env:
            - name: SPRING_PROFILES_ACTIVE
              value: "prod"                    # прямое значение
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:               # из Secret'а
                  name: myapp-secrets
                  key: db-password
            - name: APP_NAME
              valueFrom:
                configMapKeyRef:            # из ConfigMap'а
                  name: myapp-config
                  key: app.name

          # ── Ограничения ресурсов
          resources:
            requests:                         # минимум для планировщика
              memory: "256Mi"
              cpu: "250m"                   # 250 millicores = 0.25 CPU
            limits:                           # максимум — контейнер не превысит
              memory: "512Mi"
              cpu: "500m"

          # ── Health checks
          livenessProbe:                      # перезапустить если приложение зависло
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 60          # ждать 60с после старта
            periodSeconds: 10               # проверять каждые 10с
            failureThreshold: 3              # 3 провала → перезапуск
          readinessProbe:                     # не слать трафик если не готов
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 5
          startupProbe:                       # даём время на медленный старт
            httpGet:
              path: /actuator/health
              port: 8080
            failureThreshold: 30             # 30 × 10s = 5 минут на старт
            periodSeconds: 10
2. Service, ConfigMap, Secret
YAML — service.yml + config.yml
# ── Service — балансировка трафика на Pod'ы
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
  namespace: production
spec:
  selector:
    app: myapp                              # выбирает Pod'ы с label app=myapp
  ports:
    - protocol: TCP
      port: 80                              # порт Service'а
      targetPort: 8080                     # порт Pod'а
  type: ClusterIP                          # доступен только внутри кластера
---
# ── ConfigMap — несекретная конфигурация
apiVersion: v1
kind: ConfigMap
metadata:
  name: myapp-config
  namespace: production
data:
  app.name: "My Application"             # ключ: значение
  app.version: "1.0.0"
  log.level: "INFO"
  application.yml: |                       # файл конфигурации как значение
    spring:
      datasource:
        url: jdbc:postgresql://postgres-service:5432/mydb
---
# ── Secret — секретные данные (base64)
apiVersion: v1
kind: Secret
metadata:
  name: myapp-secrets
  namespace: production
type: Opaque
data:                                     # значения в base64!
  db-password: cGFzc3dvcmQxMjM=           # echo -n "password123" | base64
  jwt-secret: bXlTZWNyZXRLZXk=
# stringData: — альтернатива (plaintext, K8s сам закодирует)
# stringData:
#   db-password: "password123"
3. Ingress и HPA
YAML — ingress.yml + hpa.yml
# ── Ingress — HTTP маршрутизация снаружи в кластер
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: myapp-ingress
  namespace: production
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:                                    # HTTPS
    - hosts:
        - api.myapp.com
      secretName: myapp-tls-secret        # TLS сертификат в Secret
  rules:
    - host: api.myapp.com                 # домен
      http:
        paths:
          - path: /api/v1                 # путь → сервис
            pathType: Prefix
            backend:
              service:
                name: myapp-service      # куда направить
                port:
                  number: 80
---
# ── HPA — авто-масштабирование по CPU
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp                           # масштабировать этот Deployment
  minReplicas: 2                          # минимум 2 Pod'а
  maxReplicas: 10                         # максимум 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70          # при CPU > 70% добавить Pod'ы
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80          # при Memory > 80% добавить Pod'ы
🌱 Spring Boot + Kubernetes
application.yml для K8s
YAML — application-prod.yml
# Конфигурация Spring Boot для запуска в K8s
spring:
  application:
    name: myapp
  datasource:
    url: ${SPRING_DATASOURCE_URL}           # из ENV (ConfigMap/Secret)
    username: ${SPRING_DATASOURCE_USERNAME}
    password: ${DB_PASSWORD}               # из Secret

# ── Actuator — нужен для probes K8s
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  endpoint:
    health:
      probes:
        enabled: true                     # включить /health/liveness и /health/readiness
      show-details: always
  health:
    livenessState:
      enabled: true
    readinessState:
      enabled: true

# ── Graceful shutdown — дождаться завершения запросов
server:
  shutdown: graceful

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s        # 30 секунд на завершение
💡 Liveness vs Readiness Probe
Liveness: жив ли Pod? Если нет → перезапустить. Путь: /actuator/health/liveness
Readiness: готов ли принимать трафик? Если нет → убрать из балансировки. Путь: /actuator/health/readiness
Startup: для медленно стартующих приложений — даёт время до начала liveness проверок.
✅ Best Practices
✅ Правильно
  • Всегда задавать resources.requests и limits
  • Настроить liveness и readiness probes
  • Graceful shutdown (server.shutdown=graceful)
  • Секреты через Secret, не ConfigMap
  • Использовать Namespace для изоляции
  • minReplicas >= 2 (нет single point of failure)
  • RollingUpdate стратегия с maxUnavailable=0
  • Конкретные теги образов, не :latest
🚫 Ошибки
  • Не задавать limits — Pod съест всю память Node'а
  • Использовать :latest тег — непредсказуемые обновления
  • Хранить секреты в plaintext в ConfigMap
  • Запускать под root (SecurityContext)
  • 1 реплика в продакшене — downtime при обновлении
  • Не настраивать probes — K8s не знает когда приложение готово
  • Огромные лимиты — неэффективное использование кластера
❓ Вопросы для собеседования
Чем Pod отличается от Deployment?
What is the difference between a Pod and a Deployment?
Easy▼
✅ Ответ
Pod — минимальная единица, один или несколько контейнеров. Эфемерный — при сбое не восстанавливается. Deployment — контроллер который управляет Pod'ами: поддерживает нужное число реплик, делает rolling update, откатывает при ошибке. В продакшене всегда создают Deployment, не Pod напрямую.
Зачем нужны liveness и readiness probes?
What are liveness and readiness probes in Kubernetes?
Medium▼
✅ Ответ
Liveness probe — проверяет что приложение живо. Если probe провалится → K8s перезапустит Pod. Защищает от deadlock'ов и зависших процессов.
Readiness probe — проверяет что приложение готово принимать трафик. Если не готово → K8s убирает Pod из балансировки Service. Во время rolling update — новый Pod получает трафик только когда readiness probe успешна.
Чем ConfigMap отличается от Secret?
What is the difference between ConfigMap and Secret?
Easy▼
✅ Ответ
ConfigMap — несекретная конфигурация: URLs, имена, настройки. Хранится в plaintext. Secret — секретные данные: пароли, токены, сертификаты. Хранится в base64 (не шифрование!). Secret не попадает в логи, монтируется через tmpfs. В продакшене секреты лучше хранить в HashiCorp Vault или AWS Secrets Manager и инжектировать в K8s Secret динамически.
Как работает rolling update в Kubernetes?
How does a rolling update work in Kubernetes?
Medium▼
✅ Ответ
Rolling update постепенно заменяет старые Pod'ы новыми без downtime. При maxUnavailable=0: сначала создаётся новый Pod (+1), ждёт readiness probe, затем удаляется старый (-1). Процесс повторяется для каждой реплики. Если новый Pod не прошёл probe — обновление останавливается, можно откатить через kubectl rollout undo.
Зачем задавать resources.requests и limits?
Why should you set resource requests and limits in Kubernetes?
Medium▼
✅ Ответ
Requests — минимум ресурсов. Scheduler использует для размещения Pod'а на подходящей Node. Limits — максимум. Контейнер не может превысить. Без limits — Pod может съесть всю память Node'а → OOMKill других Pod'ов → нестабильность кластера. Без requests — Scheduler не может правильно спланировать размещение. Правило: requests = 50% limits для Java (JVM резервирует память заранее).
