Java Core OOP SOLID

4 столпа ООП + SOLID принципы + interface vs abstract class. Без этого не проходит ни одно собеседование на Java-разработчика.

💡 Главное правило
Предпочитай композицию наследованию. Наследование — «является» (is-a). Композиция — «содержит» (has-a). Глубокая иерархия наследования хрупка и сложна в поддержке.
🔒 Инкапсуляция

Объединяем данные (поля) и методы работы с ними в одном классе, скрывая детали реализации от внешнего мира. Поля — private, доступ — через публичные методы.

✅ Зачем нужна
Контролируем изменение состояния объекта. Можно добавить валидацию в setter. Внутреннее представление можно менять, не ломая внешний API. Защита от некорректных данных.

🧬 Наследование

Дочерний класс наследует поля и методы родителя (extends). Java поддерживает только одиночное наследование классов, но множественное — через интерфейсы.

⚠️ Проблема хрупкого базового класса
Изменение родительского класса может сломать все дочерние. Поэтому глубокое наследование (более 2–3 уровней) — антипаттерн. Предпочитай композицию.
✅ Когда использовать наследование
  • Дочерний — действительно «является» родительским (is-a)
  • Иерархия глубиной 1–2 уровня
  • Переиспользование реальной логики родителя
  • Пример: Animal → Dog, Cat
🚫 Когда НЕ использовать
  • Только ради переиспользования кода (бери композицию)
  • Если нужно наследовать от нескольких классов
  • Глубокая иерархия 4+ уровней
  • Пример: Stack extends Vector — классический антипаттерн
🎭 Полиморфизм

«Много форм» — один и тот же код работает с объектами разных типов. Два вида:

ВидКакКогда решаетсяПример
Runtime (динамический)@OverrideВо время выполнения (JVM)animal.sound() → Dog или Cat
Compile-time (статический)Overloading (перегрузка)Во время компиляцииprint(int) vs print(String)
💡 Dynamic Dispatch
JVM вызывает метод на основе фактического типа объекта, а не типа переменной. Это ключевой механизм полиморфизма времени выполнения.
🌫 Абстракция

Показываем пользователю класса только то, что ему нужно знать (ЧТО делает), скрывая детали реализации (КАК делает). Реализуется через abstract class и interface.

✅ Пример из жизни
Ты знаешь что метод repository.save(user) сохраняет пользователя. Тебе не важно, как именно — SQL INSERT, NoSQL, файл. Это и есть абстракция.

✅ Interface — когда
  • Определяешь контракт (что умеет объект)
  • Нужно множественное «наследование»
  • Слабая связность (loose coupling)
  • Пример: Runnable, Comparable, Serializable
✅ Abstract — когда
  • Есть общая логика для группы классов
  • Нужны конструкторы или нестатические поля
  • Template Method паттерн
  • Пример: AbstractList, HttpServlet
🏛 SOLID Принципы
S  Single Responsibility — один класс, одна ответственность ▼

Каждый класс должен иметь только одну причину для изменения. Если класс делает слишком много — его сложно тестировать, изменять и понимать.

Признак нарушения: класс называется UserManager, DataProcessor — широкое название намекает на множество обязанностей.

🚫 Плохо
Класс User содержит логику: сохранение в БД, отправку email, форматирование JSON.
✅ Хорошо
User — только данные. UserRepository — сохранение. EmailService — письма. UserMapper — маппинг.
O  Open/Closed — открыт для расширения, закрыт для изменения ▼

Добавляй новую функциональность через расширение (новые классы/методы), а не изменение существующего кода. Существующий рабочий код не трогаем.

Реализация: интерфейсы, абстрактные классы, стратегии, декораторы.

🚫 Плохо
Каждый новый тип скидки — if/else if в методе расчёта цены. Добавление нового типа ломает существующий метод.
✅ Хорошо
Интерфейс DiscountStrategy + отдельный класс для каждой скидки. Новая скидка = новый класс без изменения существующего кода.
L  Liskov Substitution — подтип заменяем базовым типом ▼

Объекты дочернего класса должны корректно заменять объекты родительского класса без изменения поведения программы.

Нарушение: метод дочернего класса кидает исключение там, где родитель работал нормально, или требует более строгих предусловий.

🚫 Классический антипример
Square extends Rectangle: у квадрата нельзя независимо менять ширину и высоту — нарушается поведение Rectangle.
✅ Хорошо
Общий интерфейс Shape с методом area(). Rectangle и Square реализуют его независимо.
I  Interface Segregation — много маленьких интерфейсов ▼

Клиент не должен зависеть от методов, которые не использует. Лучше много маленьких специализированных интерфейсов, чем один «толстый».

🚫 Плохо
Интерфейс Animal с методами fly(), swim(), run(). Класс Dog вынужден реализовывать fly().
✅ Хорошо
Отдельные интерфейсы Flyable, Swimmable, Runnable. Класс реализует только нужные.
D  Dependency Inversion — зависи от абстракций, не от конкретики ▼

Модули высокого уровня не зависят от модулей низкого уровня — оба зависят от абстракций (интерфейсов). Это основа Dependency Injection в Spring.

🚫 Плохо
UserService создаёт new MySQLUserRepository() напрямую — жёсткая связь с конкретной реализацией БД.
✅ Хорошо
UserService принимает UserRepository (интерфейс) через конструктор. Spring сам подставит нужную реализацию.
💻 Примеры кода
1. Все 4 принципа ООП в одном примере
Java
// ── АБСТРАКЦИЯ: интерфейс описывает ЧТО умеет делать, скрывая КАК
public interface PaymentService {
    void pay(double amount);         // только контракт, без реализации
    boolean supports(String method); // знаем ЧТО, не знаем КАК
}

// ── ИНКАПСУЛЯЦИЯ: поля скрыты, доступ через методы
public abstract class BasePayment implements PaymentService {
    private String merchantId;       // private — снаружи не видно
    private double commission;       // изменить можно только через метод

    public BasePayment(String merchantId, double commission) {
        this.merchantId = merchantId;
        this.commission = commission;
    }

    protected double getCommission() { // protected — только для подклассов
        return commission;
    }

    protected String getMerchantId() {
        return merchantId;
    }
}

// ── НАСЛЕДОВАНИЕ: CardPayment расширяет BasePayment
public class CardPayment extends BasePayment {

    public CardPayment() {
        super("MERCHANT_CARD", 0.015);   // вызываем конструктор родителя
    }

    @Override
    public void pay(double amount) {    // ПОЛИМОРФИЗМ: своя реализация метода
        double fee = amount * getCommission(); // используем protected метод
        System.out.printf("💳 Карта: %.2f + комиссия %.2f%n", amount, fee);
    }

    @Override
    public boolean supports(String method) {
        return "CARD".equalsIgnoreCase(method); // equalsIgnoreCase безопаснее
    }
}

public class CryptoPayment extends BasePayment {

    public CryptoPayment() {
        super("MERCHANT_CRYPTO", 0.005);  // меньше комиссия у крипты
    }

    @Override
    public void pay(double amount) {    // другая реализация — полиморфизм
        double fee = amount * getCommission();
        System.out.printf("₿ Крипта: %.2f + комиссия %.2f%n", amount, fee);
    }

    @Override
    public boolean supports(String method) {
        return "CRYPTO".equalsIgnoreCase(method);
    }
}

// ── ПОЛИМОРФИЗМ в действии: один тип, разное поведение
List<PaymentService> services = List.of(
    new CardPayment(),
    new CryptoPayment()
);

String method = "CARD";
services.stream()
    .filter(s -> s.supports(method))  // найти подходящий сервис
    .findFirst()
    .ifPresent(s -> s.pay(1000.0));   // JVM сам выберет нужный метод
// Вывод: 💳 Карта: 1000.00 + комиссия 15.00
2. Interface — default методы и функциональные интерфейсы
Java
// ── Интерфейс с default методом (Java 8+)
public interface Printable {
    String getContent();                  // абстрактный — обязан реализовать

    default void print() {               // default — реализация по умолчанию
        System.out.println(getContent()); // можно переопределить, но не обязательно
    }

    static Printable of(String text) {   // static метод в интерфейсе (Java 8+)
        return () -> text;                  // лямбда — реализация Printable
    }
}

// ── Множественная реализация интерфейсов
public class Report implements Printable, Comparable<Report> {
    private final String title;
    private final int priority;

    public Report(String title, int priority) {
        this.title = title;
        this.priority = priority;
    }

    @Override
    public String getContent() {
        return "Отчёт: " + title;            // реализация из Printable
    }

    @Override
    public int compareTo(Report other) {  // реализация из Comparable
        return Integer.compare(this.priority, other.priority);
    }
}

// ── Функциональный интерфейс + лямбда (Java 8+)
@FunctionalInterface                       // ровно 1 абстрактный метод
public interface Validator<T> {
    boolean validate(T value);            // единственный абстрактный метод

    default Validator<T> and(Validator<T> other) { // комбинирование
        return value -> this.validate(value) && other.validate(value);
    }
}

// Использование лямбдами
Validator<String> notEmpty = s -> !s.isBlank();     // лямбда = анонимный класс
Validator<String> notTooLong = s -> s.length() < 100; // ещё один валидатор
Validator<String> combined = notEmpty.and(notTooLong);  // комбинируем через default

System.out.println(combined.validate("Hello")); // true
System.out.println(combined.validate(""));       // false
3. SOLID — Dependency Inversion + Spring DI
Java
// ── D: Dependency Inversion — зависим от абстракции
public interface NotificationService {  // абстракция (интерфейс)
    void send(String to, String message);
}

@Service                                    // Spring управляет этим бином
public class EmailNotificationService implements NotificationService {
    @Override
    public void send(String to, String message) {
        // реализация отправки email
        System.out.println("📧 Email → " + to + ": " + message);
    }
}

@Service
public class SmsNotificationService implements NotificationService {
    @Override
    public void send(String to, String message) {
        System.out.println("📱 SMS → " + to + ": " + message);
    }
}

// ── UserService зависит от ИНТЕРФЕЙСА, а не от конкретного класса
@Service
public class UserService {

    private final NotificationService notificationService; // интерфейс!

    // Spring сам подставит нужную реализацию через конструктор (рекомендуется)
    public UserService(NotificationService notificationService) {
        this.notificationService = notificationService;    // DI через конструктор
    }

    public void registerUser(String email) {
        // ... сохранение пользователя ...
        notificationService.send(email, "Добро пожаловать!"); // полиморфный вызов
        // Не знаем и не должны знать: Email или SMS
    }
}

// ── Если реализаций несколько — используем @Qualifier
@Service
public class OrderService {
    private final NotificationService notificationService;

    public OrderService(
        @Qualifier("emailNotificationService") // выбираем конкретную реализацию
        NotificationService notificationService) {
        this.notificationService = notificationService;
    }
}
4. Полиморфизм — overriding vs overloading
Java
// ── Overriding (переопределение) — Runtime полиморфизм
class Animal {
    public String sound() { return "..."; }   // базовый метод
}
class Dog extends Animal {
    @Override                                      // аннотация помогает компилятору проверить
    public String sound() { return "Woof"; }  // своя реализация
}
class Cat extends Animal {
    @Override
    public String sound() { return "Meow"; }
}

Animal a1 = new Dog();   // тип переменной — Animal
Animal a2 = new Cat();   // фактический тип — Cat
System.out.println(a1.sound());   // "Woof" — JVM смотрит на РЕАЛЬНЫЙ тип
System.out.println(a2.sound());   // "Meow" — dynamic dispatch

// ── Overloading (перегрузка) — Compile-time полиморфизм
class Printer {
    public void print(String text)  { System.out.println("String: " + text); }
    public void print(int number)   { System.out.println("Int: " + number); }
    public void print(String s, int n) { System.out.println(s + ": " + n); }
    // Компилятор выбирает метод по типу аргументов ещё при компиляции
}

// ── instanceof + pattern matching (Java 16+)
void describe(Animal animal) {
    if (animal instanceof Dog dog) {       // pattern matching — кастинг сразу
        System.out.println("Собака: " + dog.sound());
    } else if (animal instanceof Cat cat) {
        System.out.println("Кошка: " + cat.sound());
    }
}

// ── switch expression с sealed классами (Java 17+)
sealed interface Shape permits Circle, Rectangle {}  // только эти реализации!
record Circle(double radius) implements Shape {}
record Rectangle(double w, double h) implements Shape {}

double area(Shape shape) {
    return switch (shape) {                         // exhaustive — все случаи покрыты
        case Circle c    -> Math.PI * c.radius() * c.radius();
        case Rectangle r -> r.w() * r.h();
    };
}
❓ Вопросы для собеседования
Расскажи о 4 принципах ООП
Explain the 4 principles of OOP
Easy▼
✅ Ответ
Инкапсуляция — скрываем внутреннее состояние, открываем только нужный API (private поля + public методы).
Наследование — дочерний класс расширяет родительский (extends), переиспользует код.
Полиморфизм — один интерфейс, разные реализации. Override (runtime) и Overload (compile-time).
Абстракция — показываем ЧТО делает объект (интерфейс/abstract), скрываем КАК.
🔥 Сильный ответ
Добавь пример из реального проекта: «В Spring Security есть интерфейс UserDetailsService — это абстракция. Я реализую его в своём классе — это полиморфизм. Поле password — private и меняется только через метод — это инкапсуляция. Мой класс может extends BaseUserService — это наследование.»
Чем отличается interface от abstract class?
What is the difference between interface and abstract class?
Medium▼
✅ Ответ
Interface: множественная реализация, нет конструктора, нет нестатических полей, описывает контракт (что умеет). С Java 8 — default и static методы.
Abstract class: одиночное наследование, есть конструктор, может иметь состояние (поля), частичная реализация, шаблонный метод (Template Method).
🔥 Добавить
«Если нужно только описать контракт — интерфейс. Если есть общая логика и состояние — abstract. В современном Java с default методами граница размылась, но abstract лучше когда нужен конструктор или protected поля.»
Что такое SOLID? Расскажи каждый принцип
What is SOLID? Explain each principle
Hard▼
✅ Ответ
S — Single Responsibility: один класс = одна причина меняться.
O — Open/Closed: расширяем новым кодом, не правим старый.
L — Liskov Substitution: подтип работает везде где работает базовый тип.
I — Interface Segregation: много мелких интерфейсов лучше одного большого.
D — Dependency Inversion: зависи от интерфейсов, не от конкретных классов.
🔥 Пример для D
«В Spring я инжектирую UserRepository как интерфейс, а не JpaUserRepository напрямую. Это DIP — могу заменить реализацию без изменения сервиса. В тестах подменяю заглушкой (mock).»
Почему предпочитают композицию наследованию?
Why is composition preferred over inheritance?
Medium▼
✅ Ответ
Наследование создаёт жёсткую связь: изменение родителя ломает детей (хрупкий базовый класс). Кроме того, Java не поддерживает множественное наследование. Композиция гибче — можно комбинировать поведение, менять реализацию во время выполнения (Strategy паттерн), легче тестировать (можно подменить поле-мок).
Что такое полиморфизм времени выполнения (dynamic dispatch)?
What is runtime polymorphism / dynamic dispatch?
Medium▼
✅ Ответ
JVM определяет, какой метод вызвать, не по типу переменной, а по фактическому типу объекта во время выполнения. Например, переменная типа Animal может ссылаться на Dog, и вызов sound() выполнит метод Dog.sound(), а не Animal.sound().
⚠️ Ошибка кандидата
Путают с overloading — перегрузка решается на этапе компиляции (по типу аргументов), а не во время выполнения.
