📌 Краткий конспект

Главное правило JPA-связей
В бидирекциональной связи всегда есть owning side (владелец, хранит FK в БД) и inverse side (зеркало, управляется через mappedBy). Hibernate слушает только owning side при сохранении!
СвязьОписаниеГде FK в БД?Частота использования
@ManyToOneМного → ОдинВ таблице "многих"⭐⭐⭐⭐⭐ (самая частая)
@OneToManyОдин → МногоВ таблице "многих" (через mappedBy)⭐⭐⭐⭐
@OneToOneОдин → ОдинВ любой из таблиц⭐⭐
@ManyToManyМного → МногоВ промежуточной таблице (@JoinTable)⭐⭐

🔗 @ManyToOne & @OneToMany

Пример: Department (1) ↔ Employee (N)

Логика: Один отдел содержит много сотрудников. Внешний ключ (department_id) хранится в таблице employees.

Правило: @ManyToOne — owning side (владелец). @OneToMany(mappedBy = "...") — inverse side (зеркало).

Department.java (Inverse Side)
@Entity
@Table(name = "departments")
public class Department {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    /*
     * @OneToMany — обратная сторона связи.
     * mappedBy = "department" указывает, что владелец связи 
     * находится в поле "department" класса Employee.
     * 
     * ⚠️ fetch = LAZY по умолчанию для коллекций.
     * ⚠️ cascade = {} по умолчанию (не каскадирует операции).
     */
    @OneToMany(mappedBy = "department", 
              cascade = CascadeType.ALL,  // Опционально: каскад на сотрудников
              orphanRemoval = true)      // Опционально: удалять сотрудников при отвязке
    private List<Employee> employees = new ArrayList<>();
}
Employee.java (Owning Side)
@Entity
@Table(name = "employees")
public class Employee {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String firstName;

    /*
     * @ManyToOne — ВЛАДЕЛЕЦ связи (owning side).
     * Именно здесь создаётся столбец department_id в БД.
     * 
     * @JoinColumn настраивает FK:
     * name = "department_id" — имя столбца в БД
     * nullable = false       — FK обязателен
     * 
     * ⚠️ fetch = EAGER по умолчанию для @ManyToOne (лучше менять на LAZY!)
     */
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id", nullable = false)
    private Department department;
}
⚠️ Важно: Двусторонняя синхронизация
При добавлении сотрудника в отдел нужно обновлять обе стороны:
employee.setDepartment(dept);
dept.getEmployees().add(employee);
Иначе Hibernate сохранит FK, но в памяти объекта Department список останется пустым до перезагрузки.

🔗 @OneToOne

Пример: User (1) ↔ UserProfile (1)

Логика: У каждого пользователя ровно один профиль. FK можно разместить в любой таблице. Обычно FK кладут в "дочернюю" таблицу (user_profiles.user_id).

User.java (Owning Side)
@Entity
@Table(name = "users")
public class User {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String username;

    /*
     * @OneToOne — владелец связи. FK будет в таблице profiles.
     * mappedBy указывает на поле "user" в классе UserProfile.
     */
    @OneToOne(mappedBy = "user", 
              cascade = CascadeType.ALL,
              fetch = FetchType.LAZY)
    private UserProfile profile;
}
UserProfile.java (Inverse Side / Owning)
@Entity
@Table(name = "user_profiles")
public class UserProfile {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String bio;

    /*
     * Владелец связи! Здесь создаётся столбец user_id.
     * unique = true гарантирует, что один user_id не повторится → 1:1
     */
    @OneToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id", unique = true, nullable = false)
    private User user;
}

🔗 @ManyToMany

Пример: Student (N) ↔ Course (N)

Логика: Студент ходит на много курсов, курс посещают много студентов. В БД создаётся промежуточная таблица (например, student_courses).

Важно: Одна сторона должна владеть связью и описывать @JoinTable. Вторая сторона использует mappedBy.

Student.java (Owning Side)
@Entity
@Table(name = "students")
public class Student {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    /*
     * @ManyToMany — владелец связи. Создаёт промежуточную таблицу.
     * 
     * @JoinTable настраивает связь N:N:
     * name = "student_courses"     — имя связующей таблицы
     * joinColumns                  — FK к ТЕКУЩЕЙ таблице (students)
     * inverseJoinColumns           — FK к СВЯЗАННОЙ таблице (courses)
     */
    @ManyToMany(fetch = FetchType.LAZY, cascade = CascadeType.PERSIST)
    @JoinTable(
        name = "student_courses",
        joinColumns = @JoinColumn(name = "student_id"),
        inverseJoinColumns = @JoinColumn(name = "course_id")
    )
    private Set<Course> courses = new HashSet<>();
}
Course.java (Inverse Side)
@Entity
@Table(name = "courses")
public class Course {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;

    /*
     * Обратная сторона. mappedBy указывает на поле "courses" в Student.
     * Промежуточная таблица уже описана там, здесь дублировать не нужно!
     */
    @ManyToMany(mappedBy = "courses", fetch = FetchType.LAZY)
    private Set<Student> students = new HashSet<>();
}
💡 Как выглядит БД?
students (id, name)
courses (id, title)
student_courses (student_id, course_id) ← Промежуточная таблица с составным PK

🔍 Разбор ключевых аннотаций

@JoinColumn(name = "...")

Пояснение
/*
 * Определяет столбец ВНЕШНЕГО КЛЮЧА (Foreign Key) в БД.
 * Ставится на ОВЛАДЕВАЮЩЕЙ стороне (@ManyToOne, @OneToOne).
 * 
 * Атрибуты:
 * name         — имя столбца FK в таблице (по умолчанию: имя_поля_id)
 * referencedColumnName — имя PK в связанной таблице (по умолчанию: id)
 * nullable     — можно ли оставлять FK пустым (по умолчанию: true)
 * unique       — уникален ли FK (для @OneToOne = true)
 */
@JoinColumn(name = "dept_id", nullable = false)

@InverseJoinColumn(name = "...")

Пояснение
/*
 * Используется ТОЛЬКО внутри @JoinTable для связи @ManyToMany.
 * Указывает FK, который ссылается на СВЯЗАННУЮ (inverse) таблицу.
 * 
 * В @JoinTable есть ДВА join-столбца:
 * 1. joinColumns        → FK к текущей сущности
 * 2. inverseJoinColumns → FK к связанной сущности
 */
@JoinTable(
    name = "user_roles",
    joinColumns = @JoinColumn(name = "user_id"),           // FK к User
    inverseJoinColumns = @JoinColumn(name = "role_id")  // FK к Role
)

mappedBy = "fieldName"

Пояснение
/*
 * mappedBy объявляет ОБРАТНУЮ (inverse) сторону связи.
 * Говорит Hibernate: "Не создавай новый FK, используй тот, 
 * что уже описан в поле 'fieldName' связанного класса".
 * 
 * Правило: mappedBy ставится там, где НЕТ @JoinColumn.
 * Если поставить mappedBy на обеих сторонах → ошибка при запуске.
 * Если не поставить ни на одной → Hibernate создаст ДВА FK (лишняя таблица/столбец).
 */
@OneToMany(mappedBy = "department")  // "department" — поле в Employee

cascade = CascadeType.???

Пояснение
/*
 * cascade определяет, какие операции "перетекают" на связанные сущности.
 * По умолчанию: NONE (ничего не каскадирует).
 * 
 * Варианты:
 * PERSIST   — при save() владельца → save() связанных
 * MERGE     — при merge() владельца → merge() связанных
 * REMOVE    — при delete() владельца → delete() связанных (ОСТОРОЖНО!)
 * REFRESH   — при refresh() владельца → refresh() связанных
 * ALL       — все вышеперечисленные (часто используется с @OneToMany)
 * 
 * ⚠️ cascade REMOVE на @ManyToOne почти никогда не нужен!
 * (Удаление отдела не должно удалять всех сотрудников!)
 */
@OneToMany(cascade = CascadeType.ALL)

fetch = FetchType.??? (LAZY vs EAGER)

Пояснение
/*
 * LAZY  — загружать связанные данные ТОЛЬКО при первом обращении.
 *         (Стандарт для коллекций @OneToMany, @ManyToMany)
 * 
 * EAGER — загружать ВСЕГДА вместе с основной сущностью (один JOIN-запрос).
 *         (Стандарт для @ManyToOne, @OneToOne, но лучше менять на LAZY!)
 * 
 * ⚠️ Проблема N+1: если оставить EAGER на коллекциях, Hibernate 
 *    выполнит 1 запрос для списка + N запросов для каждой связи!
 *    Решение: всегда LAZY + JOIN FETCH в JPQL или @EntityGraph.
 */
@OneToMany(fetch = FetchType.LAZY)   // ✅ Правильно
@ManyToOne(fetch = FetchType.LAZY)   // ✅ Рекомендуется

✅ Best & ⚠️ Anti Practices

✅ Best Practices
  • Всегда используй LAZY для коллекций и ManyToOne
  • Синхронизируй обе стороны связи в коде (add/remove helper methods)
  • Используй @JoinTable явно для ManyToMany, не полагайся на дефолтные имена
  • Избегай cascade = REMOVE на @ManyToOne и @ManyToMany
  • Возвращай DTO/Response, а не Entity, чтобы избежать LazyInitializationException и циклов в JSON
  • Используй orphanRemoval = true только для композиций (владелец полностью управляет жизненным циклом)
  • Для сложных выборок используй JPQL с JOIN FETCH или Spring Data @EntityGraph
⚠️ Anti Patterns
  • ❌ Оставлять EAGER на @OneToMany/ManyToMany (приведёт к N+1 и OutOfMemory)
  • ❌ Забывать обновлять inverse side (данные в БД сохранятся, но в памяти будет рассинхрон)
  • ❌ Ставить mappedBy на обеих сторонах (Hibernate не поймёт, где FK)
  • ❌ Использовать cascade = ALL на @ManyToMany (удаление студента удалит курсы!)
  • ❌ Сериализовать Entity в JSON без @JsonIgnore или DTO (бесконечная рекурсия Jackson)
  • ❌ Писать бизнес-логику внутри Entity (нарушение SRP, сложно тестировать)
  • ❌ Загружать огромные коллекции в память вместо пагинации

❓ Вопросы для собеседования

В чём разница между owning side и inverse side?
Difference between owning and inverse side?
Medium ▼
✅ Ответ
Owning side (владелец) — сторона, которая физически хранит внешний ключ (FK) в БД. Именно изменения на этой стороне Hibernate отслеживает для генерации INSERT/UPDATE. Inverse side (зеркало) — объявляется через mappedBy, не хранит FK, служит только для навигации в объектной модели. Hibernate игнорирует изменения на inverse side при сохранении.
Что такое N+1 проблема и как её решить?
What is N+1 problem and how to fix it?
Hard ▼
✅ Ответ
Проблема возникает при LAZY загрузке коллекций в цикле: 1 запрос на получение списка сущностей + N запросов на загрузку связей для каждой сущности. Решения: 1) JOIN FETCH в JPQL (SELECT d FROM Department d JOIN FETCH d.employees), 2) @EntityGraph в Spring Data, 3) Batch fetching (@BatchSize), 4) DTO-проекции вместо загрузки Entity.
Зачем нужен mappedBy и что будет, если его забыть?
Why mappedBy? What happens if omitted?
Easy ▼
✅ Ответ
mappedBy указывает Hibernate, что связь уже описана на другой стороне и не нужно создавать дополнительный FK. Если забыть mappedBy в бидирекциональной связи, Hibernate создаст две отдельные связи (два FK или лишнюю промежуточную таблицу), что приведёт к дублированию данных и ошибкам целостности.
В чём разница между cascade = REMOVE и orphanRemoval = true?
Difference between cascade REMOVE and orphanRemoval?
Hard ▼
✅ Ответ
cascade = REMOVE удаляет связанные сущности только при удалении родителя. orphanRemoval = true удаляет "сирот" — связанные сущности, которые были отвязаны от родителя (например, department.getEmployees().remove(emp)), даже если родитель не удаляется. orphanRemoval подразумевает cascade = ALL и используется только для композиций (полное владение жизненным циклом).
