📌 Краткий конспект
Зачем Docker Compose
Docker Compose — инструмент для запуска многоконтейнерных приложений одной командой. Вместо 10 команд docker run с параметрами — один файл docker-compose.yml и команда docker compose up.
КлючОписание
servicesКонтейнеры — основная секция
volumesИменованные volumes для данных
networksПользовательские сети
configsКонфигурационные файлы (Swarm)
secretsСекреты (Swarm)
💡 Версии Compose
Начиная с Docker Compose V2 используй docker compose (без дефиса). Файл docker-compose.yml без поля version — современный подход. Поле version: "3.8" устарело но всё ещё работает.

⚙️ depends_on и healthcheck

depends_on управляет порядком запуска сервисов. Без condition — ждёт только старта контейнера, не готовности приложения. С condition: service_healthy — ждёт пока healthcheck не вернёт healthy.

conditionЖдёт
service_startedКонтейнер запустился (default)
service_healthyHealthcheck вернул healthy
service_completed_successfullyКонтейнер завершился с кодом 0
⚠️ depends_on не гарантирует готовность приложения
PostgreSQL контейнер может быть запущен, но СУБД ещё инициализируется. Используй condition: service_healthy с healthcheck — или добавь retry логику в приложение (spring.datasource.hikari.connection-timeout).

🔑 Переменные окружения
environment: (inline)
  • Прямо в docker-compose.yml
  • Простые значения
  • Попадают в Git (не для секретов!)
  • Можно ссылаться на переменные хоста: DB_PASS=${DB_PASS}
env_file: (файл)
  • Отдельный .env файл
  • Можно добавить в .gitignore
  • Удобно для секретов
  • Синтаксис: KEY=VALUE (без кавычек)
🔐 Никогда не храни секреты в docker-compose.yml
Пароли БД, JWT секреты, API ключи — только в .env файле который добавлен в .gitignore. В docker-compose.yml ссылайся: POSTGRES_PASSWORD=${POSTGRES_PASSWORD}.

🎭 Profiles — разные конфигурации

Profiles позволяют включать/выключать сервисы в зависимости от окружения. Сервис без profiles — запускается всегда. Сервис с profiles: ["dev"] — только с --profile dev.

Без profiles (всегда)
  • app (Spring Boot)
  • db (PostgreSQL)
  • redis (Redis)
С profiles (по необходимости)
  • pgadmin → profiles: ["dev"]
  • mailhog → profiles: ["dev"]
  • prometheus → profiles: ["monitoring"]
💻 Примеры кода
1. Полный docker-compose.yml для Spring Boot приложения
YAML — docker-compose.yml
# docker-compose.yml — Spring Boot + PostgreSQL + Redis

services:

  # ════════════════════════════════
     Spring Boot приложение
     ════════════════════════════════
  app:
    build:
      context: .                           # Dockerfile в текущей директории
      dockerfile: Dockerfile               # имя файла (по умолчанию Dockerfile)
    container_name: myapp
    ports:
      - "8080:8080"                       # хост:контейнер
    environment:
      # Spring профиль
      - SPRING_PROFILES_ACTIVE=docker
      # Подключение к БД (имя сервиса = hostname в сети Compose!)
      - SPRING_DATASOURCE_URL=jdbc:postgresql://db:5432/mydb
      - SPRING_DATASOURCE_USERNAME=myuser
      - SPRING_DATASOURCE_PASSWORD=${DB_PASSWORD}  # из .env файла
      # Redis
      - SPRING_DATA_REDIS_HOST=redis
      - SPRING_DATA_REDIS_PORT=6379
      # JVM параметры
      - JAVA_OPTS=-XX:MaxRAMPercentage=75.0 -XX:+UseG1GC
    depends_on:
      db:
        condition: service_healthy         # ждём пока БД готова!
      redis:
        condition: service_started
    networks:
      - backend-net
    restart: unless-stopped
    deploy:
      resources:
        limits:
          memory: 512m                     # максимум памяти
          cpus: "1.0"                      # максимум CPU
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:8080/actuator/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 60s                   # дать время на запуск Spring Boot

  # ════════════════════════════════
     PostgreSQL
     ════════════════════════════════
  db:
    image: postgres:16-alpine              # alpine = меньший размер
    container_name: myapp-db
    ports:
      - "5432:5432"                       # открываем для локальной разработки
    environment:
      - POSTGRES_DB=mydb
      - POSTGRES_USER=myuser
      - POSTGRES_PASSWORD=${DB_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data   # данные сохраняются между перезапусками
      - ./init-scripts:/docker-entrypoint-initdb.d  # SQL скрипты инициализации
    networks:
      - backend-net
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U myuser -d mydb"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s

  # ════════════════════════════════
     Redis
     ════════════════════════════════
  redis:
    image: redis:7-alpine
    container_name: myapp-redis
    ports:
      - "6379:6379"
    command: redis-server --requirepass ${REDIS_PASSWORD} --maxmemory 256mb --maxmemory-policy allkeys-lru
    volumes:
      - redisdata:/data                   # персистентность Redis
    networks:
      - backend-net
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "redis-cli", "-a", "${REDIS_PASSWORD}", "ping"]
      interval: 10s
      timeout: 3s
      retries: 3

  # ════════════════════════════════
     PgAdmin (только dev профиль)
     ════════════════════════════════
  pgadmin:
    image: dpage/pgadmin4:8
    container_name: myapp-pgadmin
    profiles:
      - dev                               # только с --profile dev
    ports:
      - "5050:80"
    environment:
      - PGADMIN_DEFAULT_EMAIL=admin@admin.com
      - PGADMIN_DEFAULT_PASSWORD=${PGADMIN_PASSWORD}
    depends_on:
      - db
    networks:
      - backend-net
    restart: unless-stopped

# ════════════════════════════════
   Именованные volumes
   ════════════════════════════════
volumes:
  pgdata:                                 # Docker сам управляет хранением
    driver: local
  redisdata:
    driver: local

# ════════════════════════════════
   Сети
   ════════════════════════════════
networks:
  backend-net:
    driver: bridge                        # изолированная bridge сеть

3. Отдельные файлы для разных окружений
YAML — docker-compose.override.yml (dev)
# docker-compose.override.yml — автоматически мержится с docker-compose.yml
# используется для локальной разработки

services:
  app:
    build:
      target: builder                     # стадия multi-stage для dev
    environment:
      - SPRING_PROFILES_ACTIVE=dev
      - SPRING_JPA_SHOW_SQL=true          # показывать SQL в dev
      - LOGGING_LEVEL_ROOT=DEBUG
    volumes:
      - ./target:/app/target              # hot reload через bind mount
    ports:
      - "8080:8080"
      - "5005:5005"                     # порт для remote debug
    command: >
      java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005
           -jar /app/app.jar             # включаем remote debugging

  db:
    ports:
      - "5432:5432"                     # открываем порт БД для IDE

  mailhog:                               # фейковый SMTP для dev
    image: mailhog/mailhog
    ports:
      - "1025:1025"                     # SMTP
      - "8025:8025"                     # Web UI
YAML — docker-compose.prod.yml (prod)
# docker-compose.prod.yml — продакшен конфигурация
# запуск: docker compose -f docker-compose.yml -f docker-compose.prod.yml up

services:
  app:
    image: myregistry/myapp:1.0.0        # готовый образ из Registry
    environment:
      - SPRING_PROFILES_ACTIVE=prod
      - SPRING_JPA_SHOW_SQL=false
      - LOGGING_LEVEL_ROOT=WARN
    deploy:
      replicas: 2                         # 2 экземпляра приложения
      resources:
        limits:
          memory: 1g
          cpus: "2.0"
        reservations:
          memory: 512m

  db:
    ports: []                             # в проде НЕ открываем порт БД наружу!

  nginx:                                  # reverse proxy в проде
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
      - ./ssl:/etc/ssl:ro
4. Spring Boot — application-docker.yml профиль
YAML — application-docker.yml
# src/main/resources/application-docker.yml
# Активируется при SPRING_PROFILES_ACTIVE=docker

spring:
  datasource:
    url: ${SPRING_DATASOURCE_URL:jdbc:postgresql://db:5432/mydb}
    username: ${SPRING_DATASOURCE_USERNAME:myuser}
    password: ${SPRING_DATASOURCE_PASSWORD}       # нет дефолта — обязателен
    hikari:
      maximum-pool-size: 10
      connection-timeout: 30000
      initialization-fail-timeout: 60000        # ждём до 60 сек пока БД готова

  jpa:
    hibernate:
      ddl-auto: validate                           # в docker не пересоздаём схему!
    show-sql: false

  data:
    redis:
      host: ${SPRING_DATA_REDIS_HOST:redis}
      port: ${SPRING_DATA_REDIS_PORT:6379}
      password: ${REDIS_PASSWORD:}

# Actuator для healthcheck Docker
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics
  endpoint:
    health:
      show-details: when-authorized

logging:
  level:
    root: INFO
    com.company: DEBUG

    depends_on:
      db:
        condition: service_healthy
      kafka:
        condition: service_healthy

  db:
    image: postgres:16-alpine

      POSTGRES_DB: mydb
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user -d mydb"]
      interval: 5s
      retries: 10

  zookeeper:
    image: confluentinc/cp-zookeeper:7.5.0
    environment:
      ZOOKEEPER_CLIENT_PORT: 2181
      ZOOKEEPER_TICK_TIME: 2000
    healthcheck:
      test: ["CMD", "nc", "-z", "localhost", "2181"]
      interval: 10s
      retries: 5

  kafka:
    image: confluentinc/cp-kafka:7.5.0
    ports:
      - "9094:9094"                     # внешний порт для приложений вне compose
    environment:
      KAFKA_BROKER_ID: 1
      KAFKA_ZOOKEEPER_CONNECT: zookeeper:2181
      KAFKA_ADVERTISED_LISTENERS: INTERNAL://kafka:9092,EXTERNAL://localhost:9094
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT
      KAFKA_INTER_BROKER_LISTENER_NAME: INTERNAL
      KAFKA_AUTO_CREATE_TOPICS_ENABLE: "true"
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
    depends_on:
      zookeeper:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "kafka-topics", "--bootstrap-server", "localhost:9092", "--list"]
      interval: 10s
      timeout: 10s
      retries: 10

  kafka-ui:                               # Web UI для Kafka
    image: provectuslabs/kafka-ui:latest
    profiles:
      - dev
    ports:
      - "8090:8080"
    environment:
      KAFKA_CLUSTERS_0_NAME: local
      KAFKA_CLUSTERS_0_BOOTSTRAPSERVERS: kafka:9092

❓ Вопросы для собеседования
Зачем нужен Docker Compose? Чем лучше просто docker run?
What is Docker Compose and why is it better than docker run?
Easy▼
✅ Ответ
Docker Compose позволяет описать весь стек приложения (app + db + redis + kafka) в одном YAML файле и запустить одной командой docker compose up. Без него нужно помнить 10+ команд docker run с портами, volumes, networks, переменными. Compose также управляет порядком запуска (depends_on), общей сетью (сервисы обращаются друг к другу по имени), и упрощает остановку всего стека.
Как контейнеры обращаются друг к другу в Compose?
How do containers communicate with each other in Docker Compose?
Medium▼
✅ Ответ
Compose создаёт общую bridge сеть для всех сервисов. Внутри этой сети каждый сервис доступен по имени сервиса как hostname. Например, если БД называется db в compose — Spring Boot подключается через jdbc:postgresql://db:5432/mydb. Порты между контейнерами доступны напрямую без проброса (8080, 5432 и т.д.).
Почему depends_on не гарантирует готовность приложения?
Why doesn't depends_on guarantee application readiness?
Medium▼
✅ Ответ
По умолчанию depends_on ждёт только старта контейнера (docker daemon запустил процесс), но не готовности самого приложения. PostgreSQL контейнер стартует за секунды, но сама СУБД инициализируется дольше. Решение: depends_on: { db: { condition: service_healthy } } + healthcheck на PostgreSQL (pg_isready). Тогда Compose ждёт пока healthcheck вернёт healthy.
Как управлять секретами в Docker Compose?
How do you manage secrets in Docker Compose?
Medium▼
✅ Ответ
Основной подход: .env файл + env_file: [.env] + .env в .gitignore. В docker-compose.yml ссылаемся через ${VARIABLE}. Для продакшена — Docker Secrets (Swarm), Vault, или переменные окружения CI/CD системы. Никогда не коммить пароли в docker-compose.yml или .env. Для команды предоставляй .env.example с заглушками.
