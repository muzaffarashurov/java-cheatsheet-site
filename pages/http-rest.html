📌 Краткий конспект
HTTP — основа веба
HTTP (HyperText Transfer Protocol) — протокол запрос/ответ. Клиент отправляет Request (метод + URL + заголовки + тело), сервер возвращает Response (статус + заголовки + тело). Stateless — каждый запрос независим.

💡 Безопасный vs Идемпотентный
Безопасный — не изменяет состояние сервера (GET, HEAD, OPTIONS).
Идемпотентный — повторный вызов с теми же данными даёт тот же результат (GET, PUT, DELETE). POST не идемпотентен — каждый вызов создаёт новую запись.
🚦 HTTP Статус коды
2xx — Успех
  • 200 OK — GET, PUT, PATCH успешно
  • 201 Created — POST, ресурс создан
  • 202 Accepted — запрос принят, обработка асинхронна
  • 204 No Content — DELETE успешно, нет тела
  • 206 Partial Content — частичная загрузка файла
3xx — Перенаправление
  • 301 Moved Permanently — ресурс перемещён навсегда
  • 302 Found — временное перенаправление
  • 304 Not Modified — кэш актуален (ETag/If-None-Match)
  • 307 Temporary Redirect — сохраняет метод запроса
  • 308 Permanent Redirect — сохраняет метод
4xx — Ошибка клиента
  • 400 Bad Request — невалидные данные
  • 401 Unauthorized — не аутентифицирован
  • 403 Forbidden — нет прав
  • 404 Not Found — ресурс не найден
  • 405 Method Not Allowed — метод не поддержан
  • 409 Conflict — конфликт (дубль)
  • 410 Gone — ресурс удалён навсегда
  • 422 Unprocessable Entity — семантическая ошибка
  • 429 Too Many Requests — rate limiting
5xx — Ошибка сервера
  • 500 Internal Server Error — непредвиденная ошибка
  • 501 Not Implemented — метод не реализован
  • 502 Bad Gateway — ошибка upstream
  • 503 Service Unavailable — сервис недоступен
  • 504 Gateway Timeout — таймаут от upstream

6 принципов REST (Fielding)
1. Stateless — без состояния на сервере ▼

Каждый запрос содержит всё необходимое для обработки — сервер не хранит состояние клиента между запросами. Позволяет масштабировать горизонтально: любой инстанс может обработать любой запрос. JWT реализует это — токен содержит всю информацию о пользователе.

2. Uniform Interface — единообразный интерфейс ▼

Ресурсы идентифицируются через URI. Манипуляция через представления (JSON/XML). Самоописывающие сообщения (Content-Type). HATEOAS — гипермедиа как движок состояния.

3. Client-Server — разделение клиента и сервера ▼

Клиент и сервер независимы — могут развиваться отдельно. Клиент не знает о хранении данных на сервере. Сервер не знает об UI клиента.

✅ Best Practices
✅ Правильно
  • Версионирование API: /api/v1/
  • Существительные в URL, глаголы — HTTP методы
  • POST → 201 + Location header
  • DELETE → 204 No Content
  • Единый формат ошибок (ErrorResponse)
  • Пагинация через query params: ?page=0&size=20
  • HTTPS всегда в продакшене
  • Rate limiting + Retry-After заголовок
  • ETag для кэширования
  • X-Request-Id для трассировки
🚫 Ошибки
  • Глаголы в URL: /getUser, /createOrder
  • 200 OK при ошибке — скрытые ошибки
  • Разный формат ошибок в разных эндпоинтах
  • Нет версионирования — breaking changes
  • GET запрос изменяет состояние сервера
  • Чувствительные данные в URL (пароль, токен)
  • Возвращать стектрейс клиенту при ошибке
  • Игнорировать Accept заголовок клиента
💻 Примеры кода
1. WebClient — реактивный HTTP клиент
Java
// ── Конфигурация WebClient бина
@Configuration
public class WebClientConfig {

    @Bean
    public WebClient webClient() {
        return WebClient.builder()
            .baseUrl("https://api.external-service.com")  // базовый URL
            .defaultHeader("Content-Type", "application/json")
            .defaultHeader("Accept", "application/json")
            .clientConnector(new ReactorClientHttpConnector(
                HttpClient.create()
                    .responseTimeout(Duration.ofSeconds(5))   // таймаут ответа
                    .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 3000))) // таймаут соединения
            .filter(ExchangeFilterFunctions               // retry при ошибке
                .limitResponseSize(1024 * 1024))           // макс 1MB ответ
            .build();
    }
}

// ── Использование WebClient в сервисе
@Service
@RequiredArgsConstructor
@Slf4j
public class ExternalApiService {

    private final WebClient webClient;

    // ── GET запрос — получить объект
    public UserDto getUser(Long userId) {
        return webClient.get()
            .uri("/users/{id}", userId)                 // подставляем параметр
            .retrieve()                                  // выполнить и получить ответ
            .onStatus(HttpStatus::is4xxClientError,   // обработать 4xx
                res -> res.bodyToMono(String.class)
                    .map(body -> new RuntimeException("Client error: " + body)))
            .onStatus(HttpStatus::is5xxServerError,   // обработать 5xx
                res -> Mono.error(new RuntimeException("Server error")))
            .bodyToMono(UserDto.class)               // десериализуем в объект
            .block();                                  // блокируем (sync вызов)
    }

    // ── POST запрос — создать ресурс
    public UserDto createUser(CreateUserRequest request) {
        return webClient.post()
            .uri("/users")
            .header("X-Request-Id", UUID.randomUUID().toString()) // трассировка
            .bodyValue(request)                          // тело запроса
            .retrieve()
            .bodyToMono(UserDto.class)
            .block();
    }

    // ── GET список с query параметрами
    public List<UserDto> getUsers(int page, int size, String role) {
        return webClient.get()
            .uri(uriBuilder -> uriBuilder          // строим URI с параметрами
                .path("/users")
                .queryParam("page", page)
                .queryParam("size", size)
                .queryParamIfPresent("role", Optional.ofNullable(role)) // только если не null
                .build())
            .retrieve()
            .bodyToFlux(UserDto.class)             // поток элементов
            .collectList()                          // собираем в List
            .block();
    }

    // ── PUT запрос — обновление
    public UserDto updateUser(Long userId, UpdateUserRequest request) {
        return webClient.put()
            .uri("/users/{id}", userId)
            .bodyValue(request)
            .retrieve()
            .bodyToMono(UserDto.class)
            .block();
    }

    // ── DELETE запрос
    public void deleteUser(Long userId) {
        webClient.delete()
            .uri("/users/{id}", userId)
            .retrieve()
            .toBodilessEntity()                     // ответ без тела
            .block();
    }
}
2. RestTemplate — синхронный клиент (legacy)
Java
@Service
@RequiredArgsConstructor
public class LegacyApiService {

    private final RestTemplate restTemplate;

    // ── GET — получить объект
    public UserDto getUser(Long id) {
        return restTemplate.getForObject(
            "/users/{id}",                            // URL шаблон
            UserDto.class,                            // тип ответа
            id                                        // подстановка в шаблон
        );
    }

    // ── GET с полным ответом (статус, заголовки, тело)
    public ResponseEntity<UserDto> getUserEntity(Long id) {
        return restTemplate.getForEntity("/users/{id}", UserDto.class, id);
    }

    // ── GET список через ParameterizedTypeReference
    public List<UserDto> getAllUsers() {
        return restTemplate.exchange(
            "/users",
            HttpMethod.GET,
            null,
            new ParameterizedTypeReference<List<UserDto>>() {} // generic тип
        ).getBody();
    }

    // ── POST — создать
    public UserDto createUser(CreateUserRequest request) {
        HttpHeaders headers = new HttpHeaders();
        headers.setContentType(MediaType.APPLICATION_JSON);
        headers.set("Authorization", "Bearer " + token);

        HttpEntity<CreateUserRequest> entity =
            new HttpEntity<>(request, headers);    // тело + заголовки

        return restTemplate.postForObject("/users", entity, UserDto.class);
    }

    // ── exchange — универсальный метод
    public ResponseEntity<UserDto> patchUser(Long id, PatchUserRequest request) {
        return restTemplate.exchange(
            "/users/{id}",
            HttpMethod.PATCH,
            new HttpEntity<>(request),
            UserDto.class,
            id
        );
    }
}

// ── Зависимость: spring-cloud-starter-openfeign

// ── Включить Feign клиенты
@SpringBootApplication
@EnableFeignClients                               // сканирует @FeignClient
public class Application { ... }

// ── Декларативный клиент — только интерфейс!
@FeignClient(
    name = "user-service",                      // имя сервиса
    url = "${services.user.url:http://user-service}", // базовый URL
    fallback = UserClientFallback.class          // fallback при ошибке
)
public interface UserClient {

    @GetMapping("/api/v1/users/{id}")
    UserDto getUser(@PathVariable Long id);

    @GetMapping("/api/v1/users")
    List<UserDto> getUsers(
        @RequestParam int page,
        @RequestParam int size
    );

    @PostMapping("/api/v1/users")
    UserDto createUser(@RequestBody CreateUserRequest request);

    @DeleteMapping("/api/v1/users/{id}")
    void deleteUser(@PathVariable Long id);
}

// ── Fallback — что вернуть при недоступности сервиса
@Component
public class UserClientFallback implements UserClient {

    @Override
    public UserDto getUser(Long id) {
        return null;                              // или кэшированное значение
    }

    @Override
    public List<UserDto> getUsers(int page, int size) {
        return Collections.emptyList();           // пустой список
    }

    @Override
    public UserDto createUser(CreateUserRequest request) {
        throw new ServiceUnavailableException("User service недоступен");
    }

    @Override
    public void deleteUser(Long id) { /* ничего не делаем */ }
}

❓ Вопросы для собеседования
Что такое REST и каковы его принципы?
What is REST and what are its principles?
Medium▼
✅ Ответ
REST (Representational State Transfer) — архитектурный стиль для распределённых систем. Принципы: 1) Stateless — нет состояния на сервере; 2) Client-Server — независимость; 3) Cacheable — ответы можно кэшировать; 4) Uniform Interface — единообразный интерфейс; 5) Layered System — уровни (proxy, LB); 6) Code on Demand (опционально). В REST ресурсы идентифицируются URI, управляются HTTP методами.
Чем 401 Unauthorized отличается от 403 Forbidden?
What is the difference between 401 and 403?
Easy▼
✅ Ответ
401 Unauthorized — клиент не аутентифицирован (нет токена или токен недействителен). Ответ включает заголовок WWW-Authenticate. Нужно войти в систему.
403 Forbidden — клиент аутентифицирован, но у него нет прав на этот ресурс. Авторизация провалилась. Повторная аутентификация не поможет.
Что такое CORS и как он работает?
What is CORS and how does it work?
Medium▼
✅ Ответ
CORS (Cross-Origin Resource Sharing) — механизм браузера, запрещающий JS запросы к другому origin (домен/порт/протокол) без разрешения сервера. Для «сложных» запросов (не-GET с заголовками) браузер сначала делает preflight OPTIONS запрос. Сервер отвечает заголовками Access-Control-Allow-Origin, Access-Control-Allow-Methods. В Spring настраивается через corsConfigurationSource() в SecurityFilterChain или через @CrossOrigin.
Чем WebClient отличается от RestTemplate?
What is the difference between WebClient and RestTemplate?
Medium▼
✅ Ответ
RestTemplate — синхронный, блокирует поток до получения ответа. Простой API. Помечен как deprecated в новых версиях Spring. WebClient — реактивный, non-blocking, работает с Mono/Flux. Поддерживает streaming. Рекомендован для новых проектов. Можно использовать синхронно через .block(). Лучше производительность при большом числе одновременных запросов.
Что такое идемпотентность и зачем она важна?
What is idempotency and why does it matter?
Medium▼
✅ Ответ
Идемпотентный метод даёт одинаковый результат при повторных вызовах. GET, PUT, DELETE — идемпотентны. POST — нет. Важность: при сетевой ошибке клиент не знает дошёл ли запрос. Безопасно повторить только идемпотентные методы — DELETE дважды вернёт 404, но система в том же состоянии. POST дважды создаст две записи — проблема. Решение для POST: Idempotency-Key заголовок (уникальный ключ операции) — сервер дедуплицирует.
