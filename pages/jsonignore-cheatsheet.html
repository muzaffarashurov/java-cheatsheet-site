@JsonIgnore & Управление JSON-сериализацией

Полное руководство по исключению полей из JSON, управлению видимостью, борьбе с циклическими зависимостями и современным альтернативам в Spring Boot + Jackson.

📌 Краткий конспект

Главное правило
@JsonIgnore полностью исключает поле из сериализации (Java → JSON) и десериализации (JSON → Java). Jackson обрабатывает свойства, а не поля напрямую: аннотация на поле игнорирует и getter, и setter.
ЗадачаРешениеКогда использовать
Скрыть поле полностью@JsonIgnoreПароли, внутренние ID, служебные флаги
Только запись (скрыть в ответе)@JsonProperty(access = WRITE_ONLY)Пароли при регистрации
Только чтение (игнорировать ввод)@JsonProperty(access = READ_ONLY)createdAt, version, вычисляемые поля

🚫 Основы @JsonIgnore

Простое использование на поле
UserDTO.java
@Data
public class UserDTO {
    private Long id;
    private String username;
    
    /*
     * @JsonIgnore полностью исключает поле из JSON.
     * Jackson не вызовет getPassword() при сериализации
     * и не вызовет setPassword() при десериализации.
     */
    @JsonIgnore
    private String password;
}
Важно: Поле vs Геттер/Сеттер

Jackson работает с свойствами (property), а не с полями напрямую. Если аннотация стоит на поле — она применяется и к getter, и к setter. Если нужно игнорировать только сериализацию или только десериализацию, ставь аннотацию на метод.

Разница размещения
public class Example {
    // 1. На поле → игнорируется И сериализация, И десериализация
    @JsonIgnore
    private String fieldIgnore;

    // 2. На getter → игнорируется ТОЛЬКО сериализация (Java → JSON)
    @JsonIgnore
    public String getReadOnly() { ... }
    // При десериализации Jackson всё ещё вызовет setReadOnly()

    // 3. На setter → игнорируется ТОЛЬКО десериализация (JSON → Java)
    public void setWriteOnly(String val) { ... }
    @JsonIgnore
    // При сериализации поле попадёт в JSON, но принять из JSON нельзя
}

🔍 Продвинутые сценарии

READ_ONLY / WRITE_ONLY (Современная альтернатива)

Вместо `@JsonIgnore` часто лучше использовать `@JsonProperty(access = ...)` для более точного контроля.

User.java
@Data
public class User {
    private Long id;
    private String username;

    /*
     * WRITE_ONLY: поле есть в запросе (JSON → Java), но НЕТ в ответе (Java → JSON)
     * Идеально для паролей: клиент отправляет пароль, но сервер никогда не возвращает его обратно.
     */
    @JsonProperty(access = JsonProperty.Access.WRITE_ONLY)
    private String password;

    /*
     * READ_ONLY: поле есть в ответе, но игнорируется при запросе
     * Идеально для createdAt, version, fullName (вычисляемое поле)
     */
    @JsonProperty(access = JsonProperty.Access.READ_ONLY)
    private LocalDateTime createdAt;
}
Динамическое игнорирование (@JsonInclude)
DTO с опциональными полями
/*
 * @JsonInclude управляет сериализацией на уровне КЛАССА или ПОЛЯ.
 * Варианты:
 * ALWAYS (default) — всегда сериализовать
 * NON_NULL         — пропускать, если поле == null
 * NON_EMPTY        — пропускать, если null или пустая строка/коллекция
 * NON_DEFAULT      — пропускать, если равно значению по умолчанию (0, false, null)
 */
@JsonInclude(JsonInclude.Include.NON_NULL)
public class UserUpdateDTO {
    private String username;
    
    // Перекрываем классовую настройку для конкретного поля
    @JsonInclude(JsonInclude.Include.ALWAYS)
    private Boolean active;  // false всё равно попадёт в JSON
    
    private String bio;      // Если null → не попадёт в JSON
}
Условная сериализация (@JsonView)
Разные роли → разный JSON
// 1. Определяем "представления" (Views)
public class Views {
    public static class Public {}
    public static class Internal extends Public {}  // Internal включает Public
}

// 2. Размечаем DTO
public class UserDTO {
    @JsonView(Views.Public.class)
    private String username;

    @JsonView(Views.Internal.class)
    private String email;  // Только для админов

    @JsonIgnore  // Никогда не попадёт в JSON
    private String password;
}

// 3. В контроллере выбираем View
@JsonView(Views.Public.class)  // Для публичного API
@GetMapping("/users")
public List<UserDTO> getPublicUsers() { ... }

@JsonView(Views.Internal.class)  // Для админки
@GetMapping("/admin/users")
public List<UserDTO> getAllUsers() { ... }

🔄 Циклические зависимости JPA + Jackson

Проблема: `Department` имеет `List`, а `Employee` имеет `Department`. При сериализации Jackson зацикливается: Dept → Emp → Dept → Emp → StackOverflowError.

Решение 1 (Лучшее): Не сериализовать Entity! Используй DTO/Mapper.

Решение 2 (Быстрое): Разорвать цикл аннотациями Jackson.

Разрыв цикла через аннотации
// Сторона-владелец (хранит FK в БД)
@Entity
public class Employee {
    @Id private Long id;
    
    /*
     * @JsonBackReference: поле НЕ сериализуется в JSON.
     * Используется ТОЛЬКО при десериализации для восстановления связи.
     */
    @ManyToOne
    @JsonBackReference
    private Department department;
}

// Обратная сторона
@Entity
public class Department {
    @Id private Long id;
    
    /*
     * @JsonManagedReference: поле сериализуется в JSON.
     * Jackson понимает, что это "родительская" часть связи.
     */
    @OneToMany(mappedBy = "department")
    @JsonManagedReference
    private List<Employee> employees;
}

// 💡 Результат JSON при GET /departments/1:
// {"id": 1, "name": "IT", "employees": [{"id": 10, "name": "Ivan"}]}
// (Employee.department будет null в JSON, чтобы не было цикла)
⚠️ Почему DTO лучше?
Аннотации `@JsonManagedReference`/`@JsonBackReference` работают, но смешивают логику сериализации с Entity. Это нарушает Separation of Concerns. В реальных проектах создавай `DepartmentResponse` и `EmployeeResponse`, где связи контролируются явно через Mapper.

✅ Best & ⚠️ Anti Practices

✅ Best Practices
  • Используй DTO для API вместо Entity с `@JsonIgnore`
  • Для паролей применяй `@JsonProperty(access = WRITE_ONLY)`
  • Для audit-полей (createdAt, updatedAt) используй `READ_ONLY`
  • Разрывай циклы на уровне Mapper, а не аннотациями в Entity
  • Используй `@JsonInclude(NON_NULL)` на уровне DTO, а не на каждом поле
  • Для сложных сценариев ролей используй `@JsonView` или разные DTO
  • Всегда тестируй JSON-контракт через `MockMvc` или интеграционные тесты
⚠️ Anti Patterns
  • ❌ Сериализовать JPA-Entity напрямую в контроллере
  • ❌ Использовать `@JsonIgnore` на `@Id` (ломает десериализацию PUT/PATCH)
  • ❌ Забывать про `@JsonIgnore` на геттере при использовании Lombok `@Data`
  • ❌ Игнорировать поля валидации через `@JsonIgnore` (валидация сработает ДО сериализации!)
  • ❌ Использовать `@JsonManagedReference`/`@JsonBackReference` в новых проектах вместо DTO
  • ❌ Возвращать `Map` вместо типизированного DTO

❓ Вопросы для собеседования

В чём разница между @JsonIgnore и @JsonInclude(Include.NON_NULL)?
Difference between @JsonIgnore and @JsonInclude(NON_NULL)?
Easy ▼
✅ Ответ
@JsonIgnore полностью убирает поле из JSON независимо от его значения. @JsonInclude(NON_NULL) убирает поле только если оно равно null. Если поле содержит пустую строку `""` или `0`, оно всё равно попадёт в ответ. `@JsonIgnore` — жёсткое правило, `@JsonInclude` — условное.
Как игнорировать поле только при сериализации, но принимать при десериализации?
How to ignore only during serialization but allow deserialization?
Medium ▼
✅ Ответ
Два способа: 1) Поставить @JsonIgnore на getter (игнорируется вывод), но не на setter. 2) Современный подход: @JsonProperty(access = JsonProperty.Access.WRITE_ONLY). Второй способ предпочтительнее, так как явно декларирует намерение и работает предсказуемо с Lombok и валидацией.
Почему возникает StackOverflowError при возврате Entity с двусторонней связью?
Why StackOverflowError with bidirectional Entity relations?
Hard ▼
✅ Ответ
Jackson рекурсивно обходит граф объектов. Если `A` ссылается на `B`, а `B` на `A`, сериализатор попадает в бесконечный цикл: A → B → A → B... Решения: 1) Использовать DTO (рекомендуется), 2) `@JsonManagedReference`/`@JsonBackReference`, 3) `@JsonIgnore` на одной из сторон, 4) `@JsonIdentityInfo` (сериализация по ID с последующими ссылками). В Spring Boot 3+ лучше всего проектировать API вокруг DTO.
Влияет ли @JsonIgnore на валидацию (@Valid)?
Does @JsonIgnore affect @Valid validation?
Medium ▼
✅ Ответ
Нет. Валидация (`@Valid`) происходит до сериализации/десериализации Jackson. Даже если поле помечено `@JsonIgnore`, если клиент передаст его в JSON, Jackson сначала распарсит его в объект, запустится валидация, и только потом поле будет проигнорировано при формировании ответа. Чтобы полностью заблокировать ввод, используй `@JsonProperty(access = READ_ONLY)` или удали setter.
