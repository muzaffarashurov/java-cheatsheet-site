📌 Краткий конспект

Что такое паттерн?
Паттерн (шаблон проектирования) — это проверенное решение типовой проблемы в определённом контексте. Это не готовый код, а идея, которую можно адаптировать под свою задачу.

🔨 Порождающие паттерны

Singleton — единственный экземпляр

Проблема: Нужно гарантировать, что у класса только один экземпляр, и предоставить глобальную точку доступа к нему.

Решение: Приватный конструктор + статический метод/поле.

Java
// ✅ Thread-safe Singleton (Bill Pugh)
public class DatabaseConnection {
    private DatabaseConnection() {}  // Приватный конструктор

    private static class Holder {
        static final DatabaseConnection INSTANCE = new DatabaseConnection();
    }

    public static DatabaseConnection getInstance() {
        return Holder.INSTANCE;  // Ленивая инициализация, thread-safe
    }
}

// 💡 В Spring: Singleton — default scope для всех @Component/@Service
// Не пиши Singleton вручную — используй DI!
Factory Method — фабрика объектов

Проблема: Не знаем заранее, какой класс нужно создать.

Решение: Делегируем создание подклассам или отдельному методу.

Java
// Интерфейс продукта
interface Notification { void send(String message); }

// Конкретные продукты
class EmailNotification implements Notification {
    public void send(String msg) { System.out.println("Email: " + msg); }
}
class SmsNotification implements Notification {
    public void send(String msg) { System.out.println("SMS: " + msg); }
}

// Фабрика
public class NotificationFactory {
    public static Notification create(String type) {
        return switch (type.toLowerCase()) {
            case "email" -> new EmailNotification();
            case "sms"   -> new SmsNotification();
            default -> throw new IllegalArgumentException("Unknown type: " + type);
        };
    }
}

// 💡 В Spring: @Bean-методы в @Configuration — это Factory Method!
Builder — пошаговое создание сложных объектов

Проблема: Конструктор с 10+ параметрами — нечитаемо и ошибкоопасно.

Решение: Отдельный Builder-класс для пошаговой сборки.

Java
// ✅ Lombok @Builder — автоматически генерирует Builder
@Data @Builder @NoArgsConstructor @AllArgsConstructor
public class User {
    private Long id;
    private String username;
    private String email;
    private LocalDateTime createdAt;
    private Set<String> roles;
}

// Использование:
User user = User.builder()
    .username("admin")
    .email("admin@company.ru")
    .createdAt(LocalDateTime.now())
    .roles(Set.of("ADMIN", "USER"))
    .build();

// 💡 Spring: ResponseEntity.builder(), UriComponentsBuilder
Prototype — клонирование объектов

Проблема: Создание объекта дорого (тяжёлые вычисления, БД-запросы).

Решение: Клонировать готовый прототип вместо создания с нуля.

Java
public class Config implements Cloneable {
    private Map<String, Object> settings = new HashMap<>();

    @Override
    protected Config clone() {
        try {
            Config copy = (Config) super.clone();
            copy.settings = new HashMap<>(this.settings);  // Глубокое копирование
            return copy;
        } catch (CloneNotSupportedException e) {
            throw new RuntimeException(e);
        }
    }
}

Abstract Factory — семейство связанных объектов

Проблема: Нужно создавать группы связанных объектов (кнопки + чекбоксы для разных ОС).

Решение: Интерфейс фабрики, который создаёт целое семейство продуктов.

Java
// Абстрактные продукты
interface Button { void render(); }
interface Checkbox { void render(); }

// Абстрактная фабрика
interface GUIFactory {
    Button createButton();
    Checkbox createCheckbox();
}

// Конкретная фабрика для Windows
class WindowsFactory implements GUIFactory {
    public Button createButton() { return new WindowsButton(); }
    public Checkbox createCheckbox() { return new WindowsCheckbox(); }
}

// Клиентский код не знает, какая фабрика используется
public void renderUI(GUIFactory factory) {
    factory.createButton().render();
    factory.createCheckbox().render();
}

🧱 Структурные паттерны

Adapter — адаптер интерфейсов

Проблема: Классы с несовместимыми интерфейсами не могут работать вместе.

Решение: Обёртка, которая преобразует интерфейс одного класса в интерфейс, ожидаемый клиентом.

Java
// Целевой интерфейс
interface PaymentProcessor {
    void processPayment(double amount);
}

// Существующий класс с другим интерфейсом
class LegacyPayPal {
    public void makePayment(String currency, double amount) {
        System.out.println("PayPal: " + amount + " " + currency);
    }
}

// Адаптер
class PayPalAdapter implements PaymentProcessor {
    private final LegacyPayPal payPal = new LegacyPayPal();

    public void processPayment(double amount) {
        payPal.makePayment("USD", amount);  // Адаптируем вызов
    }
}

// 💡 В Spring: @RestController — адаптер между контроллером и HTTP
Proxy — прокси-объект

Проблема: Нужно добавить поведение (логирование, кэш, проверка прав) без изменения основного класса.

Решение: Прокси-класс, который контролирует доступ к реальному объекту.

Java
// Реальный сервис
interface UserService { String getUser(Long id); }

class UserServiceImpl implements UserService {
    public String getUser(Long id) {
        return "User_" + id;  // Тяжёлый запрос к БД
    }
}

// Прокси с кэшированием
class UserServiceProxy implements UserService {
    private final UserService realService = new UserServiceImpl();
    private final Map<Long, String> cache = new HashMap<>();

    public String getUser(Long id) {
        if (!cache.containsKey(id)) {
            System.out.println("Cache miss, loading from DB...");
            cache.put(id, realService.getUser(id));
        }
        return cache.get(id);
    }
}

// 💡 В Spring: @Transactional, @Cacheable, @Secured — всё это Proxy через AOP!
Decorator — динамическое добавление поведения

Проблема: Нужно гибко добавлять функциональность объектам без наследования.

Решение: Обёртка, которая добавляет поведение "на лету".

Java
// Компонент
interface Coffee { double getCost(); String getDescription(); }

// Базовый компонент
class SimpleCoffee implements Coffee {
    public double getCost() { return 5.0; }
    public String getDescription() { return "Simple coffee"; }
}

// Декоратор
abstract class CoffeeDecorator implements Coffee {
    protected final Coffee coffee;
    public CoffeeDecorator(Coffee coffee) { this.coffee = coffee; }
    public double getCost() { return coffee.getCost(); }
    public String getDescription() { return coffee.getDescription(); }
}

// Конкретный декоратор
class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee coffee) { super(coffee); }
    public double getCost() { return super.getCost() + 2.0; }
    public String getDescription() { return super.getDescription() + ", milk"; }
}

// Использование: можно комбинировать декораторы
Coffee order = new MilkDecorator(new SimpleCoffee());
System.out.println(order.getDescription());  // "Simple coffee, milk"

// 💡 В Spring: @Cacheable, @Transactional — декораторы через AOP
Facade — упрощённый интерфейс к сложной подсистеме

Проблема: Сложная библиотека с десятками классов — неудобно использовать.

Решение: Единый простой интерфейс, который скрывает сложность.

Java
// Сложная подсистема
class VideoCodec { public void encode() { ... } }
class AudioCodec { public void encode() { ... } }
class StreamMuxer { public void mux() { ... } }

// Фасад — простой интерфейс
class VideoConverter {
    public void convert(String filename, String format) {
        new VideoCodec().encode();
        new AudioCodec().encode();
        new StreamMuxer().mux();
        System.out.println("Конвертация завершена!");
    }
}

// Клиентский код — простой и понятный
new VideoConverter().convert("video.mp4", "avi");

// 💡 В Spring: Spring Boot Auto-configuration — фасад к сложной настройке

🔄 Поведенческие паттерны

Strategy — семейство алгоритмов

Проблема: Нужно менять алгоритм "на лету" без изменения контекста.

Решение: Вынести алгоритм в отдельный класс с общим интерфейсом.

Java
// Стратегия
interface PaymentStrategy {
    void pay(double amount);
}

// Конкретные стратегии
class CreditCardPayment implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("Оплата картой: $" + amount);
    }
}
class PayPalPayment implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("Оплата через PayPal: $" + amount);
    }
}

// Контекст
class ShoppingCart {
    private PaymentStrategy paymentStrategy;

    public void setPaymentStrategy(PaymentStrategy strategy) {
        this.paymentStrategy = strategy;
    }

    public void checkout(double amount) {
        paymentStrategy.pay(amount);  // Делегируем стратегию
    }
}

// 💡 В Spring: @Qualifier + DI — выбор стратегии через конфигурацию
Observer — подписка на события

Проблема: Нужно уведомлять множество объектов об изменении состояния одного.

Решение: Механизм подписки: наблюдатели регистрируются и получают уведомления.

Java
// Наблюдатель
interface Observer {
    void update(String event);
}

// Субъект (издатель)
class OrderService {
    private final List<Observer> observers = new ArrayList<>();

    public void attach(Observer observer) {
        observers.add(observer);
    }

    public void placeOrder(String orderId) {
        System.out.println("Заказ " + orderId + " размещён");
        notifyObservers("ORDER_PLACED:" + orderId);
    }

    private void notifyObservers(String event) {
        for (Observer obs : observers) {
            obs.update(event);
        }
    }
}

// Конкретные наблюдатели
class EmailNotifier implements Observer {
    public void update(String event) {
        if (event.startsWith("ORDER_PLACED")) {
            System.out.println("Email отправлен: " + event);
        }
    }
}

// 💡 В Spring: @EventListener, ApplicationEventPublisher — встроенный Observer
Command — инкапсуляция запроса как объекта

Проблема: Нужно параметризовать объекты операциями, поддерживать отмену/повтор, очередь команд.

Решение: Превратить запрос в объект с методами execute/undo.

Java
// Команда
interface Command {
    void execute();
    void undo();
}

// Получатель
class Light {
    public void turnOn() { System.out.println("💡 Свет включён"); }
    public void turnOff() { System.out.println("💡 Свет выключен"); }
}

// Конкретная команда
class LightOnCommand implements Command {
    private final Light light;
    public LightOnCommand(Light light) { this.light = light; }
    public void execute() { light.turnOn(); }
    public void undo() { light.turnOff(); }
}

//.Invoker (вызывающий)
class RemoteControl {
    private Command command;
    public void setCommand(Command cmd) { this.command = cmd; }
    public void pressButton() { command.execute(); }
    public void pressUndo() { command.undo(); }
}

// 💡 В Spring: @Async, @Scheduled — команды, выполняемые асинхронно

🌱 Spring-specific паттерны

Dependency Injection (DI) — внедрение зависимостей

Суть: Объекты не создают зависимости сами, а получают их извне (через конструктор, setter или поле).

Зачем: Упрощает тестирование, снижает связность, позволяет гибко конфигурировать приложение.

Java
// ❌ Плохо: жёсткая зависимость
class UserService {
    private UserRepository repo = new UserRepositoryImpl();  // Жёстко привязан!
}

// ✅ Хорошо: внедрение через конструктор (рекомендуется!)
@Service
@RequiredArgsConstructor  // Lombok генерирует конструктор
class UserService {
    private final UserRepository repo;  // final = гарантированная инициализация
    // Spring сам передаст реализацию при создании бина
}

// 💡 Types of DI:
// • Constructor (✅ лучший): через конструктор, immutable зависимости
// • Setter (⚠️ осторожно): через setter-метод, мутабельные зависимости
// • Field (❌ не рекомендуется): @Autowired на поле, сложно тестировать
Front Controller — единая точка входа

Суть: Все запросы обрабатываются одним контроллером, который делегирует обработку.

Зачем: Централизованная обработка (аутентификация, логирование, маппинг).

Java
// В Spring MVC это DispatcherServlet + @RestController

// Все запросы идут через DispatcherServlet (Front Controller)
// Он находит подходящий @RequestMapping и вызывает метод контроллера

@RestController
@RequestMapping("/api/users")
public class UserController {
    @GetMapping                    // GET /api/users
    public List<User> getAll() { ... }

    @GetMapping("/{id}")          // GET /api/users/5
    public User getById(@PathVariable Long id) { ... }

    @PostMapping                  // POST /api/users
    public User create(@RequestBody UserDTO dto) { ... }
}

// 💡 Преимущества:
// • Единое место для @ControllerAdvice (обработка ошибок)
// • Глобальные фильтры (CORS, security, logging)
// • Автоматическая сериализация в JSON (@RestController)
Template Method — скелет алгоритма

Суть: Определяем скелет алгоритма в базовом классе, а шаги делегируем подклассам.

Зачем: Переиспользование кода с возможностью кастомизации.

Java
// Абстрактный шаблон
abstract class DataImporter {
    // Шаблонный метод — финальный алгоритм
    public final void importData(String path) {
        validatePath(path);           // Общий шаг
        List<String> lines = readFile(path);  // Абстрактный шаг
        processLines(lines);          // Общий шаг
        saveToDatabase(lines);        // Общий шаг
    }

    protected abstract List<String> readFile(String path);  // Реализуют подклассы
    protected void validatePath(String path) { ... }  // Общий код
}

// Конкретная реализация для CSV
class CsvImporter extends DataImporter {
    protected List<String> readFile(String path) {
        return Files.readAllLines(Paths.get(path));
    }
}

// 💡 В Spring: JdbcTemplate, RestTemplate — Template Method
// Вы предоставляете RowMapper/ResponseExtractor, шаблон делает остальное
AOP (Aspect-Oriented Programming) — аспекты

Суть: Выделяем сквозную функциональность (логирование, транзакции, безопасность) в отдельные аспекты.

Зачем: Не засорять бизнес-логику техническим кодом.

Java
// Аспект для логирования
@Aspect @Component
public class LoggingAspect {
    @Around("@annotation(Loggable)")  // Точка входа: методы с @Loggable
    public Object logExecution(ProceedingJoinPoint joinPoint) throws Throwable {
        String method = joinPoint.getSignature().toShortString();
        System.out.println("▶ Начало: " + method);

        long start = System.currentTimeMillis();
        Object result = joinPoint.proceed();  // Выполняем целевой метод
        long duration = System.currentTimeMillis() - start;

        System.out.println("✅ Конец: " + method + " (" + duration + "ms)");
        return result;
    }
}

// Использование: просто добавляем аннотацию
@Service
public class UserService {
    @Loggable  // Аспект автоматически применится!
    public User getUser(Long id) { ... }
}

// • @Transactional — управление транзакциями
// • @Cacheable/@CacheEvict — кэширование
// • @Secured/@PreAuthorize — безопасность

✅ Best & ⚠️ Anti Patterns

✅ Best Practices
  • Используй DI через конструктор (@RequiredArgsConstructor)
  • Предпочитай композицию наследованию
  • Применяй паттерны только когда есть реальная проблема
  • Используй Spring-аналоги вместо ручных реализаций
  • Документируй, почему выбран конкретный паттерн
  • Тестируй каждый паттерн отдельно (особенно Strategy, Command)
  • Избегай God Object — разбивай на мелкие классы
  • Используй records (Java 16+) для DTO и Value Objects
⚠️ Anti Patterns
  • ❌ Singleton через static поле — сложно тестировать
  • ❌ Factory без необходимости — over-engineering
  • ❌ Наследование ради наследования (используй композицию)
  • ❌ Анонимные классы вместо лямбд (до Java 8)
  • ❌ @Autowired на поле — скрытая зависимость, сложно тестировать
  • ❌ Pattern matching через if-else вместо полиморфизма
  • ❌ "Умные" данные, "глупые" сервисы (нарушение инкапсуляции)
  • ❌ Применение паттерна "потому что модно", а не по необходимости

💻 Практические примеры

1. Strategy + DI в Spring ▼
Java
// Интерфейс стратегии
public interface DiscountStrategy {
    double calculate(double price);
}

// Конкретные стратегии (все @Component)
@Component
public class NoDiscount implements DiscountStrategy {
    public double calculate(double price) { return price; }
}

@Component
public class PercentDiscount implements DiscountStrategy {
    private static final double PERCENT = 0.1;  // 10%
    public double calculate(double price) { return price * (1 - PERCENT); }
}

// Фабрика стратегий через Map injection
@Service
@RequiredArgsConstructor
public class DiscountService {
    private final Map<String, DiscountStrategy> strategies;

    // Spring автоматически соберёт все DiscountStrategy в Map по имени бина
    public double applyDiscount(String type, double price) {
        return strategies.getOrDefault(type, strategies.get("noDiscount"))
            .calculate(price);
    }
}
2. Builder + Validation ▼
Java
// Record с валидацией в компактном конструкторе (Java 16+)
public record Order(
    Long id,
    String customerId,
    List<OrderItem> items,
    BigDecimal total,
    OrderStatus status,
    LocalDateTime createdAt
) {
    // Компактный конструктор для валидации
    public Order {
        if (customerId == null || customerId.isBlank()) {
            throw new IllegalArgumentException("customerId required");
        }
        if (items == null || items.isEmpty()) {
            throw new IllegalArgumentException("items required");
        }
        if (total.compareTo(BigDecimal.ZERO) < 0) {
            throw new IllegalArgumentException("total must be positive");
        }
    }

    // Статический фабричный метод для удобства
    public static Order create(String customerId, List<OrderItem> items) {
        BigDecimal total = items.stream()
            .map(OrderItem::getPrice)
            .reduce(BigDecimal.ZERO, BigDecimal::add);
        
        return new Order(
            null,  // id сгенерирует БД
            customerId,
            items,
            total,
            OrderStatus.PENDING,
            LocalDateTime.now()
        );
    }
}

❓ Вопросы для собеседования

В чём разница между Factory Method и Abstract Factory?
Difference between Factory Method and Abstract Factory?
Medium ▼
✅ Ответ
Factory Method создаёт один продукт через наследование (подкласс решает, какой класс инстанцировать). Abstract Factory создаёт семейство связанных продуктов через композицию (интерфейс фабрики, который возвращает несколько типов объектов). Factory Method — про наследование, Abstract Factory — про композицию и группировку.
Зачем в Spring использовать constructor injection вместо @Autowired на поле?
Why use constructor injection over field injection in Spring?
Easy ▼
✅ Ответ
1) Immutable зависимости: final поля гарантируют, что зависимость не изменится. 2) Тестируемость: в тестах можно передать mock через конструктор без Spring-контекста. 3) Явность: сразу видно, какие зависимости нужны классу. 4) Защита от циклических зависимостей: Spring обнаружит их при старте, а не в runtime. Field injection скрывает зависимости и усложняет тестирование.
Как работает @Transactional в Spring? Какой паттерн используется?
How does @Transactional work? What pattern is used?
Hard ▼
✅ Ответ
Используется паттерн Proxy + AOP. При старте приложения Spring создаёт прокси-объект для @Transactional-класса. Когда вызывается метод, прокси: 1) Открывает транзакцию, 2) Вызывает реальный метод, 3) Коммитит при успехе или роллбэкает при исключении. Прокси создаётся через CGLIB (для классов) или JDK Dynamic Proxy (для интерфейсов). Важно: вызов @Transactional-метода из того же класса не сработает — прокси не перехватит self-invocation.
Когда НЕ стоит использовать паттерны?
When should you NOT use design patterns?

1) YAGNI: если проблема ещё не возникла — не добавляй абстракцию. 2) Over-engineering: простой if-else лучше сложной иерархии для 2-3 вариантов. 3) Преждевременная оптимизация: не делай Singleton, если не доказана необходимость единственного экземпляра. 4) Сложность > польза: если паттерн делает код менее читаемым — не используй его. Паттерны — инструменты, а не самоцель.
