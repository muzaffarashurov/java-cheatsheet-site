Service Layer

Spring Backend @Service @Transactional

@Service, @Transactional, Repository, разделение слоёв, бизнес-логика, паттерны сервисного слоя, работа с JPA, обработка исключений — всё что нужно знать о сервисном слое Spring приложения.

🚫 Антипаттерн — логика в контроллере
  • Контроллер сам обращается к репозиторию
  • Бизнес-правила разбросаны по контроллерам
  • Невозможно переиспользовать логику
  • Сложно тестировать без HTTP контекста
✅ Правильно — логика в сервисе
  • Контроллер только вызывает сервис
  • Сервис можно вызвать из разных контроллеров
  • Сервис легко тестировать с mock репозиторием
  • Транзакции управляются в одном месте
🔄 @Transactional — управление транзакциями

@Transactional — Spring управляет транзакцией автоматически: открывает перед методом, коммитит при успехе, откатывает при исключении.

АтрибутЗначенияОписание
readOnlytrue / falseОптимизация для SELECT — не нужен flush, подсказка Hibernate
rollbackForException.classОткат при checked исключении (по умолч. только RuntimeException)
noRollbackForSpecificException.classНе откатывать при этом исключении
timeoutсекундыОткат если транзакция длится дольше N секунд
isolationREAD_COMMITTED и др.Уровень изоляции транзакции
propagationREQUIRED и др.Поведение при вложенных транзакциях
Propagation — распространение транзакций
PropagationПоведениеКогда
REQUIRED (default)Использует существующую или создаёт новую99% случаев
REQUIRES_NEWВсегда создаёт новую, приостанавливает текущуюЛогирование, аудит — должен сохраниться даже при откате внешней
NESTEDВложенная транзакция (savepoint)Частичный откат

⚠️ Частые ошибки с @Transactional
1. Self-invocation — вызов @Transactional метода из того же класса не работает (нет AOP прокси).
2. private методы — @Transactional не работает на private методах (Spring AOP не может создать прокси).
3. Checked исключения — по умолчанию откат только при RuntimeException. Добавь rollbackFor = Exception.class если нужно.
4. readOnly на write операциях — данные не сохранятся в БД.

🚨 Обработка исключений в сервисе

Сервис должен кидать осмысленные бизнесовые исключения — не JPA исключения напрямую. GlobalExceptionHandler их перехватит и вернёт правильный HTTP статус.

ИсключениеHTTP статусКогда кидать

EmailAlreadyExistsException409 ConflictДублирующийся уникальный ключ
AccessDeniedException403 ForbiddenНет прав на операцию
InvalidPasswordException400 Bad RequestНеверный пароль при смене
InsufficientFundsException422 Unprocessable EntityБизнес-правило нарушено
IllegalStateException400 Bad RequestНедопустимое состояние
🧩 Паттерны сервисного слоя
Interface + Implementation — разделение контракта и реализации ▼

Классический подход: создать интерфейс UserService и реализацию UserServiceImpl. Плюсы: легко заменить реализацию, мокировать в тестах, соответствует DIP.
Минус: много бойлерплейта. В современном Spring — необязательно если нет нескольких реализаций. Достаточно просто класса @Service.

Facade — упрощение сложных операций ▼

Один сервис оркестрирует несколько других. Например, RegistrationFacade вызывает UserService.create(), EmailService.sendWelcome(), ProfileService.createDefault(). Контроллер вызывает только Facade, не зная о деталях.

Strategy — заменяемое поведение через интерфейс ▼

Разные алгоритмы за одним интерфейсом. Пример: PaymentStrategy с реализациями CardPayment, CryptoPayment, BankTransfer. Сервис выбирает нужную через List<PaymentStrategy> или Map. Spring инжектирует все реализации автоматически.

✅ Best Practices
✅ Правильно
  • @Transactional(readOnly = true) на методах чтения
  • Кидать бизнесовые исключения, не JPA напрямую
  • DI через конструктор + @RequiredArgsConstructor
  • Один сервис — одна область ответственности
  • Возвращать DTO, не Entity из сервиса
  • Логировать через @Slf4j + log.info/debug
  • Транзакция на уровне сервиса, не репозитория
  • Валидация бизнес-правил в сервисе, не в контроллере
🚫 Ошибки
  • Бизнес-логика в контроллере или репозитории
  • Вызывать @Transactional метод из того же класса
  • @Transactional на private методах
  • Возвращать Entity из сервиса в контроллер
  • Ловить и проглатывать исключения без логирования
  • God Service — один сервис делает всё
  • Инжектировать контроллер в сервис (нарушение слоёв)
  • Не освобождать ресурсы при ошибках
💻 Примеры кода
1. Полный UserService с CRUD операциями
Java
@Service                                          // бин сервисного слоя
@RequiredArgsConstructor                          // Lombok: конструктор для final полей
@Slf4j                                            // Lombok: поле log = LoggerFactory.getLogger()
public class UserService {

    private final UserRepository  userRepository;  // доступ к БД
    private final UserMapper      userMapper;       // маппинг Entity ↔ DTO
    private final PasswordEncoder passwordEncoder; // BCrypt хэширование

    // ── Получение всех с пагинацией — readOnly оптимизация
    @Transactional(readOnly = true)                // нет flush, быстрее
    public Page<UserResponse> findAll(Pageable pageable, String search) {
        Page<User> users = search != null
            ? userRepository.findByNameContainingIgnoreCase(search, pageable)
            : userRepository.findAll(pageable);
        return users.map(userMapper::toResponse);   // Entity → DTO для каждой записи
    }

    // ── Поиск по ID — кидаем 404 если не найден
    @Transactional(readOnly = true)
    public UserResponse findById(Long id) {
        return userRepository.findById(id)
            .map(userMapper::toResponse)              // нашли — конвертируем
            .orElseThrow(() -> {
                log.warn("User not found: id={}", id);  // логируем предупреждение
                return new ResourceNotFoundException("User", id); // → 404
            });
    }

    // ── Создание нового пользователя
    @Transactional                                  // по умолч. REQUIRED — откат при RuntimeEx
    public UserResponse create(CreateUserRequest request) {
        // ── Бизнес-валидация: email должен быть уникальным
        if (userRepository.existsByEmail(request.email())) {
            throw new EmailAlreadyExistsException(request.email()); // → 409
        }

        // ── Создаём Entity через Builder
        User user = User.builder()
            .name(request.name())
            .email(request.email().toLowerCase().trim()) // нормализуем email
            .password(passwordEncoder.encode(request.password())) // BCrypt хэш
            .role(Role.ROLE_USER)                    // роль по умолчанию
            .active(true)
            .build();

        User saved = userRepository.save(user);     // INSERT INTO users
        log.info("Created user: id={}, email={}", saved.getId(), saved.getEmail());
        return userMapper.toResponse(saved);        // Entity → DTO
    }

    // ── Полное обновление (PUT)
    @Transactional
    public UserResponse update(Long id, UpdateUserRequest request) {
        User user = userRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("User", id));

        // Проверяем что email не занят другим пользователем
        if (!user.getEmail().equals(request.email()) &&
            userRepository.existsByEmail(request.email())) {
            throw new EmailAlreadyExistsException(request.email());
        }

        // Обновляем поля Entity
        user.setName(request.name());
        user.setEmail(request.email());
        // В @Transactional — dirty checking сам сохранит изменения при коммите!
        // save() не обязателен, но явный вызов — хорошая практика
        return userMapper.toResponse(userRepository.save(user));
    }

    // ── Частичное обновление (PATCH)
    @Transactional
    public UserResponse patch(Long id, PatchUserRequest request) {
        User user = userRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("User", id));

        // Обновляем только непустые поля
        if (request.name() != null)  user.setName(request.name());
        if (request.email() != null) user.setEmail(request.email());
        if (request.phone() != null) user.setPhone(request.phone());

        return userMapper.toResponse(userRepository.save(user));
    }

    // ── Soft Delete (помечаем удалённым, не удаляем из БД)
    @Transactional
    public void delete(Long id) {
        User user = userRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("User", id));
        user.setDeletedAt(Instant.now());           // помечаем время удаления
        user.setActive(false);
        userRepository.save(user);
        log.info("Soft deleted user: id={}", id);
    }
}
2. @Transactional — тонкости и ловушки
Java
@Service
@RequiredArgsConstructor
public class PaymentService {

    private final AccountRepository accountRepository;
    private final AuditService     auditService;      // для логирования

    // ── Перевод денег — атомарная операция
    @Transactional                                   // откат при любой ошибке
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        Account from = accountRepository.findById(fromId)
            .orElseThrow(() -> new ResourceNotFoundException("Account", fromId));
        Account to = accountRepository.findById(toId)
            .orElseThrow(() -> new ResourceNotFoundException("Account", toId));

        // Бизнес-проверка
        if (from.getBalance().compareTo(amount) < 0) {
            throw new InsufficientFundsException(fromId, amount); // → 422
        }

        from.setBalance(from.getBalance().subtract(amount)); // списываем
        to.setBalance(to.getBalance().add(amount));          // зачисляем

        accountRepository.save(from);
        accountRepository.save(to);

        // auditService использует REQUIRES_NEW — сохранится даже при откате transfer
        auditService.logTransfer(fromId, toId, amount);
    }

    // ── ЛОВУШКА: self-invocation не работает!
    @Transactional
    public void processAll() {
        processOne(1L);   // ❌ @Transactional на processOne НЕ СРАБОТАЕТ
                           // вызов идёт напрямую, минуя Spring прокси
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void processOne(Long id) { ... }

    // ── РЕШЕНИЕ: вынести в отдельный бин или использовать ApplicationContext
}

// ── AuditService с REQUIRES_NEW — независимая транзакция
@Service
@RequiredArgsConstructor
public class AuditService {
    private final AuditLogRepository auditLogRepository;

    @Transactional(propagation = Propagation.REQUIRES_NEW) // НОВАЯ транзакция!
    public void logTransfer(Long fromId, Long toId, BigDecimal amount) {
        // сохранится ВСЕГДА — даже если внешняя транзакция откатится
        auditLogRepository.save(AuditLog.builder()
            .action("TRANSFER")
            .details("from=" + fromId + " to=" + toId + " amount=" + amount)
            .timestamp(Instant.now())
            .build());
    }
}
3. Repository — кастомные запросы
Java
@Repository                                        // Spring Data JPA репозиторий
public interface UserRepository extends JpaRepository<User, Long> {

    // ── Query methods — Spring генерирует SQL по имени
    Optional<User> findByEmail(String email);                      // WHERE email = ?
    boolean existsByEmail(String email);                          // EXISTS WHERE email = ?
    List<User> findByActiveTrue();                                 // WHERE active = true
    List<User> findByDeletedAtIsNull();                            // WHERE deleted_at IS NULL
    Page<User> findByNameContainingIgnoreCase(String name, Pageable p); // ILIKE

    // ── @Query — JPQL (Java Persistence Query Language)
    @Query("SELECT u FROM User u WHERE u.role = :role AND u.active = true")
    List<User> findActiveByRole(@Param("role") Role role);      // именованный параметр

    // ── @Query с нативным SQL (когда JPQL недостаточно)
    @Query(value = """
        SELECT u.*, COUNT(o.id) as orders_count
        FROM users u
        LEFT JOIN orders o ON u.id = o.user_id
        WHERE u.active = true
        GROUP BY u.id
        HAVING COUNT(o.id) >= :minOrders
        """, nativeQuery = true)                                // nativeQuery = реальный SQL
    List<User> findUsersWithMinOrders(@Param("minOrders") int minOrders);

    // ── @Modifying — UPDATE/DELETE запросы
    @Modifying                                                     // обязательно для изменений
    @Transactional                                                 // нужна транзакция
    @Query("UPDATE User u SET u.active = false WHERE u.id = :id")
    int deactivateById(@Param("id") Long id);                    // возвращает кол-во изменённых

    // ── Projection — возвращаем не всю Entity, только нужные поля
    @Query("SELECT u.id as id, u.name as name, u.email as email FROM User u")
    List<UserSummary> findAllSummaries();                        // интерфейс-проекция
}

// ── Интерфейс проекции
public interface UserSummary {
    Long   getId();                                              // Spring создаёт прокси
    String getName();
    String getEmail();
}
4. Кастомные исключения сервиса
Java
// ── Базовое исключение приложения
public abstract class AppException extends RuntimeException { // Unchecked — не нужен throws
    private final HttpStatus status;                            // HTTP статус для ответа

    protected AppException(String message, HttpStatus status) {
        super(message);
        this.status = status;
    }

    public HttpStatus getStatus() { return status; }
}

// ── 404 Not Found
public class ResourceNotFoundException extends AppException {
    public ResourceNotFoundException(String resource, Long id) {
        super(resource + " с id " + id + " не найден", HttpStatus.NOT_FOUND);
    }
    public ResourceNotFoundException(String resource, String field, String value) {
        super(resource + " с " + field + "='" + value + "' не найден", HttpStatus.NOT_FOUND);
    }
}

// ── 409 Conflict
public class EmailAlreadyExistsException extends AppException {
    public EmailAlreadyExistsException(String email) {
        super("Email '" + email + "' уже используется", HttpStatus.CONFLICT);
    }
}

// ── 422 Unprocessable Entity — бизнес-правило нарушено
public class InsufficientFundsException extends AppException {
    public InsufficientFundsException(Long accountId, BigDecimal required) {
        super("На счёте " + accountId + " недостаточно средств. Нужно: " + required,
              HttpStatus.UNPROCESSABLE_ENTITY);
    }
}

// ── Использование в сервисе
throw new ResourceNotFoundException("User", id);           // → 404
throw new EmailAlreadyExistsException(email);                // → 409
throw new InsufficientFundsException(accountId, amount);     // → 422
5. Strategy паттерн в сервисе
Java
// ── Интерфейс стратегии
public interface NotificationStrategy {
    boolean supports(NotificationType type);  // поддерживает ли этот тип
    void    send(String recipient, String message);
}

// ── Реализации
@Service
public class EmailNotificationStrategy implements NotificationStrategy {
    @Override
    public boolean supports(NotificationType type) {
        return type == NotificationType.EMAIL;
    }
    @Override
    public void send(String recipient, String message) {
        // отправка email через JavaMailSender
    }
}

@Service
public class SmsNotificationStrategy implements NotificationStrategy {
    @Override
    public boolean supports(NotificationType type) {
        return type == NotificationType.SMS;
    }
    @Override
    public void send(String recipient, String message) {
        // отправка SMS
    }
}

// ── Сервис автоматически получает ВСЕ реализации
@Service
@RequiredArgsConstructor
public class NotificationService {

    // Spring инжектирует все бины NotificationStrategy автоматически!
    private final List<NotificationStrategy> strategies;

    public void send(NotificationType type, String recipient, String message) {
        strategies.stream()
            .filter(s -> s.supports(type))           // находим подходящую стратегию
            .findFirst()
            .orElseThrow(() -> new IllegalArgumentException(
                "Нет стратегии для: " + type))
            .send(recipient, message);               // полиморфный вызов
    }
}
❓ Вопросы для собеседования
Зачем нужен Service слой? Почему нельзя писать логику в контроллере?
Why do we need a Service layer? Why not put logic in the controller?
Easy▼
✅ Ответ
Service слой обеспечивает: 1) Разделение ответственности — контроллер знает только HTTP, сервис — только бизнес. 2) Переиспользование — логику можно вызвать из разных контроллеров, Kafka-слушателей, schedulers. 3) Тестируемость — сервис тестируется без HTTP контекста. 4) Транзакции — управляются в одном месте. 5) Безопасность — @PreAuthorize на методах сервиса.
Как работает @Transactional? Что такое propagation?
How does @Transactional work? What is propagation?
Medium▼
✅ Ответ
Spring создаёт AOP прокси вокруг метода: открывает транзакцию до вызова, коммитит при успехе, откатывает при RuntimeException. Propagation определяет поведение при вложенных транзакциях: REQUIRED (default) — использует существующую или создаёт новую. REQUIRES_NEW — всегда новая независимая транзакция. Важно: откатывает по умолчанию только RuntimeException, не checked.
⚠️ Частые ошибки
Self-invocation — вызов @Transactional метода из того же класса не работает (прокси минуется). @Transactional на private методах не работает. readOnly = true при write операциях — данные не сохранятся.
Зачем readOnly = true в @Transactional?
What is the purpose of readOnly = true in @Transactional?
Medium▼
✅ Ответ
readOnly = true даёт оптимизации: 1) Hibernate не делает dirty checking (не проверяет что изменилось) — быстрее. 2) Не делает flush перед запросом. 3) JDBC драйвер может оптимизировать соединение. 4) Документирует намерение — читаем, не пишем. Используй на всех GET методах сервиса. Если поставить readOnly = true на метод с save() — изменения могут не сохраниться.
Чем JpaRepository отличается от CrudRepository?
What is the difference between JpaRepository and CrudRepository?
Easy▼
✅ Ответ
CrudRepository — базовый CRUD: save, findById, findAll, delete, count. PagingAndSortingRepository добавляет пагинацию и сортировку. JpaRepository расширяет оба и добавляет: flush(), saveAll(), deleteAllInBatch(), getReferenceById(), findAll(Pageable). Используй JpaRepository — он включает всё нужное для JPA.
Что такое N+1 проблема и как её решить?
What is the N+1 problem and how do you fix it?
Hard▼
✅ Ответ
N+1: при загрузке N сущностей с lazy связями — каждое обращение к связи делает отдельный SELECT. Итого: 1 запрос для списка + N запросов для каждой связи. Решения: 1) JOIN FETCH в JPQL: SELECT u FROM User u JOIN FETCH u.orders. 2) @EntityGraph на методе репозитория. 3) @BatchSize(size=20) — пакетная загрузка. 4) Проекции (DTO) вместо Entity. 5) Нативный SQL с JOIN.
🔥 Диагностика
Включи логирование: spring.jpa.show-sql=true и считай запросы. Или Hibernate Statistics, p6spy, datasource-proxy.
