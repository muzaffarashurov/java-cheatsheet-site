📌 Краткий конспект
Что такое Redis
Redis (Remote Dictionary Server) — in-memory хранилище структур данных. Скорость: сотни тысяч операций в секунду. Основное применение в Spring: кэширование, хранение сессий, rate limiting, distributed locks, Pub/Sub.

⏰ TTL и Eviction политики
TTL (Time To Live)

TTL — время жизни ключа в секундах. По истечении Redis автоматически удаляет ключ. Всегда устанавливай TTL — иначе память переполнится.

📡 Pub/Sub

Redis Pub/Sub — механизм публикации/подписки на каналы. В отличие от Kafka — сообщения не сохраняются, subscriber получает только сообщения отправленные пока он подписан.

⚠️ Redis Pub/Sub vs Kafka
Redis Pub/Sub: простой, быстрый, сообщения не сохраняются, нет retry. Подходит для: инвалидация кэша в кластере, real-time уведомления, chat. Kafka: надёжный, сохраняет сообщения, retry, consumer groups. Для важных бизнес-событий — Kafka.
🧩 Паттерны кэширования
ПаттернОписаниеПлюсы/Минусы
Cache-AsideПриложение сначала проверяет кэш, при miss — берёт из БД и кладёт в кэш✅ Гибко. ❌ Cache miss = 2 запроса
Write-ThroughЗапись одновременно в кэш и БД✅ Консистентность. ❌ Запись медленнее
Write-BehindПишем в кэш, асинхронно в БД✅ Быстрая запись. ❌ Риск потери
Read-ThroughКэш сам загружает данные из БД✅ Прозрачно. ❌ Сложнее
💡 Cache stampede (Dog-pile эффект)
Когда TTL истекает у популярного ключа — множество запросов одновременно идут в БД. Решения: Probabilistic Early Expiration, mutex lock при cache miss, background refresh.
✅ Best Practices
✅ Правильно
  • Всегда устанавливать TTL
  • Именование ключей: entity:id:field
  • Сериализация через JSON (читаемо)
  • Настроить maxmemory + политику eviction
  • @CacheEvict при изменении данных
  • Мониторинг: hit rate, memory, connected clients
  • Для distributed lock — Redisson
  • Отдельный Redis для кэша и для сессий
🚫 Ошибки
  • Ключи без TTL — память переполнится
  • Хранить слишком большие объекты (>1МБ)
  • Кэшировать null значения без обработки
  • Не инвалидировать кэш при изменениях
  • Использовать Redis как основную БД
  • Слишком маленький TTL — частые cache miss
  • Слишком большой TTL — устаревшие данные

Java — KafkaConfig
@Configuration
@EnableCaching                                     // включаем кэширование Spring
public class RedisConfig {

    // ── RedisTemplate для работы с Java объектами
    @Bean
    public RedisTemplate<String, Object> redisTemplate(
            RedisConnectionFactory connectionFactory) {

        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(connectionFactory);

        // ── Сериализация ключей как строки
        StringRedisSerializer stringSerializer = new StringRedisSerializer();
        template.setKeySerializer(stringSerializer);
        template.setHashKeySerializer(stringSerializer);

        // ── Сериализация значений как JSON
        GenericJackson2JsonRedisSerializer jsonSerializer =
            new GenericJackson2JsonRedisSerializer();
        template.setValueSerializer(jsonSerializer);
        template.setHashValueSerializer(jsonSerializer);

        template.afterPropertiesSet();
        return template;
    }

    // ── CacheManager с настройками по каждому кэшу
    @Bean
    public CacheManager cacheManager(RedisConnectionFactory connectionFactory) {

        // Конфигурация по умолчанию
        RedisCacheConfiguration defaultConfig = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofHours(1))            // TTL 1 час
            .disableCachingNullValues()                // не кэшировать null
            .serializeKeysWith(
                RedisSerializationContext.SerializationPair
                    .fromSerializer(new StringRedisSerializer()))
            .serializeValuesWith(
                RedisSerializationContext.SerializationPair
                    .fromSerializer(new GenericJackson2JsonRedisSerializer()));

        // Специфичные TTL для разных кэшей
        Map<String, RedisCacheConfiguration> cacheConfigs = Map.of(
            "users",    defaultConfig.entryTtl(Duration.ofMinutes(30)),
            "products", defaultConfig.entryTtl(Duration.ofHours(6)),
            "settings", defaultConfig.entryTtl(Duration.ofDays(1))
        );

        return RedisCacheManager.builder(connectionFactory)
            .cacheDefaults(defaultConfig)
            .withInitialCacheConfigurations(cacheConfigs)
            .build();
    }
}
2. @Cacheable, @CachePut, @CacheEvict
Java
@Service
@RequiredArgsConstructor
@Slf4j
public class UserService {

    private final UserRepository userRepository;
    private final UserMapper     userMapper;

    // ── @Cacheable — кэшируем результат
    // 1й вызов: идёт в БД, кладёт в кэш
    // 2й+ вызовы: возвращает из кэша, метод НЕ выполняется
    @Cacheable(
        value = "users",                        // имя кэша
        key = "#id",                             // ключ = параметр id
        unless = "#result == null"              // не кэшировать null результат
    )
    @Transactional(readOnly = true)
    public UserResponse findById(Long id) {
        log.debug("Cache MISS: загружаем user id={} из БД", id); // только при miss
        return userRepository.findById(id)
            .map(userMapper::toResponse)
            .orElseThrow(() -> new ResourceNotFoundException("User", id));
    }

    // ── Составной ключ кэша
    @Cacheable(value = "users", key = "'email:' + #email")
    public UserResponse findByEmail(String email) {
        return userRepository.findByEmail(email)
            .map(userMapper::toResponse)
            .orElseThrow();
    }

    // ── Условное кэширование
    @Cacheable(
        value = "users",
        key = "#id",
        condition = "#id > 0"                   // кэшировать только если id > 0
    )
    public UserResponse findByIdConditional(Long id) { ... }

    // ── @CachePut — ВСЕГДА выполняет метод И обновляет кэш
    @CachePut(value = "users", key = "#result.id") // ключ из результата
    @Transactional
    public UserResponse update(Long id, UpdateUserRequest request) {
        // метод выполнится и обновит кэш свежими данными
        User user = userRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("User", id));
        userMapper.updateEntity(request, user);
        return userMapper.toResponse(userRepository.save(user));
    }

    // ── @CacheEvict — удаляем из кэша при удалении
    @CacheEvict(value = "users", key = "#id")    // удалить конкретный ключ
    @Transactional
    public void delete(Long id) {
        userRepository.deleteById(id);
        // кэш инвалидируется автоматически
    }

    // ── @CacheEvict allEntries — очистить весь кэш
    @CacheEvict(value = "users", allEntries = true) // удалить все ключи кэша "users"
    public void clearUsersCache() {
        log.info("Кэш users очищен");
    }

    // ── @Caching — несколько операций с кэшем на одном методе
    @Caching(
        put  = { @CachePut(value = "users", key = "#result.id"),
                 @CachePut(value = "users", key = "'email:' + #result.email") },
        evict = { @CacheEvict(value = "userList", allEntries = true) }
    )
    @Transactional
    public UserResponse create(CreateUserRequest request) {
        // кэшируем по id И по email, очищаем список пользователей
        User user = userMapper.toEntity(request);
        return userMapper.toResponse(userRepository.save(user));
    }
}
3. RedisTemplate — ручная работа с Redis
Java
@Service
@RequiredArgsConstructor
public class RedisCacheService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final StringRedisTemplate stringTemplate;     // для простых строк

    // ── String операции (ValueOperations)
    public void setWithTtl(String key, Object value, long ttlSeconds) {
        redisTemplate.opsForValue()
            .set(key, value, Duration.ofSeconds(ttlSeconds)); // SET + TTL
    }

    public Object get(String key) {
        return redisTemplate.opsForValue().get(key);       // GET
    }

    // ── Атомарный инкремент (счётчики)
    public long increment(String key) {
        return redisTemplate.opsForValue().increment(key); // INCR атомарно
    }

    // ── Rate limiting: счётчик запросов с TTL
    public boolean isRateLimited(String userId, int maxRequests) {
        String key = "rate:limit:" + userId;
        Long count = redisTemplate.opsForValue().increment(key);
        if (count == 1) {
            redisTemplate.expire(key, Duration.ofMinutes(1)); // сбрасывать раз в минуту
        }
        return count > maxRequests;                          // превышен лимит?
    }

    // ── Hash операции (объекты)
    public void saveUserSession(String sessionId, Map<String, Object> data) {
        String key = "session:" + sessionId;
        redisTemplate.opsForHash().putAll(key, data);       // HMSET
        redisTemplate.expire(key, Duration.ofHours(24));  // TTL 24 часа
    }

    public Object getSessionField(String sessionId, String field) {
        return redisTemplate.opsForHash()
            .get("session:" + sessionId, field);           // HGET
    }

    // ── Sorted Set — лидерборд
    public void updateScore(String userId, double score) {
        redisTemplate.opsForZSet()
            .add("leaderboard", userId, score);            // ZADD
    }

    public Set<Object> getTopN(int n) {
        return redisTemplate.opsForZSet()
            .reverseRange("leaderboard", 0, n - 1);      // ZREVRANGE top N
    }

    // ── Set — уникальные элементы
    public void trackVisitor(String date, String userId) {
        redisTemplate.opsForSet()
            .add("visitors:" + date, userId);              // SADD
    }

    public long getUniqueVisitors(String date) {
        return redisTemplate.opsForSet()
            .size("visitors:" + date);                    // SCARD
    }

    // ── Distributed Lock через SETNX
    public boolean acquireLock(String resource, String token, long ttlSec) {
        Boolean acquired = redisTemplate.opsForValue()
            .setIfAbsent(                                  // SET NX EX
                "lock:" + resource,
                token,                                     // уникальный токен
                Duration.ofSeconds(ttlSec));
        return Boolean.TRUE.equals(acquired);
    }

    public void releaseLock(String resource, String token) {
        String key = "lock:" + resource;
        String current = (String) redisTemplate.opsForValue().get(key);
        if (token.equals(current)) {                       // проверяем что наш токен
            redisTemplate.delete(key);                    // освобождаем
        }
    }
}
4. Redis Pub/Sub в Spring
Java
// ── Конфигурация Pub/Sub
@Configuration
public class RedisPubSubConfig {

    @Bean
    public MessageListenerAdapter messageListener(CacheInvalidationListener listener) {
        return new MessageListenerAdapter(listener, "onMessage"); // имя метода
    }

    @Bean
    public RedisMessageListenerContainer container(
            RedisConnectionFactory factory,
            MessageListenerAdapter listenerAdapter) {

        RedisMessageListenerContainer container = new RedisMessageListenerContainer();
        container.setConnectionFactory(factory);
        container.addMessageListener(listenerAdapter,
            new PatternTopic("cache:invalidate:*"));    // слушаем паттерн
        return container;
    }
}

// ── Listener — получение сообщений
@Component
@RequiredArgsConstructor
@Slf4j
public class CacheInvalidationListener {

    private final CacheManager cacheManager;

    public void onMessage(String message, String channel) {
        // channel = "cache:invalidate:users:42"
        log.info("Получено сообщение инвалидации: channel={}, message={}", channel, message);
        String[] parts = channel.split(":");
        if (parts.length >= 4) {
            Cache cache = cacheManager.getCache(parts[2]); // "users"
            if (cache != null) {
                cache.evict(parts[3]);                   // "42"
            }
        }
    }
}

// ── Publisher — отправка сообщений
@Service
@RequiredArgsConstructor
public class CacheInvalidationPublisher {

    private final RedisTemplate<String, String> template;

    public void invalidateUserCache(Long userId) {
        template.convertAndSend(
            "cache:invalidate:users:" + userId,          // канал
            "invalidate");                               // сообщение
        // Все экземпляры приложения получат это сообщение и инвалидируют свой кэш
    }
}
❓ Вопросы для собеседования
Чем отличаются @Cacheable, @CachePut и @CacheEvict?
What is the difference between @Cacheable, @CachePut, and @CacheEvict?
Easy▼
✅ Ответ
@Cacheable — при cache hit возвращает из кэша, метод не выполняется. При cache miss — выполняет метод и кладёт результат в кэш.
@CachePut — всегда выполняет метод и обновляет кэш. Используется после update — гарантирует актуальность кэша.
@CacheEvict — удаляет ключ или все ключи кэша. Используется после delete или при инвалидации данных.
Что такое cache stampede и как его предотвратить?
What is cache stampede and how to prevent it?
Hard▼
✅ Ответ
Cache stampede (dog-pile): когда TTL популярного ключа истекает, множество запросов одновременно идут в БД (cache miss storm). Решения: 1) Mutex lock — только первый запрос идёт в БД, остальные ждут (через Redis SETNX). 2) Probabilistic Early Expiration — заранее обновляем кэш до истечения TTL. 3) Background refresh — фоновый поток обновляет кэш за некоторое время до TTL. 4) Staggered TTL — случайный TTL чтобы ключи не истекали одновременно.
Какие структуры данных есть в Redis и когда их использовать?
What Redis data structures exist and when to use each?
Medium▼
✅ Ответ
String: кэш объектов, счётчики, rate limiting. Hash: профиль пользователя (много полей одного объекта). List: очереди, последние N событий (LPUSH+LRANGE). Set: уникальные элементы, теги, пересечения множеств. Sorted Set: лидерборды, топ N по рейтингу, временные диапазоны. HyperLogLog: приближённый подсчёт уникальных (DAU, UV). Stream: лог событий, альтернатива Kafka для простых случаев.
Как реализовать distributed lock через Redis?
How do you implement a distributed lock using Redis?
Hard▼
✅ Ответ
Простой вариант: SET key token NX EX seconds — атомарно устанавливает ключ если его нет (NX) с TTL (EX). При снятии блокировки — проверяем что token наш (чтобы не снять чужой лок) и удаляем. Проблема: если приложение упало после захвата но до освобождения — TTL автоматически освободит. Для продакшена используй Redisson — реализует алгоритм RedLock (несколько Redis узлов) с watch dog (автопродление TTL).
