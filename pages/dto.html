📌 Краткий конспект
DTO (Data Transfer Object)
Объект для передачи данных между слоями приложения или через сеть. Не содержит бизнес-логики. Отделяет внутреннюю модель данных (Entity) от внешнего API.
ТипНаправлениеСодержаниеПример
Request DTOClient → ServerДанные от клиента + валидацияCreateUserRequest
Response DTOServer → ClientДанные для клиента (без секретов)UserResponse
Command DTOController → ServiceКоманда с данными для выполненияCreateUserCommand
Event DTOService → Kafka/QueueСобытие для другого сервисаUserCreatedEvent
ProjectionDB → ServiceПодмножество полей из БДUserSummary (JPA проекция)
🤔 Зачем нужен DTO
❌ Без DTO — возвращаем Entity
  • Раскрываем структуру БД клиенту
  • Пароли, токены попадают в ответ
  • Ленивые связи JPA → N+1 или LazyInitException
  • Изменение Entity ломает API
  • Нельзя контролировать что отдаётся
  • Jackson сериализует всё подряд
✅ С DTO
  • Полный контроль над структурой ответа
  • Чувствительные поля скрыты (password, token)
  • Нет проблем с JPA lazy loading
  • Можно менять Entity не трогая API
  • Можно агрегировать данные из нескольких сущностей
  • Валидация входных данных отдельно
🚫 Никогда не делай так
return userRepository.findById(id); — возвращать Entity из контроллера напрямую. Поле password уйдёт в JSON ответ. @OneToMany(fetch = LAZY) вызовет ошибку или N+1 при сериализации.
🗂 Типы DTO
Request DTO — данные от клиента ▼

Принимает данные от клиента. Содержит аннотации валидации. Не должен содержать вычисляемые поля. Именование: CreateUserRequest, UpdateOrderRequest, LoginRequest.

Response DTO — данные клиенту ▼

Отдаёт данные клиенту. Только нужные поля — никаких паролей, внутренних токенов. Может содержать вычисляемые поля (fullName = firstName + lastName). Именование: UserResponse, OrderResponse, ProductResponse.

Nested DTO — вложенные объекты ▼

Когда Response содержит связанные объекты. Например, OrderResponse содержит List<OrderItemResponse> и UserSummaryResponse. Каждый вложенный объект — тоже DTO, а не Entity.

Pagination DTO — страничный ответ ▼

Обёртка для страничных данных. Содержит: список элементов, номер страницы, размер, общее количество, флаг последней страницы. Spring Data Page сериализуется в объёмный JSON — лучше создать свой PageResponse<T>.

📝 Java record (Java 16+)

record — идеальный выбор для DTO. Автоматически генерирует: конструктор, геттеры, equals(), hashCode(), toString(). Immutable по умолчанию.

✅ Best Practices
✅ Правильно
  • Отдельный DTO для каждого направления (Request/Response)
  • Использовать record для DTO (Java 16+)
  • Маппинг в сервисе или через отдельный Mapper класс
  • Никогда не возвращать Entity из контроллера
  • Валидация только в Request DTO
  • Именование: CreateUserRequest, UserResponse
  • Вложенные DTO для связанных объектов
  • PageResponse обёртка вместо Spring Page напрямую
🚫 Ошибки
  • Один DTO и для запроса и для ответа
  • Возвращать Entity из контроллера или сервиса
  • Хранить бизнес-логику в DTO
  • Помещать пароли/токены в Response DTO
  • Слишком большой DTO со всеми полями всех сущностей
  • Маппинг в контроллере — должен быть в сервисе/маппере
💻 Примеры кода
1. Request и Response DTO через record
Java
// ── Request DTO — данные от клиента с валидацией
public record CreateUserRequest(

    @NotBlank(message = "Имя обязательно")
    @Size(min = 2, max = 50)
    String name,                              // компонент record = final поле

    @NotBlank @Email
    String email,

    @NotBlank
    @Size(min = 8)
    String password,                          // есть в запросе, НЕТ в ответе

    @Min(0) @Max(120)
    Integer age
) {}
// record автоматически генерирует:
// - конструктор CreateUserRequest(name, email, password, age)
// - геттеры: name(), email(), password(), age()
// - equals(), hashCode(), toString()

// ── Response DTO — данные клиенту (без пароля!)
public record UserResponse(
    Long    id,
    String  name,
    String  email,
    // password — НИКОГДА не включаем в ответ!
    String  role,
    boolean active,
    Instant createdAt
) {}

// ── UpdateUserRequest — только изменяемые поля
public record UpdateUserRequest(
    @NotBlank String name,
    @NotBlank @Email String email,
    Integer age                               // опционально
) {}

// ── PatchUserRequest — все поля опциональны (null = не изменять)
public record PatchUserRequest(
    String  name,                             // null = не менять
    String  phone,                            // null = не менять
    Integer age                               // null = не менять
) {}

// ── LoginRequest / AuthResponse
public record LoginRequest(@NotBlank String email, @NotBlank String password) {}
public record AuthResponse(String accessToken, String refreshToken, Long expiresIn) {}
2. Вложенные DTO (Nested)
Java
// ── Краткое DTO пользователя для вложения
public record UserSummary(          // минимум полей для отображения в списке
    Long   id,
    String name,
    String email
) {}

// ── DTO позиции заказа
public record OrderItemResponse(
    Long       productId,
    String     productName,
    int        quantity,
    BigDecimal price,
    BigDecimal subtotal           // вычисляемое поле: quantity * price
) {}

// ── DTO заказа с вложенными объектами
public record OrderResponse(
    Long                   id,
    String                 status,
    BigDecimal             total,
    UserSummary            customer,    // вложенный DTO пользователя
    List<OrderItemResponse> items,      // список DTO позиций
    Instant                createdAt
) {}

// ── Маппинг с вложенными DTO в сервисе
public OrderResponse toResponse(Order order) {
    return new OrderResponse(
        order.getId(),
        order.getStatus().name(),
        order.getTotal(),
        new UserSummary(                  // маппинг пользователя
            order.getCustomer().getId(),
            order.getCustomer().getName(),
            order.getCustomer().getEmail()
        ),
        order.getItems().stream()          // маппинг списка позиций
            .map(this::toItemResponse)
            .toList(),
        order.getCreatedAt()
    );
}

private OrderItemResponse toItemResponse(OrderItem item) {
    return new OrderItemResponse(
        item.getProduct().getId(),
        item.getProduct().getName(),
        item.getQuantity(),
        item.getPrice(),
        item.getPrice().multiply(           // вычисляем subtotal
            BigDecimal.valueOf(item.getQuantity()))
    );
}
3. PageResponse — своя обёртка для страничных данных
Java
// ── Своя обёртка для Page (Spring Page слишком объёмный)
public record PageResponse<T>(
    List<T> content,       // данные текущей страницы
    int      page,          // номер текущей страницы (0-based)
    int      size,          // размер страницы
    long     totalElements, // всего элементов
    int      totalPages,    // всего страниц
    boolean  last           // последняя ли страница
) {
    // Фабричный метод из Spring Page
    public static <T> PageResponse<T> of(Page<T> page) {
        return new PageResponse<>(
            page.getContent(),           // список элементов
            page.getNumber(),            // номер страницы
            page.getSize(),              // размер
            page.getTotalElements(),     // всего
            page.getTotalPages(),        // страниц
            page.isLast()               // последняя?
        );
    }
}

// ── Использование в контроллере
@GetMapping
public ResponseEntity<PageResponse<UserResponse>> getAll(
        @RequestParam(defaultValue = "0")  int page,
        @RequestParam(defaultValue = "20") int size) {

    Pageable pageable = PageRequest.of(page, size);
    Page<UserResponse> result = userService.findAll(pageable);
    return ResponseEntity.ok(PageResponse.of(result));  // компактный JSON
}

// JSON ответ:
// {
//   "content": [ {...}, {...} ],
//   "page": 0,
//   "size": 20,
//   "totalElements": 156,
//   "totalPages": 8,
//   "last": false
// }
4. Ручной маппинг через статический метод
Java
// ── Вариант 1: статический фабричный метод в DTO (from Entity)
public record UserResponse(
    Long id, String name, String email, String role, Instant createdAt
) {
    // Статический метод маппинга — читается как "UserResponse из User"
    public static UserResponse from(User user) {
        return new UserResponse(
            user.getId(),
            user.getName(),
            user.getEmail(),
            user.getRole().name(),              // Enum → String
            user.getCreatedAt()
        );
    }
}

// Использование:
UserResponse dto = UserResponse.from(user);  // читаемо и явно

// ── Вариант 2: отдельный Mapper класс (без MapStruct)
@Component
public class UserMapper {

    public UserResponse toResponse(User user) {
        return new UserResponse(
            user.getId(),
            user.getName(),
            user.getEmail(),
            user.getRole().name(),
            user.getCreatedAt()
        );
    }

    public User toEntity(CreateUserRequest request) {
        return User.builder()
            .name(request.name())
            .email(request.email().toLowerCase())   // нормализация
            .role(Role.ROLE_USER)                    // дефолт
            .build();
        // password не тут — хэшируется в сервисе!
    }

    // Маппинг списка
    public List<UserResponse> toResponseList(List<User> users) {
        return users.stream()
            .map(this::toResponse)               // маппинг каждого элемента
            .toList();
    }
}

// ── Использование в сервисе
@Service
@RequiredArgsConstructor
public class UserService {
    private final UserRepository userRepository;
    private final UserMapper     userMapper;        // инжектируем маппер

    @Transactional(readOnly = true)
    public List<UserResponse> findAll() {
        return userMapper.toResponseList(userRepository.findAll()); // маппинг в сервисе
    }
}
5. JPA Projection — DTO прямо из запроса
Java
// ── Интерфейс проекции — Spring Data создаёт прокси
public interface UserSummaryProjection {
    Long   getId();      // имена методов совпадают с именами полей Entity
    String getName();
    String getEmail();

    // @Value для вычисляемых полей (SpEL выражение)
    @Value("#{target.name + ' (' + target.email + ')'}")
    String getDisplayName();                     // "Иван (ivan@mail.ru)"
}

// ── Репозиторий с проекцией
public interface UserRepository extends JpaRepository<User, Long> {

    // Spring Data вернёт только нужные колонки — быстрее!
    List<UserSummaryProjection> findByActiveTrue();

    // С @Query — явный JPQL
    @Query("SELECT u.id AS id, u.name AS name, u.email AS email FROM User u")
    List<UserSummaryProjection> findAllSummaries();
}

// ── Class-based Projection (record) — альтернатива интерфейсу
public record UserSummaryDto(Long id, String name, String email) {}

@Query("SELECT new com.example.dto.UserSummaryDto(u.id, u.name, u.email) FROM User u")
List<UserSummaryDto> findAllAsDto();               // конструктор вызывается в JPQL
6. Кастомный Jackson для DTO
Java
// ── Управление сериализацией через Jackson аннотации
public record UserResponse(
    Long    id,

    @JsonProperty("full_name")           // в JSON будет "full_name" вместо "name"
    String  name,

    String  email,

    @JsonIgnore                           // это поле НЕ будет в JSON
    String  internalCode,

    @JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss", timezone = "UTC")
    LocalDateTime createdAt,             // формат даты в JSON

    @JsonInclude(JsonInclude.Include.NON_NULL) // не включать если null
    String  phone                         // если null — поля нет в JSON
) {}

// ── @JsonView — разные представления одного DTO
public class Views {
    public interface Public  {}
    public interface Admin extends Public {}  // Admin включает всё из Public
}

public class UserDto {
    @JsonView(Views.Public.class)            // видят все
    public Long   id;

    @JsonView(Views.Public.class)
    public String name;

    @JsonView(Views.Admin.class)             // только для ADMIN
    public String internalNotes;
}

// Использование в контроллере:
@GetMapping("/{id}")
@JsonView(Views.Public.class)               // клиент видит только Public поля
public UserDto getUser(@PathVariable Long id) { ... }

@GetMapping("/admin/{id}")
@PreAuthorize("hasRole('ADMIN')")
@JsonView(Views.Admin.class)              // admin видит все поля
public UserDto getUserAdmin(@PathVariable Long id) { ... }
❓ Вопросы для собеседования
Что такое DTO и зачем он нужен?
What is a DTO and why do we use it?
Easy▼
✅ Ответ
DTO (Data Transfer Object) — объект для передачи данных между слоями или через сеть, без бизнес-логики. Нужен чтобы: 1) скрыть чувствительные поля (пароль, токены), 2) отделить внутреннюю модель от API — можно менять Entity не ломая контракт, 3) избежать проблем с JPA lazy loading при сериализации, 4) контролировать что именно отдаётся клиенту.
Почему нельзя возвращать Entity из контроллера?
Why shouldn't you return JPA Entity from a REST controller?
Medium▼
✅ Ответ
1. Безопасность: поле password попадёт в JSON.
2. JPA проблемы: @OneToMany(fetch=LAZY) вызовет LazyInitializationException или N+1 запросов при сериализации.
3. Связанность: изменение структуры Entity автоматически меняет API — нарушение контракта.
4. Гибкость: DTO может содержать агрегированные данные из нескольких Entity или вычисляемые поля.
Что такое Java record и почему он подходит для DTO?
What is a Java record and why is it good for DTOs?
Medium▼
✅ Ответ
record (Java 16) — компактное объявление класса с автоматическим конструктором, геттерами, equals(), hashCode(), toString(). Immutable по умолчанию. Идеален для DTO потому что DTO: должен быть immutable (данные не меняются после создания), нужны equals/hashCode (сравнение ответов в тестах), минимум кода — нет геттеров, сеттеров, constructors вручную.
Где должен происходить маппинг Entity ↔ DTO?
Where should Entity to DTO mapping happen in the application?
Medium▼
✅ Ответ
Маппинг должен происходить в сервисном слое или в отдельном Mapper классе, который инжектируется в сервис. В контроллере — только HTTP логика. В репозитории — только CRUD. Контроллер принимает Request DTO, передаёт в сервис, получает Response DTO — ничего не маппирует сам. Альтернатива: MapStruct генерирует маппер при компиляции.
